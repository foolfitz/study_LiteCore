# 2026-08-15/16 — D3 的八格、以及擋在它前面的 finding 048

## 一句話

D3 的清單八格跑完了（**六個預測成立、兩個不成立、零內容遺失**），但在那之前
先掉出 [finding 048](../findings/048-place-caret-confirms-before-the-click-takes-effect.md)：
**`placeCaret` 在點擊生效之前就回報成功**，於是第一輪八格全部在文件第一段動作，
其中三格回綠而且什麼都沒量到。

## 怎麼發現的

第一輪能派送的結果看起來像一份可以分析的資料：八格裡五格 `verified-format-readback`、
三格 `EDITOR_FORMAT_POSTCONDITION_FAILED`。**是去看存檔文件才發現不對**——
`lists=3 items=5` 這種數字對得上「新增了一個清單」，但打開 XML 看，變成清單項的是
`E1-LC-HEADING`，而那一格的錨點在四段之外。

教訓不新，但這次的形狀值得記：**完成碼與計數都「說得通」，只有結構本身會說謊被抓到**。

## 一次判斷錯誤，以及推翻它的東西

我第一版把 048 寫成「合成滑鼠點擊完全不會移動游標」，理由是四組對照裡游標一直停在
`y=1418`：沒繪製、繪製過、已經有游標之後再點——都不動。

**推翻它的是 D2 自己的存檔文件。** D2 在手勢與動作之間有一次 `snapshot()` 存檔，
而那一格的 after 文件顯示變成清單項的**正是點的那個空段落**。點擊是有效的，
只是不同步。改用輪詢量：**22–28 ms**（Chrome）、**23–33 ms**（Firefox）。

固定延遲的階梯（250／500／1000／2000）只能回答「這麼久夠了」，回答不了「多久」。
**換成輪詢才是量測。**

## 八格的結果

| 格 | 預測 | 結果 |
|---|---|---|
| L1 | 獨立段落 → 新的項目符號清單 | ✅ |
| L2 | 最後一段 → **新的**編號清單 | ❌ 併入上面那個編號清單 |
| L3／L4 | 第二項離開、第一項留著 | ✅ |
| L5 | 就地轉編號、**不出現第三個清單** | ❌ 清單 2 → 3 |
| L6 | 重複派送 → body 位元組相同 | ✅（對照組是「什麼都不做的存檔」） |
| L7 | 中間項離開 → 一分為二、不掉項 | ✅ 三項都在、`continue-numbering="true"` |
| L8 | 與前面的清單合併 | ✅ |

**L7 是上位規格停止條款正對著的那一格，沒有觸發。** 八格 `textLost` 全空。

兩個不成立的預測是同一種東西：**相鄰同型清單會合併**。L2、L8 都合併了，L5 因為
轉成不同型所以必然分裂。事後看是一條連貫的規則，但**預測是照寫下來的樣子計分的**。

L6 的判準在執行中就地更正過：原本寫「與磁碟上的語料位元組相同」，那必然不同——
語料是本 repo 的產生器寫的、存檔是 LibreOffice 匯出寫的。能回答那個預測的對照組是
**同一份文件、什麼都不做的存檔**，因此加了 `L6C`。這是**更正判準，不是放寬判準**：
它讓 L6 從「量不到」變成「量得到而且成立」。

## 順帶掉出來的三件

1. **[046](../findings/046-an-empty-readback-is-reported-as-the-document-being-in-the-wrong-state.md) 的修法不在原始碼樹裡。**
   `grep -rn "empty-readback" src/` 零筆。先前的紀錄寫成「已寫、待 relink」是錯的；
   P1 的其他四項確實在樹裡。
2. **同一個空段落有兩個出口，取決於手勢。** 產品點擊 → `postcondition-not-met`；
   派送前已證明游標在該段落 → `multi-block-readback`。兩者 `postBlocks` 都是 0，
   差別在 `itemCount`——**而產品投影沒有這一欄**。relink 佇列新增 3c。
3. **一次證據覆蓋事故。** 第二次跑 D3 時 `--output` 指到第一次執行的目錄，
   把 047 那一輪的紀錄蓋掉了。已從 git 還原，被蓋掉的另存 `run-1b-before-skip/`；
   runner 現在會在**開瀏覽器之前**拒絕寫進已有 `result.json` 的目錄。
