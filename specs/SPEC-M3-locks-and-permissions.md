# SPEC M3：鎖與權限

2026-09-28 立。擁有者裁示 A（`handoff/HANDOFF-2026-09-28f-host-entry-landed-shell-v53.md`：鎖與權限先做），
並在第 0 步量完之後選了 **token 鎖＋逾時**（同日）。

## 1. 為什麼要有

宿主入口落地之後（`findings/evidence/m3-host-entry/RESULT.md`）剩一條**已命名的資料遺失路徑**：伺服器拒絕寫入
但不是衝突——403（唯讀）、423（鎖住）、斷線——內容只在頁面裡、沒有出口。另外路線圖 §5.5 的完成判準要「鎖正確」，
而宿主目前完全不上鎖。

## 2. 第 0 步量到的事實（已觀察）

`findings/evidence/m3-locks/README.md`，HTTP 層、兩輪一致（L6 一輪）。決定設計的那幾條：

- `files_lock` 隨 NC 34 正式版 tarball 出貨且預設啟用；使用者鎖**預設永不過期**（`lock-timeout -60`）。
- 上鎖與解鎖都會**改檔案自己的 ETag**；同一把鎖續約不改；token 鎖過期不改。
- token 鎖（RFC 4918 `LOCK`＋`Timeout`）：持有者不帶 token 的 PUT 是 423，帶了是 204；到時沒續約就失效；同一個使用者的
  第二個視窗再鎖是 423；檔案擁有者可以不帶 token 解掉它。
- **帶著已失效 token 的 PUT 是 412**，即使 `If-Match` 正確、檔案沒被動過；只帶 `If-Match` 是 204。
- 唯讀分享的檔案 PUT 是 403，但在收件人自己的資料夾放新檔是 201；唯讀分享的**資料夾**裡放新檔也是 403；超過配額 507。
- 檔案被別人鎖住時，OCS 上鎖端點回 500 而不是 423（finding 100），DAV `LOCK` 回 423。

## 3. 宿主的行為

全部在 `litecore` app（`js/litecore-editor.js`、`EditorController`、`templates/editor.php`）。**產品頁的位元組不動**
（`web/e2-editor-app.js` 仍是 `fbfb59a4…`、殼層仍是 v53），頁面契約（`SPEC-M3-host-entry.md` §2）不變：宿主的 `save()`
成功就 resolve，否則 throw，頁面把訊息顯示出來。

**開檔**

- O1 路由把 `writable`（`$node->isUpdateable()`）交給宿主。
- O2 可寫時，**先** `LOCK`（token 鎖，`Timeout: Second-300`，`<d:owner>` 是使用者的顯示名稱——別人看到的持有者名字就是它），**再** GET。ETag 取自 GET，所以是上鎖之後的版本。
  - 200：~~持有 token。~~ 再用 PROPFIND `lockdiscovery` 確認 token 真的在伺服器上才算持有（使用者自己已有一把使用者鎖時，LOCK 也回 200 卻沒有 token 鎖）。
  - 423：不持有；宿主去問持有者是誰（PROPFIND `nc:lock-owner-displayname`），在宿主列顯示「正被〈誰〉鎖定編輯：你的存檔會另存副本」
    （持有者是自己時寫「你在另一個視窗或裝置開著它」）。
  - 其他狀態或網路錯誤：不持有；宿主列顯示「無法上鎖」。仍照常開檔。
- O3 不可寫時不送 `LOCK`；宿主列顯示「唯讀：你的存檔會另存副本」。

**持有**

- K1 每 60 秒續約（`LOCK`＋`If: (<token>)`＋~~`Timeout: Second-300`~~`Timeout: Second-(自上鎖以來的秒數＋300)`——files_lock 的續約不會把到期時間往後延，只會把 ttl 設成請求的秒數，而到期＝上鎖時間＋ttl（finding 101），所以要自己把經過的時間加進去）。~~任何非 200 的 HTTP 回應~~ 400、404、409、412、423＝鎖已失去：丟掉 token、停止續約、
  宿主列顯示「鎖已失效」。~~或網路錯誤~~**網路錯誤不算**，其他狀態（5xx、401、429…）也不算：伺服器上的鎖可能還在，下一次再續；真的失效了，下一次存檔由 S3 接住。**不重新上鎖**（重新上鎖會改 ETag，而那時已分不出「是我自己改的」還是「別人在空窗期寫過」）。

**存檔**（`save(bytes)`，一次一個，頁面已排隊）

- S1 PUT 一律帶 `If-Match`；持有 token 時另帶 `If: (<token>)`。
- S2 2xx：成功，換成新的 ETag。
- S3 帶著 token 拿到 412：~~**丟掉 token，只帶 `If-Match` 重送一次**~~ **先 PROPFIND `lockdiscovery`**：token 還在＝鎖活著、是版本真的變了，不重送、直接照 S4 另存（鎖留著）；token 不在了才**丟掉 token，只帶 `If-Match` 重送一次**，結果照 S2／S4 處理。理由是第 2 節：失效的 token 本身就會造成 412；而別人一個**被拒絕**的解鎖也會改 ETag（files_lock `unlockFile` 先改 ETag 才檢查權限），那時鎖其實還活著。
- S4 其他任何拒絕（沒帶 token 的 412、423、403、507、401、其他 4xx／5xx）、網路失敗，或根本不知道伺服器上的版本（此時不送 PUT）：把這份位元組以 `If-None-Match: *` 另存在
  同一個資料夾（412、423 叫「〈原名〉（衝突副本 〈時間〉）.odt」，其餘叫「〈原名〉（另存副本 〈時間〉）.odt」）。
  - 另存成功：throw，訊息說明原檔沒被覆寫、內容存在哪個檔名。
  - 另存也失敗：這份位元組**留在宿主手上**，宿主列出現「下載這份內容」按鈕，並**擋住關頁**（`beforeunload`）；throw，訊息說明
    內容還在頁面裡、請按下載。
- S5 ~~下列任一件發生之後，擋關頁就解除、按鈕收起：使用者按了下載，或之後有一次存檔（寫進原檔或另存副本）成功。~~ 只有之後有一次存檔（寫進原檔或另存副本）成功，擋關頁才解除、按鈕才收起。按了下載不算：頁面看不到下載有沒有真的存好（使用者可能在「另存新檔」對話框按了取消），所以按過之後按鈕仍在（可再下載），離開仍會先問。
- S5′ 有存檔還在進行（還沒 settled）時也擋關頁。
- S6 下載只在使用者按按鈕時發生（使用者手勢），不自動觸發。

**關頁**

- C1 `pagehide` 時以 `fetch(…, { keepalive: true })` 送 `UNLOCK`（`Lock-Token`）~~，~~**兩次**，停止續約。送兩次是實測的選擇，不是有解釋的選擇：Chrome 151 在這條路由上單獨一個 UNLOCK 到達伺服器 0/4、兩個 4/4，原因未明（`findings/evidence/m3-locks/unload/README.md`）；~~第二個若多餘，伺服器回 412、什麼都不改。~~ 第二個若多餘，伺服器可能回 204 或 500（依原始碼；Firefox 的 access log 量到 204＋204），都不會解掉別人的鎖（Sabre 比對 token）。
- C1′ **關分頁或關整個瀏覽器時不釋放**（量到的，見修訂紀錄）：鎖在 300 秒內自己失效，跟當掉一樣。所以關掉之後 5 分鐘內重開同一個檔，宿主會說「你在另一個視窗或裝置開著這個檔案」，存檔會另存副本——具名限制，資料不會掉。
- C2 瀏覽器當掉或被砍時，鎖在最後一次續約之後 300 秒內自己失效（續約真的延長之後，這句才不是空話）（第 2 節 L3 量過機制，這裡量的是整條路）。

**明確不承諾**：頁面沒有唯讀模式（唯讀檔照樣能編輯，存檔走另存）；「乾淨」仍在宿主收下之前就成立（殼層語意，另一步）；
頁面沒有 dirty 追蹤，所以**從沒按過儲存**的編輯在關頁時不擋；背景分頁的計時器節流（Chrome 隱藏 5 分鐘後對齊到每分鐘）
理論上仍在 300 秒之內，**不量**；bfcache 回來的頁面不重新上鎖；開檔與上鎖之間檔案被刪掉時，`LOCK` 會建出一個空檔（Sabre，未量）；存檔進行中離頁的保護（S5′）未量。
鎖只擋得住照規矩來的用戶端：有寫入權的人拿持有者的 token 送 PUT，伺服器照收（finding 102，上游；token 在 PROPFIND `lockdiscovery` 與被拒絕解鎖的 423 本文裡都看得到）。~~宿主不因此掉資料——寫入一律帶 `If-Match`，~~ 寫穿換了 ETag 時宿主不掉資料——寫入一律帶 `If-Match`，「token 還在、PUT 卻 412」走副本且不重送，這條路徑由 K12 驅動；**寫穿本身不在任何一臂裡**。但寫穿若與**宿主手上那個 ETag 所屬的寫入**（宿主最後一次成功的存檔，或開檔時讀到的版本）落在同一秒，ETag 不會換（finding 103），宿主的下一次存檔會把它蓋掉；被蓋掉的內容留在版本歷史裡（`specs/SPEC-M3-versions.md` §5）。

## 4. 驗收判準（先於任何宿主改動與量測寫下）

宿主＝`litecore` app，環境同宿主入口（ddev、NC 34.0.2 tarball、Apache、admin）。第二使用者 `lcprobe` 由 runner 每次計數執行
建一次、跑完刪除；分享在一開始一次建好（Nextcloud 對建立分享有每 10 分鐘 20 次的限制，第 0 步撞到過 429）。每一臂一個新瀏覽器。
