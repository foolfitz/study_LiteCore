---
name: upstream-findings
description: >
  Record a bug found in someone else's codebase (upstream project, dependency,
  vendor SDK) so it can actually be reported later without losing the evidence.
  Use when work turns up a defect that is not in the user's own code — a crash
  in a library, a broken build rule upstream, behaviour that contradicts the
  project's own docs — especially when the user says they will report it later,
  or when several findings are accumulating. Also use when preparing a finding
  for submission, or auditing which findings are actually ready to send.
---

Findings evaporate. Three days later the version string is fuzzy, the exact
error message is paraphrased, and nobody remembers which hypotheses were already
ruled out. That missing detail is exactly what a triager uses to decide whether
to accept the report.

So: **capture at discovery time, report later.**

## Layout

```
findings/
├── README.md              index table + workflow
├── TEMPLATE.md
├── env-snapshot.sh        generates the environment block
├── NNN-short-slug.md      one file per finding
├── drafts/                submission-ready text, written when a finding is ready
└── evidence/NNN/          raw artifacts, never paraphrased
```

Create `findings/` at the repo/workspace root, not inside the source tree of the
project being reported against — it is the user's work product, not a patch.

## The finding file

Header table first, so the index can be generated by scanning:

| field | values |
|---|---|
| 狀態 / status | 待驗證 → 可送出 → 已回報 → 已修 ／ 撤銷 |
| Bugzilla / tracker | id, filled in after submission |
| 嚴重度 | blocker / severe / normal / minor |
| 可重現 | 100% / n out of m / unconfirmed |
| **是否上游** | **yes / no (our config) / UNCONFIRMED** |

Then: 現象 → 重現步驟（含預期 vs 實際）→ 證據 → 分析 → 環境 → **還缺什麼才能送** → tracker 欄位 → 時間軸.

Two sections carry most of the value:

**「還缺什麼才能送」** — a checklist. This is what stops a half-verified guess
from being submitted months later when the context is gone. Typical items:

- [ ] reproduce on the project's own default configuration
- [ ] symbolised stack / minimal reproducer
- [ ] search the tracker for duplicates
- [ ] confirm which component to file under

**「是否上游」** — never write "yes" before reproducing on a stock configuration.
A bug found only under a custom build is the reporter's problem until proven
otherwise, and getting this wrong once damages the credibility of everything
reported afterwards.

## Evidence discipline

Store raw artifacts as files under `evidence/NNN/`. Quote the few decisive lines
in the finding; keep the full output in the file.

| artifact | note |
|---|---|
| environment | run `env-snapshot.sh` **at discovery time**, not later |
| logs / console | full capture, with timestamps if available |
| build errors | include surrounding context, not just the failing line |
| source excerpts | **always with a commit hash** — line numbers drift |
| screenshots | both the broken and the working state, if there is a working one |

`env-snapshot.sh` must report whether the source tree has **local modifications**,
and list them. Reproducing with local patches applied and not saying so is the
fastest way to get a report dismissed.

If a snapshot is taken under conditions that differ from the reproduction (tree
was reverted, different build dir), append a caveat to the evidence file saying
so. An accurate-looking snapshot that silently misrepresents the repro is worse
than no snapshot.

## Separating fact from inference

Findings usually have a verified input/output relation and an unverified
mechanism. Label them:

- what was **observed** — put it in 現象 / 證據
- what was **ruled out**, and by what test — a table, one row per hypothesis
- what is **inferred** — say "NOT VERIFIED — treat as a hypothesis" in the text
  itself, not only in a covering note

A report whose mechanism section can be deleted without invalidating the report
is a strong report. Write it so that is true.

## Send order

Do not batch. Findings are independent; sending them together only delays the
easy ones.

Rank by (evidence strength × impact) ÷ review cost:

1. **Certain root cause, tiny fix** — send first even if impact is low. Fast
   feedback, and it builds standing with the maintainers.
2. **High impact, solid isolation** — send next. If the maintainer can reproduce
   by flipping one flag, say so prominently.
3. **Certain but niche** — send, cross-reference related findings.
4. **Root cause in a different project** — decide where it belongs *before*
   sending. Filing against the wrong project wastes everyone's time.

## Before submitting, answer these

1. Reproduced on stock configuration?
2. Searched the tracker for duplicates?
3. Which parts are fact and which are inference — is that visible in the text?
4. Is this one bug, or several sharing a file?

Then write the submission text into `drafts/NNN-<tracker>.txt` — in the
project's language, in their format, ready to paste. Where a patch is
appropriate, add `drafts/NNN-commit-msg.txt` with the project's commit
conventions, plus a clearly separated note about their submission process
(hooks, review system, which branch patches must land on first).

After submission, backfill the id into both the finding file and the index.
