# §3.4 ARIA 投影：開工之前先量到的三件事

寫於 2026-08-22，閘門 0 過了之後、寫第一行投影程式碼之前。

路線圖 §3.4 說這條路「目前一行都沒有」，而且「閘門 0 沒過就不要開始」。閘門過了，
所以這份文件處理下一個問題：**開始之後第一步要往哪裡走**，以及一個只有使用者答得
出來的岔路。

---

## 0. 「零行」精確是什麼意思（已量，而且是量報讀軟體真正吃的那棵樹）

**2026-08-22 用 `tools/probe_aria_projection.py` 量到：171 個 accessibility tree
節點，其中帶著文件文字的是 0 個。**整個文件區域就是一個節點：

```
Canvas   name="ODT 文件畫面"   value=None
```

在場的角色有 `RootWebArea`、`Canvas`、`StaticText`、`button`、`combobox`、
`textbox`、`status`……**不在場的**才是重點：沒有 `document`、沒有 `paragraph`、
沒有 `heading`、沒有 `list`。那 52 個 `StaticText` 和 58 個 `InlineTextBox`
全部是工具列、狀態列和 fixture 下拉選單——一個都不是文件內容。

而且這是在**帶 a11y 的那顆 core** 上量的，也就是最好的情況。
證據：[`findings/evidence/aria-projection/BASELINE.md`](../findings/evidence/aria-projection/BASELINE.md)。

**這一格不是人回報的，是量的。**「報讀軟體要人來試」是一個可否證的宣稱，不是一個
類別——finding 073 對 IME 組字犯過同一個錯，而 CDP 的 `Input.imeSetComposition`
當天就否證了它。AX tree 是每一套報讀軟體共同吃的東西，瀏覽器建它，CDP
（`Accessibility.getFullAXTree`）讀得到它，**而同一支儀器之後會用來量投影**。
真正還是要人的那一塊要講窄一點：某一套報讀軟體怎麼**唸**這棵樹（順序、詳簡、
瀏覽模式）是它自己的事，不在這裡。

至於原始標記那一面，`grep -c "aria-"` 是 **3**：

| 位置 | 現況 |
|---|---|
| `<canvas id="canvas" aria-label="ODT 文件畫面">` | 報讀軟體念得出這句標籤，**念不出裡面任何一個字** |
| `<textarea id="sink" aria-label="輸入">` | 輸入槽，1px 透明 |
| `<div id="toast" role="status">` | 提示訊息，這一格其實是好的 |
| 工具列 `aria-pressed` | 格式按鈕的狀態，這一格也是好的 |

所以「零」不是全頁零，是**文件內容零**。報讀軟體使用者拿到的是一張圖片和幾個按鈕。

## 1. 擋路的事實：報讀軟體要的是**文字**，而現在沒有任何一層送得出來

這是開工前必須先知道的，因為它決定投影餵什麼。

**引擎把段落文字算完雜湊就丟掉。**`probe_engine.cpp:1640-1667`：從
`getA11yFocusedParagraph()` 的 JSON 取出 `content`，量長度、算 FNV-1a、存進
`contentHash`，**`content` 這個 std::string 是區域變數，出了函式就不存在**。
`EditorSemanticSnapshot` 裡沒有文字欄位。

而且那是**刻意的**，原始碼自己寫了理由：

> A hash, because the engine does not forward the raw payload to JS […] and the
> host needs to compare, not to read.

worker 的投影也照同一條走（`sdk-worker.js:311-312`）：「a fingerprint and an
offset, never the paragraph's text」。

**產品狀態裡唯一帶文字的欄位是 `selectionText`**——那是**選取**的文字，不是段落的。
想用它讀出一段的內容就得先去選那一段，而**為了念出來而改動使用者的選取，本身就是
一個無障礙缺陷**。這條路不能走。

⇒ **投影今天沒有文字可餵。**

## 2. 決定性的事實：出貨那顆 core 上，這條路是死的（已量）

2026-08-22 在 `e2-editor-v4` 上跑同一支探針，三個游標位置全部：

```
enabled: false   unavailable: "core-built-without-accessibility"
contentLength: 0   fingerprint: cbf29ce484222325（空字串的雜湊）
```

閘門 profile 上則是 `enabled: true` 加三個相異且對得上的指紋。兩顆 profile 乾淨
地相反。

⇒ **不管投影怎麼做，它在今天的產品上不會有任何輸入。**§3.4 要能出貨，
**產品那顆 core 必須帶 accessibility**。

代價已經量到了（`findings/evidence/a11y-gate-0/RESULT.md`）：

| | 產品 core | 帶 a11y 的 core | 差 |
|---|---:|---:|---:|
| `probe.wasm` | 115,297,675 | 135,216,207 | **+19.9 MB** |
| `soffice.data` | 102,765,226 | 108,527,803 | +5.8 MB |

**但這個數字裡有 calc**，而 calc 不是我們要的東西——它只是 `configure.ac` 裡用來
清掉 `ENABLE_WASM_STRIP_ACCESSIBILITY` 的那根槓桿（PATCH.md 選它是因為那是上游
預設、風險最低）。「writer ＋ a11y、不含 calc」這個組態**沒有人量過**，它需要
module 迴圈多一個說法（約三行），然後**再重編一次 core**。

⇒ 在把產品綁上 +19.9 MB 之前，值得先花一次重編去量那個組態。這是判斷題，見 §5。

## 3. 岔路：文字從哪裡來

### 路線 A — 殼層自己解 ODT，用指紋對上

殼層**手上就有文件的 bytes**（是它開的檔）。所以它可以：

1. 解 `content.xml`，取出段落序列（文字 ＋ 角色：標題／清單項／內文）；
2. 把那個結構畫成一份**離屏的 DOM**，帶正確的 ARIA 角色；
3. 游標移動時，引擎給 `paragraphFingerprint`，殼層**對自己那份文字算同一個
   FNV-1a**，對上就把焦點移到那個節點。

第 3 步不是推測——**閘門 0 的判定就是這樣做出來的**：我拿 fixture 的 XML 自己算
FNV-1a，對上了 `d389fc99dd9a78cf` 與 `ecb72cdf76d825c2`，hash 與長度雙雙吻合。
這條路已經被走過一次了，只是走在 python 裡。

- **不用連結、不用改契約。**
- 代價：殼層要有一個 ODT 解析器（範圍有限：`text:p`／`text:h`／清單）。
- **會過期**：使用者編輯之後那份影子就開始漂。殼層知道自己送出了哪些動作，但
  重建是會出錯的；保守作法是重新導出。這是這條路最大的未知。

### 路線 B — 把文字從契約開出去

在產品契約裡加一個具名欄位：焦點段落的文字。

- 引擎改動 ＋ **一次連結** ＋ 契約版本。
- 沒有解析器、不會過期、文字精確。
- 它**牴觸一個刻意的封閉決定**，但要注意 E1-B 的禁令原文是「不把 a11y diagnostic
  counters、scheduler probe 或 **raw callback payload** 升格為產品 state」——
  一個**具名、有目的**的欄位跟「把原始 payload 升格」不是同一件事。這一點值得
  在寫規格時講清楚，而不是拿禁令當結論。

### 兩條路共用的部分（先做這塊不會白做）

- 離屏 DOM 的結構與 ARIA 角色（`role="document"`／標題層級／清單）；
- 游標移動的 live region 播報策略（什麼時候念、念多少、怎麼不吵）；
- 焦點管理與鍵盤導覽（報讀軟體的瀏覽模式 vs 我們的 sink）。

差別只在「文字哪裡來」和「怎麼對上」。

## 4. §3.4 會繼承的三個已具名極限

不要在投影裡重新發現它們：

1. **兩段文字相同的段落指紋相同**，分不出來。這是 LOK 沒有段落序號的直接後果
   （四輪原生量測），已具名。
2. **`listPrefixLength == contentLength` 的段落會塌成空字串指紋**（閘門 0 在標題
   上量到）。`queue-a11y-prefix-swallows-the-paragraph`，兩個假說都還沒量。
3. **`paragraphFresh` 在讀不到的 build 上回報 true**——投影要決定「這個指紋能不能
   信」時讀的正是這一格。已在原始碼修好，**但要等下一次連結才會進到產品**
   （`queue-fresh-is-true-where-no-read-can-succeed`）。

第 1 和第 2 條合起來是同一句話：**指紋是「是不是同一段」的答案，不是「這是第幾段」
的答案。**投影要能在指紋對不上或塌掉的時候**說自己不知道**，而不是指到一個看起來
合理的節點。

## 5. 需要使用者決定的兩件事

**A. 產品 core 要不要帶 accessibility，什麼時候帶。**
不帶＝§3.4 做出來沒有輸入。帶＝目前量到 +19.9 MB（含 calc）。
建議：**先花一次 core 重編去量「writer ＋ a11y、不含 calc」**，再決定要不要綁。
那次重編也順便把 §4 第 3 點的引擎修法帶進產品。

**B. 台灣公部門實際適用的無障礙規範與等級**（路線圖 §10 第 3 題，仍未答）。
它決定 §3.6 的完成判準寫不寫得出來。現在刻意空著——沒有依據就寫死一個判準，比
不寫更糟。這一題會直接影響投影要做到哪裡：只念得出焦點段落，跟能用瀏覽模式在整份
文件裡導覽，是兩個量級。

## 6. §3.4 自己的閘門（在寫程式之前先寫下來）

依這棵樹的規矩，判準先寫：

> **G3.4-1**：報讀軟體在文件區域念得出**焦點段落的文字**，而且游標移到另一段時
> 念出來的**會變**。
>
> 兩半都要。只有一半＝一個會響的事件，不是一份可讀的文件——這正是閘門 0 的
> G0-2 用三個位置去擋掉的同一種假綠燈。

**儀器已經有了，而且已經跑過一次**：`tools/probe_aria_projection.py` 用
`Accessibility.getFullAXTree` 拍下報讀軟體真正吃的那棵樹，§0 的 171／0 就是它量的。
同一支儀器之後量投影，所以前後是同一把尺——兩個印象換不到這個。

還沒有寫死的是**門檻**，而那是刻意的：判準要寫在**投影之前**、放進一份 PREDICTION，
不能從第一次輸出反推。閘門 0 那一輪的整個價值就在這個順序上。

真正還留給人的那一塊要講窄：某一套報讀軟體怎麼**唸**這棵樹（順序、詳簡、瀏覽模式）
是 AT 自己的事，量不到也不該假裝量得到。**「a11y 需要真人」是錯的，「某一套 AT 的
朗讀行為需要真人」是對的**——差別是後者是一個小很多的宣稱。

## 7. 規範來了之後，範圍怎麼變（2026-08-23）

使用者提供了來源：**[網站無障礙規範（110.07）]
(https://accessibility.moda.gov.tw/Accessible/Guide/68)**，2021-07-01 實施，基礎是
**WCAG 2.1**，4 原則／13 指引／**78 條成功準則**；AA ＝ 第1＋第2 優先等級，**68 條
檢測碼**。詳見路線圖 §3.6。

（WCAG 2.1 的成功準則也正好是 78 條，數目相符；但**檢測碼不等於成功準則**，粒度不同，
所以下面這份對照是**對 WCAG 條文**做的，不是對 68 條檢測碼做的。）

### 7.1 這份對照的效力，先講清楚

**不是完整稽核。**官方文件抓不到——`accessibility.moda.gov.tw` 對自動抓取回 403，
NCC 的鏡站解析不到。所以這裡只列**咬到 canvas 文件編輯器**的那些條，而且：

- 條號與等級是**查過的**，不是憑記憶寫的（4.1.2 的等級特地單獨查了一次確認是 A）；
- 有一次抓回來的清單**明顯不完整**（漏了 4.1.2 等條），所以**不宣稱這份列完了**；
- 完整那份要用官方 68 條檢測碼逐條做，而那需要有人能取得文件。**這是使用者能做、
  我做不到的一件事**（或改用能繞過 403 的方式取得）。

### 7.2 咬到我們的條，以及現況

| 準則 | 等級 | 對這個產品的意思 | 2026-08-23 現況 |
|---|---|---|---|
| **1.3.1 Info and Relationships** | **A** | 文件的資訊與關係必須**程式可判定**：標題是標題、清單是清單 | **不符合。**投影只有焦點段落，而且不帶角色 |
| **1.1.1 Non-text Content** | **A** | canvas 要有等效的文字替代 | **不符合。**`aria-label="ODT 文件畫面"` 是標籤不是替代內容 |
| **1.3.2 Meaningful Sequence** | A | 閱讀順序要程式可判定 | **不符合**（沒有順序可讀，只有一段） |
| **4.1.2 Name, Role, Value** | **A** | 每個 UI 元件的名稱與角色可判定 | 工具列大致有（`aria-pressed`）；**文件區域沒有角色** |
| **2.1.1 Keyboard** | A | 全功能鍵盤可達 | 大致有（15 個動作、上下鍵、快捷鍵），**未逐條驗** |
| **2.4.3 Focus Order** | A | 焦點順序不破壞意義 | **未驗** |
| **4.1.3 Status Messages** | AA | 狀態訊息要能被程式判定 | **部分**：`#toast` 是 `role="status"`，投影是 `aria-live` |
| **1.4.10 Reflow** | AA | 320px 寬不得需要雙向捲動 | **未驗，而且是 canvas 固定版面最可能踩到的一條** |
| **1.4.3 / 1.4.11 對比** | AA | 文字與非文字對比 | **未驗**——而文字是**我們畫的**，不是瀏覽器畫的 |

### 7.3 對 §3.4 的直接後果

**「只投影焦點段落」從「已知範圍邊界」變成「已知缺口」。**1.3.1 是 **A 級**，不是
AA——全文件結構投影不是加分項，是最低門檻。2026-08-23 出貨的增量因此是**第一步而
不是一半**。

而這件事把 §3 的岔路重新打開了一次：**結構**（哪些段落、什麼角色、什麼順序）引擎
現在**不給**——它只給焦點那一段。要拿到結構，還是回到那兩條路：

- **路線 A（殼層解 ODT）**：結構本來就在 `content.xml` 裡，`text:h` 的 outline-level
  就是標題層級，`text:list` 就是清單。**不用連結。**
- **路線 B 再走一次**（引擎多吐一份文件大綱）：又是一次引擎改動＋連結。

**注意這跟「文字從哪裡來」不是同一題。**文字選了 B 是因為正確性是構造上的（投影念
的就是引擎看到的那一段）。**結構是靜態的**——它在檔案裡，不在游標下——所以 A 的
「會漂」這個缺點在結構上小得多：使用者編輯會改文字，但很少改整份文件的骨架，而且
骨架改變時我們**知道**（那是我們自己送出的動作）。

⇒ **建議：結構走 A，文字維持 B。**兩者在同一個投影裡會合：骨架來自 ODT，游標所在
那一段的文字來自引擎，指紋是把兩邊對起來的鍵——而那個對法**已經在閘門 0 驗過一次**。

這一項要不要這樣定，值得外部裁決，因為它推翻了「路線 A 有第二份會漂的模型」這個
先前用來否決 A 的理由的一半。
