# 提案：M1 的合約修訂——四件事卡在同一個地方

> **日期**：2026-08-21
> **文件性質**：**提案與成本，不是授權。**沒有動任何出貨中的合約。
> **要決定的**：roadmap §10 第一項——M1 的 ABI 變更做不做。
> **依據**：[ROADMAP §2／§10](./ROADMAP-2026-08-20-milestones.md)、
> [PLAN-2026-08-21](../handoff/PLAN-2026-08-21-close-m1-without-a-link.md)、
> fable 2026-08-21 的裁決、以及 2026-08-21 對剪下的實測。
> **證據標記**：**已觀察**／**推論**／**待驗證**。

---

## 0. 一句話

M1 的驗收清單上剩下的每一格，都卡在**同一件事**：合約要新的動作，而合約是編進
artifact 的。**要不要開這一次連結，是這份提案唯一在問的問題。**

---

## 1. 卡住的四件事，以及它們**不是同一種東西**

這一節是 fable 2026-08-21 裁決的核心，也是我原本的理解錯的地方。

| | 現況 | 它到底是什麼 |
|---|---|---|
| **`redo`** | `blocked` | **不是 wire id 的問題。**（已觀察，我自己回查確認）產品的復原走 `session.undo()` → `document-sdk.js:482` 的 `_request("undo")`，是一個**有自己 capability 的頂層 SDK 操作**（`sdk-worker.js:32`），跟那十五個動作的合約無關。redo 的位置是一個**兄弟操作**：仍然要連結（新的編譯匯出），但**零個 wire id** |
| **`move-by-line`**（↑↓／Home／End） | `blocked` | **唯一真正的 append。**四個游標動作，Writer 文字模型形狀，`extendSelection` 的樣板在 `editor_api.cpp:59-62` 已經有了。這是乾淨的 16–19 |
| **`select-all`** | 刻意未綁定 | **性質不同。**它**連 discovery map 裡都沒有**（`sdk-worker.js:102-122`，十九個動作，沒有 select-all）——**從來沒有透過任何 ABI 派送過**。而且語料裡有一個**量過的**全選卡死案例（SPEC E2-C，「不要用它」），就坐在 038 的斷層上。需要 discovery 等級的特性描述才談得上承諾 |
| **`cut` 真的能刪** | `partial` | **2026-08-21 新加進來的**，而且是量出來的——見 §2 |

**「四件事一起解決」是錯的框法。**它們共用的只有「都要一次連結」，處方各不相同。

---

## 2. 剪下為什麼在這裡（2026-08-21 的實測）

佇列項 `queue-cut-cannot-remove-text` 原本寫著 **「NOT a link either way——手勢是
manifest 的選擇」**，roadmap §2 也據此把「剪下真的能刪」列在**不需連結**那一欄。

**那是錯的，而且現在有量測。**（已觀察）

先寫 PREDICTION，再用**鏡像**的 manifest 把 `delete-backward` 的兩個 range bit 一起
授予（`dist/` 沒被寫、`probe.wasm` 與 `29ec627b` 逐位元相同）：

- `EDITOR_FORMAT_GESTURE_UNSUPPORTED` **消失了**——證實 caret-only 的宣告確實是舊拒絕
  的來源；
- 但**選取屏障**接手拒絕：`EDITOR_STATE_UNAVAILABLE：selection barrier requires a
  callback-confirmed collapsed caret`；
- session 進 `recoverable-error`，本來要回答「文字有沒有被移除」的那次存檔被
  `EDITOR_NOT_READY` 拒絕。

**所以引擎能不能刪掉一個範圍，仍然沒有量到**，而剩下的兩條處方——屏障要能確認
**範圍**，或加一個刪除選取的動作——**都是引擎工作**。

⇒ **M1 的「不需連結」清單比 roadmap 寫的短一項。**

## 3. 兩個選項，以及為什麼**兩個都不是正確答案**

### 選項 A：往現有合約後面加 id 16–21

**問題**：這棵樹自己記錄過這個失敗模式。「一條路徑、兩個身分」正是 E1-C 就地擴充 v1、
而凍結測試還在釘八個動作的那次（`build_e2_b_profile.py` 的檔頭）。
`tests/test_e2_b_profile.py:78` 現在就釘著 v1 動作在兩個 disposition 下都是 caret-only。

### 選項 B：凍結 v2，重新設計一份有版本的合約

**我原本傾向這個，而 fable 指出理由不成立。**（已觀察，roadmap §8 自己寫著）

我的理由是「M5 反正需要不同的動作集」。但 id 空間是**依操作名與 capability 劃分的**
（`sdk-worker.js:140-148`），而 roadmap §8 說每個 app **各自走一次** discovery → 窄合約
→ validation。所以 Calc 的合約會是**兄弟**，不是後繼者——往 Writer 合約後面加東西，
**不會焊死任何人的未來**。

而且 B 等於在**還沒有 discovery 資料**的情況下先寫合約，這件事這個專案從來沒做過，
方法論上也不允許。

### ⇒ 正確的是第三種：**這棵樹自己在 v1→v2 發明過的做法**

**鑄一個後繼身分，繼承既有 id，往後append，用完全相符的 ABI 握手把關。**

- `abiVersion` 3 → 4，由**後繼 builder** 產出（E2-B 5.8：「一個能產出兩種版本的
  builder，它的產物沒有人叫得出名字」）；凍結的 v2／v3 位元組**一個都不動**。
- id 1–15 **逐字繼承**，新的從 16 開始。
- 由 `sdk-worker.js:925-930` 的完全相符握手把關：對不上的 profile 在 init 就
  `INCOMPATIBLE_ABI`，這正是「append 在一個後繼身分底下」安全、而「就地 append」
  不安全的差別。

> discovery map 的編號衝突（它的 `move-line-up` = 3 = 產品的 `delete-backward`；
> `redo` = 12 = 產品的 `set-list-unordered`）**是文件危害，不是機械危害**：
> `editor_api.cpp:71-106` 的 `internalAction()` 明確做外部→內部轉譯，而佇列項當初
> 選 16 而不選 12 就是為了這個。（已觀察）

## 4. 建議的連結貨載

一次連結，一個後繼身分，付掉好幾筆債：

| | 內容 | 代價 |
|---|---|---|
| **move-line ×4** | id 16–19，引擎對應，manifest 條目 | 乾淨的 append |
| **redo** | **一個 SDK 操作**，不是 wire id | 新的編譯匯出 |
| **select-all** | **引擎那一半出貨，manifest 裡先扣住** | 見下 |
| **delete-selection**（或屏障改成能確認範圍） | 由 §2 決定 | 見下 |
| **搭便車**：`queue-engine-must-report-core-lacks-accessibility` | 佇列項自己寫「ride along with the next one」 | 一行 |
| **搭便車（可選）**：32,767 的拒絕 | 等 T5 的源碼歸因 | 待定 |

**「先扣住」是這個交集設計本來就是為了這件事做的**（`sdk-worker.js:79-86`、
`probe_engine.cpp:5736-5748`）：manifest 可以**扣住**這個 binary 實作了的類別，
**永遠不能**授予它沒實作的。所以 select-all 與 delete-selection 的引擎那一半可以先
出貨、在 manifest 裡關著，**之後放行不需要再連結一次**——只需要一次量測。

## 5. 時機：**不要為這幾個 id 單獨開一次連結**

三個理由，都在樹裡：

1. **Firefox 那一臂今天才剛從紅變綠**（2026-08-21）。08-19 那兩次連結之所以扛得住，
   是因為意外落地時網子是綠的。**網子綠的時間還很短。**
2. 下一次連結的貨載清單**已經存在**（a11y 誠實化明寫「ride along with the next one」；
   32,767 的拒絕等 T5）。
3. 這棵樹自己的判例是 2026-08-16 的 `linkDecision: WAIT`——**攢到貨載夠了再一次出**。

**（推論，fable 提出）**若 a11y 閘門 0 過了，它本來就要重編一次核心、鑄一次新
artifact，**這六個 id 是那次連結的天然貨載**。但閘門 0 自己的探針 build 要保持乾淨、
只問一個問題，**不要把合約貨載混進閘門探針**。

## 6. M1 可以帶著 `blocked` 收嗎？

**照現在寫的判準：不行。**（已觀察）roadmap §2 的 M1 完成判準是
「清單全綠 ＋ 每個 done 的檢查綠 ＋ **沒有 blocked** ＋ D0 跑完、矩陣凍結」。

但**同一份文件**（i）自稱「排序與理由，不是規格……不構成執行授權」，（ii）把這件事
標成 M1 **唯一的岔路**，其中一條合法分支就是「就這樣收」，（iii）在 §10 把它列成
待決定。**所以那條判準本來就懸在這個決定上。**

兩種誠實的收法：

1. **做這次連結**，當 M1 的第三次；或
2. **明確修訂判準**——在 roadmap 的修訂紀錄裡把這幾列移出 M1，**並指名去處**。

**這個專案自己的紀律禁止的是第三種**：判準原封不動、然後宣稱綠了
（`Do not widen a check to close a row`）。

> **（fable 的建議，推論）**若走修訂，`move-by-line` 應該併進 **a11y** 那個
> milestone，不是模糊的「以後」：買家是機構、a11y 的理由是採購門檻，而**不用滑鼠、
> 用鍵盤逐行移動游標**正是無障礙稽核會測的東西。在 a11y 那一格失敗，等於那個
> milestone 的目的失敗。

## 7. 什麼會推翻這份提案

- **計畫裡任何地方出現「跨 app 共用的動作命名空間」。** 那樣 append 就會吃掉共用空間，
  重新設計的論點就活過來。今天 roadmap §8 說的正好相反。
- **a11y 閘門 0 沒過。** 承載這次連結的那班車就沒了，時機要重排（但 append-vs-重設計
  的結論不變）。
- **使用者判斷 redo ＋ 上下鍵不值得一次連結。** 那麼近期唯一剩下的貨載就是四個 id
  加一個沒特性描述過的 select-all，連結延到 M2a 之後，**明確修訂判準**就變成唯一
  誠實的 M1 收法。
