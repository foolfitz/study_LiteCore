# 123 — 畫布最後一條太短時被當成「引擎沒畫」，頁面每一輪重畫都跳「重繪失敗」

| | |
|---|---|
| **狀態** | 已確認、未修 |
| **所在** | 我們的頁面 `wasm_sdk_probe/web/e2-editor-app.js`：`renderBands`（:820）切出的最後一條可以很短；`tileWasPainted`（:1011）要求取樣點至少一半不透明；不過就由 `renderDocument`（:919–923）丟 `TILE_NOT_PAINTED`、:983 跳 toast |
| **發現日** | 2026-10-10（解釋 R2 診斷裡 Chrome 2 倍三份報告「最後一鍵後整張換新」是空值時；fable 第五次裁決要求先解釋） |
| **嚴重度** | 中：不丟資料、文件沒被改動，但使用者每開檔、每打字一輪就看到「重繪失敗」；文件末端在視野內時，那一輪其他的條也不更新 |
| **可重現** | 每次（Chrome、devicePixelRatio 2、預設視窗、擁有者文件：畫布 1450 × 35,858，最後一條 53 列）；在其他組合上依畫布高度而定（推導：1 倍 900 寬約 3.4%、1800 寬約 7%） |
| **是否上游** | 否 |

## 現象

開檔之後與每次打字之後，toast：「重繪失敗：TILE_NOT_PAINTED：引擎回了一張沒有畫進去的圖」。畫布最底下那一條從來沒被畫過（底部是最後一頁下方的空白，畫面上看不出缺了什麼）。

## 分析

- **已觀察**（`evidence/123/`）：Chrome 2 倍時畫布 35,858 列，切成 35 條 1023 列加最後一條 53 列；三份報告裡 y = 35,805 那一條從來沒有被貼上過；同一組態記 toast，開檔後與打字後各一次「重繪失敗：TILE_NOT_PAINTED」。
- **已觀察**：1 倍、725 寬時，畫布最後 14 列完全透明（最後一頁下方的間隙），其上每列 96% 不透明。間隙的 twips 固定，列數跟著畫布寬度走，1450 寬時約 28 列；53 列的最後一條因此只有約 45% 不透明。
- **讀原始碼**：`tileWasPainted` 是 finding 062 的守衛，「引擎沒畫」的那張是全零（alpha 也是 0），而它的判準是「至少一半取樣不透明」。最後一條若大半落在最後一頁下方的透明間隙，就被誤判。
- **推導**：餘數（畫布高度除以 1023）小於約兩倍間隙列數時就中。比間隙還短的最後一條是整條透明，任何只看像素的判準都分不出來。v58 一張畫到 32,767 列，只有超過 32,767 列而且餘數很小時才會有短的最後一塊；v59 的 1023 列分條讓這件事變常見。

## 處置方向

不讓最後一條變短：`renderBands` 在餘數小於半條時把它併進前一條（最後一條介於半條與一條半之間，仍遠低於 `MAX_TILE_HEIGHT`），062 的守衛原樣保留。只動頁面。單元測試：任何畫布高度都不切出短於半條的最後一條（除非整張畫布本來就不到半條）；瀏覽器紅案：上面那個組態不再跳 toast、「最後一鍵後整張換新」有數字。放進哪一次頁面發佈交擁有者（fable 第五次裁決的 A 是下一次頁面發佈）。
