Description
-----------

In a Qt 6.10.2 WASM/JSPI build, the LibreOffice Start Center opens, but
opening Writer aborts the whole application:

    Qt for WebAssembly: soffice
    Application exit (Assertion failed: invalid handle: 32)

With a diagnostic distinction added to the generated soffice.js, the
assertion is specifically an invalid emval handle. The symbolised stack
is:

    Emval.toValue()
    __emval_set_property()
    emscripten::val::set("value", ...)
    QWasmInputContext::updateInputElement()
    QWasmInputContext::update(...)
    QInputMethod::update(...)
    QWidget::setAttribute(Qt::WidgetAttribute, bool)
    QtFrame::SetInputContext(SalInputContext*)
    vcl::Window::ImplNewInputContext()

The object passed to __emval_set_property is an HTMLInputElement handle
created in the main browser JavaScript context. Qt's input-context update
later uses the same numeric handle from an Emscripten pthread whose emval
table does not contain that handle.


Steps to Reproduce
------------------

1. Build Qt 6.10.2 for WebAssembly with threads, WASM exceptions and
   WASM JSPI enabled.
2. Build LibreOffice from libreoffice-26-8 commit
   671c848b1bb81e5b1a90d97675db9a0f3ae2a9cb with at least:

       --enable-qt6
       --disable-qt5
       --enable-emscripten-jspi
       --disable-emscripten-proxy-to-pthread
       --with-wasm-module=writer
       --enable-symbols=Executable_soffice_bin

   The independent Qt 6.10 compatibility prerequisites used by this
   build are disclosed below.
3. Serve instdir/program/qt_soffice.html over HTTP with the COOP/COEP
   headers required for SharedArrayBuffer/pthreads.
4. Wait for the LibreOffice Start Center to appear.
5. Select Writer.


Actual Results
--------------

The application exits with "Assertion failed: invalid handle: 32" while
QWasmInputContext::updateInputElement() tries to update the hidden HTML
input element.

Observed 5 out of 5 times before applying the proposed change.


Expected Results
----------------

Writer opens and accepts text input without aborting the WebAssembly
application.


Cross-Thread Isolation
----------------------

Temporary instrumentation of the generated soffice.js recorded the
lifecycle of handle 32.

Producer:

    JavaScript context: main browser context
    workerId:           0
    pthread:            false
    C++ thread:         0x0372a98c
    value:              HTMLInputElement
    saved refcount:     1

Consumer:

    JavaScript context: em-pthread-7
    C++ thread:         0x038c0128
    call:               QWasmInputContext::updateInputElement()
    handle allocated:   false
    handle value:       undefined
    refcount after use: NaN

The property-name and property-value handles used by the same
__emval_set_property call were valid in em-pthread-7. Only the DOM object
handle was missing. This rules out the earlier hypothesis that the
std::string conversion was producing the invalid handle.

An Emscripten upstream issue explains that emscripten::val objects
representing JavaScript values are sensitive to being used and destroyed
on the same thread/context where they were created:

    https://github.com/emscripten-core/emscripten/issues/20610


Proposed Fix
------------

QtFrame::SetInputContext() currently enters Qt directly:

    m_pQWidget->setAttribute(Qt::WA_InputMethodEnabled);

Run that synchronous Qt/input-method update through LibreOffice's
existing Emscripten main-runtime-thread helper instead:

    GetQtInstance().EmscriptenLightweightRunInMainThread(
        [this] { m_pQWidget->setAttribute(Qt::WA_InputMethodEnabled); });

Full diff:

    diff --git a/vcl/qt5/QtFrame.cxx b/vcl/qt5/QtFrame.cxx
    --- a/vcl/qt5/QtFrame.cxx
    +++ b/vcl/qt5/QtFrame.cxx
    @@
    -    m_pQWidget->setAttribute(Qt::WA_InputMethodEnabled);
    +    GetQtInstance().EmscriptenLightweightRunInMainThread(
    +        [this] { m_pQWidget->setAttribute(Qt::WA_InputMethodEnabled); });

Despite the vcl/qt5 path, this source is shared with the Qt6 VCL plugin.

EmscriptenLightweightRunInMainThread() performs the special synchronous
proxy only for this configuration:

    __EMSCRIPTEN__ && ENABLE_QT6 && HAVE_EMSCRIPTEN_JSPI
        && !HAVE_EMSCRIPTEN_PROXY_TO_PTHREAD

It releases SolarMutex around the proxy and acquires it on the main
runtime thread. In other configurations it calls the function directly.

There is an existing LibreOffice precedent using the same helper to fix
another QtFrame WASM "invalid handle" failure:

    https://github.com/LibreOffice/core/commit/46cadd6b0329

Independent Local Modifications / Reproduction Boundary
---------------------------------------------------------

This is not yet a stock build. The tested worktree also contained these
independent prerequisites or product-specific changes:

  * removal of stale qstdweb::EventListener exports which no longer
    exist in Qt 6.10.2;
  * an Emscripten gbuild fix making a partial-symbol soffice target run
    emdwp and complete installation;
  * a filesystem-image change for zh-TW data and a CJK font;
  * a Qt 6.10.2 guard for a delayed pointer-enter event whose DOM node
    had become null;
  * a backport of Qt's suspend/resume pending-event reentrancy fix.

Those changes address separate build/runtime blockers and are not part
of the proposed SetInputContext patch. However, their presence must be
disclosed, and a clean current-master validation is required before this
draft is submitted.

The local origin/master snapshot inspected while preparing this draft
was d9d87d79ced23f8a770eaf94de7e59d59d8eb49e. It still contained the
direct QWidget::setAttribute call, but it has not yet been used for a
runtime reproduction and must be refreshed before submission.


Separate Issue Explicitly Excluded
----------------------------------

The first successful Writer session also showed one English key press
inserting two characters. That behaviour is tracked separately because
there is not yet an input-event trace or an identified owner. It must
not be combined with this startup crash report.
