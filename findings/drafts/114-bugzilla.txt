Summary: Packaged fontconfig 35-lang-normalize.conf rewrites the string FC_LANG "zh-tw" to "tw" (Twi), so a substituted CJK font is replaced by a Latin one (seen in WASM builds)

Description:

LibreOffice packages its own fontconfig configuration for some platforms (external/fontconfig/ExternalPackage_fontconfig_data.mk; per commit 703466d7 it is used for WASM and CODA-W). That configuration enables conf.d/35-lang-normalize.conf. Upstream fontconfig does not enable this file by default (in 2.18.2 it is generated into conf.avail and is not in conf.d/meson.build's conf_links), and Ubuntu, which 703466d7 says it follows, ships it only in conf.avail. The list in ExternalPackage_fontconfig_data.mk is generated with find over the template directory, which is how 35 came to be enabled (it is in the list since b7313bc1, 2021).

35 consists of rules of the form <test name="lang" compare="contains"><string>tw</string></test> followed by an assignment of "tw". LibreOffice adds the language to its font patterns as a string, FcPatternAddString(pPattern, FC_LANG, ...): in PrintFontManager::Substitute and, separately, in PrintFontManager::matchFont (on master 216d3914: vcl/unx/generic/font/fontconfig.cxx:1125 and :1406). fontconfig accepts a string for the lang property, but when both sides are strings it evaluates "contains" as a case-insensitive substring test (src/fccfg.c, FcConfigCompareValue, FcStrStrIgnoreCase). So "zh-tw" contains "tw" and the language becomes "tw", a Latin-script language.

The visible effect needs three things together: 35 is active, the language LibreOffice sends is one 35 rewrites, and the requested family is not installed under that name, so that fontconfig's choice decides the font. Then the primary font chosen for a Traditional Chinese paragraph is a Latin face. The CJK glyphs are still drawn by glyph fallback, so nothing looks missing; what changes is the line height (the Latin font's) and therefore the pagination.

Steps to reproduce (native LibreOffice on Linux, no WASM build needed):
1. Make two fontconfig configurations that each include, by ABSOLUTE path, the conf.d directory LibreOffice packages (for example instdir/share/fontconfig/conf.d of a WASM build): one as packaged, one with 35-lang-normalize.conf removed. Give both a <dir> containing Liberation Sans and Noto Sans CJK TC. Note: a relative <include>conf.d</include> resolves against fontconfig's default configuration directory, not the including file's, so it would silently load /etc/fonts/conf.d instead.
2. Open the attached fixture.fodt with FONTCONFIG_FILE pointing at each configuration in turn. Each paragraph style is used twice and tagged Asian language zh-TW: (a) Asian font 思源黑體 (not installed) 12 pt, (b) Noto Sans CJK TC 12 pt, (c) 思源黑體 18 pt, (d) Latin-only control 12 pt.
3. Read the caret height (or the distance between the two copies) of each paragraph. FC_DEBUG=1024 prints which rule files were loaded.

Actual, with 35: (a) 276 twips, (b) 348, (c) 414, (d) 276.
Expected, and observed with 35 removed: (a) 348, (b) 348, (c) 521, (d) 276. Only the paragraphs whose CJK font needed substitution change; the installed-font and Latin controls do not move.

A smaller check without LibreOffice: the attached fc_string_lang.py builds a pattern the way Substitute does (family 思源黑體, lang added with FcPatternAddString) and prints the lang after FcConfigSubstitute and the match: with the packaged rules the lang is "tw" and the match is a Liberation face (Liberation Mono for this bare pattern, which carries no weight or generic family); with 35 removed it stays "zh-tw" and matches Noto Sans CJK.

Scope of the rewrite: of the 282 language tags FcGetLangs() returns (the values mapToFontConfigLangTag can produce), 66 are changed by 35 when passed as a string, among them zh-tw to tw, zh-sg to sg, zh-mo to mo, nan to an and hak to ak. With 35 removed, none are. These are altered language values, not measured layout failures; the layout effect was measured for zh-TW only.

Where we saw it: in our WASM build of libreoffice-26-8, a Taiwanese document whose CJK font names need substitution was laid out about one fifth shorter than in desktop LibreOffice; removing 35 from the packaged conf.d made the eleven caret positions and heights we measured on it equal desktop LibreOffice's. Reading master's source suggests the default Qt-based WASM build takes the same path (Cairo text rendering through the generic fontconfig substitution, with fontconfig_data in the filesystem image); we have not tested a published WASM build or CODA-W. Ordinary Windows and macOS desktop builds do not use this code (configure.ac disables freetype/fontconfig there unless building headless), and Linux desktop builds use the system's fontconfig configuration, where 35 is normally not enabled.

Suggested fix: drop conf.d/35-lang-normalize.conf from ExternalPackage_fontconfig_data.mk. For LibreOffice's own requests it can only change a tag, since mapToFontConfigLangTag already returns members of FcGetLangs(). Optionally, LibreOffice could also add the language as an FcLangSet (FcPatternAddLangSet), for which "contains" means language containment; that would make it robust where 35 is enabled system-wide.

Version: master (216d3914) and libreoffice-26-8. Platform: WASM (Emscripten) observed; other self-packaged-fontconfig builds possibly affected, not tested.
