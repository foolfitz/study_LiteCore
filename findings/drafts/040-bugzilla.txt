Description
-----------

On an Emscripten build, `Scheduler::IdlesLockGuard` constructed on any thread
other than the main thread never returns from its constructor.

The guard waits for a condition that this platform's main loop never sets.  It
is not a race and not a timing window: the code that would set it is
unreachable on Emscripten by construction.

    vcl/source/app/scheduler.cxx:280
      Scheduler::IdlesLockGuard::IdlesLockGuard()
      {
          ...
          if (!Application::IsMainThread())
          {
              // Make sure that main thread has reached the main message loop [...]
              // Only main thread returning to Application::Execute guarantees that
              // the flag really took effect.
              pSVData->m_inExecuteCondtion.reset();
              Application::PostUserEvent({});
              SolarMutexReleaser releaser;
              pSVData->m_inExecuteCondtion.wait();      // <-- never returns
          }
      }

`m_inExecuteCondtion` appears in exactly four places in the tree:

    vcl/inc/svdata.hxx:414          declaration
    vcl/source/app/svapp.cxx:366    the ONLY set()
    vcl/source/app/scheduler.cxx:292  reset(), in the guard
    vcl/source/app/scheduler.cxx:297  wait(), in the guard

and the only set() sits inside a branch Emscripten cannot enter:

    vcl/source/app/svapp.cxx:355
      if (!pSVData->mpDefInst->DoExecute(nExitCode))
      {
          if (Application::IsUseSystemEventLoop()) { ...; std::abort(); }
          while (!pSVData->maAppData.mbAppQuit)
          {
              Application::Yield();
              SolarMutexReleaser releaser;
              pSVData->m_inExecuteCondtion.set();       // <-- the only set()
          }
      }

    vcl/headless/svpinst.cxx:308  (#if defined __EMSCRIPTEN__)
      bool SvpSalInstance::DoExecute(int &) {
          assert(Application::IsUseSystemEventLoop());
          ReleaseYieldMutex(false);
          emscripten_set_main_loop_arg(loop, this, 100, 1);
          O3TL_UNREACHABLE;                             // <-- never returns
      }

`emscripten_set_main_loop_arg` unwinds the stack by throwing a JS exception, so
`DoExecute` never returns, the `if (!...)` body is never entered, and the
condition is never set.  `Application::PostUserEvent({})` does not help: it
makes the main loop run an iteration, but the code that sets the condition is
not in the main loop -- it is in the `while` that cannot be reached.

`m_bUseSystemLoop` is set unconditionally for this platform
(vcl/headless/svpinst.cxx:103, under `#if defined __EMSCRIPTEN__`), so this is
not a configuration that can be avoided.


How we hit it -- three measured entry points, and two of them look read-only
----------------------------------------------------------------------------

All three are the same thing underneath: destroying an SwDoc that contains a
frame, from a thread that is not the VCL main thread.

**(1) The selection readers.** These are the ones that should worry a client
most, because nothing about them suggests they destroy a document.  Three
functions in desktop/source/lib/init.cxx take pDoc->getSelection() into local
UNO references:

    doc_getTextSelection            getSelection() at init.cxx:5926   HANGS (measured)
    doc_getSelectionType            getSelection() at init.cxx:5966   not measured
    doc_getSelectionTypeAndText     getSelection() at init.cxx:6004   HANGS (measured)

For Writer that reference is an SwTransferable holding its own clipboard SwDoc
(m_pClpDocFac).  Each function actually holds two locals -- the XTransferable
and the XTransferable2 queried from it.  When they release at return,
~SwTransferable resets the factory (sw/source/uibase/dochdl/swdtflvr.cxx:295)
and the clipboard SwDoc is destroyed, through the same DelLayoutFormat path.

    doc_getSelectionTypeAndText(doc, "text/plain;charset=utf-8", &text, nullptr)
      -> cppu::OWeakObject::release -> SwTransferable::~SwTransferable
      -> rtl::Reference<SwDoc>::~Reference -> SwDoc::release -> ~SwDoc
      -> SwNodes::DelNodes -> RemoveNode -> DeleteAttribute -> EraseText
      -> SwTextNode::DestroyAttr
      -> sw::DocumentLayoutManager::DelLayoutFormat(SwFrameFormat*)
      -> Scheduler::IdlesLockGuard::IdlesLockGuard()
      -> osl_waitCondition -> ... -> emscripten_futex_wait

doc_getTextSelection produces a stack that is frame-for-frame identical to this
one from Scheduler::IdlesLockGuard downwards, and identical above it as far as
the LOK entry point; the two differ only in which of the two functions appears
there.  Both were captured on the same build, so this is a direct comparison
rather than an alignment of two descriptions.

The extraction itself succeeds.  doc_getSelectionTypeAndText writes its
out-parameter (init.cxx:6028) before returning, so the text has already been
placed in the caller's memory -- but the call never returns, so the caller is
still blocked inside it and never learns that.  The hang is in the cleanup on
the way out, not in reading.

We did not measure doc_getSelectionType, only its two siblings; our client
calls the combined function.  It holds the same locals in the same shape.

Worth noting for anyone looking for a client-side mitigation: asking for the
selection *type* first, and refusing to read the text when it is not plain
text, does not avoid this.  That check goes through the very same function.
We tried exactly that as a workaround for entry point (1a); it works for a
paragraph holding an as-char frame, and it does not work when the frame is
inside a footnote whose citation mark the selection covers, because then the
type query itself is the call that hangs.

**(2) doc_destroy.** Closing a Writer document that contains a frame, from a
LibreOfficeKit thread:

    doc_destroy()
      -> SwXTextDocument::close -> SfxBaseModel::dispose -> ~SwDocShell
      -> SwDoc::release -> ~SwDoc
      -> SwNodes::DelNodes -> SwNodes::RemoveNode
      -> SwTextNode::DeleteAttribute -> EraseText -> DestroyAttr
      -> sw::DocumentLayoutManager::DelLayoutFormat(SwFrameFormat*)
           (sw/source/core/doc/DocumentLayoutManager.cxx:197 -- Scheduler::IdlesLockGuard g;)
      -> Scheduler::IdlesLockGuard::IdlesLockGuard()
      -> osl_waitCondition
      -> std::condition_variable::wait -> __libcpp_condvar_wait
      -> pthread_cond_wait -> __pthread_cond_timedwait -> __timedwait_cp
      -> emscripten_futex_wait

Neither call returns.  The document, the engine thread and every subsequent
call on that document are lost; the only recovery available to a client is to
terminate the worker.

All stacks are read from builds linked with `--profiling-funcs`, captured with
Chrome DevTools Protocol `Debugger.pause` against the parked worker -- V8's
inspector can interrupt `memory.atomic.wait32`, so a parked thread is still
introspectable.  The innermost frame is that instruction, verified independently
by reading the module bytes at the frame's offset (`fe 01`).  The doc_destroy
stack is 35 frames and was captured twice, identically; getTextSelection is 27
frames; getSelectionTypeAndText is 28 frames and was captured in three separate
runs, three pauses each, all nine identical.

The wait is indefinite by construction, not merely slow: IdlesLockGuard calls
the no-argument Condition::wait() (scheduler.cxx:297), whose default timeout is
null (include/osl/conditn.hxx:121), and the null branch is an unbounded
predicate wait (sal/osl/unx/conditn.cxx:125).  The `__timedwait_cp` frame in
the stacks is musl's internal implementation, not a deadline set by the caller.

DelLayoutFormat is not special -- it is simply the first place we happened to
reach the guard from a non-main thread.  Any other off-main-thread caller of
`Scheduler::IdlesLockGuard` on this platform has the same fate.

                -- added the Emscripten SvpSalInstance::DoExecute that installs
                   emscripten_set_main_loop_arg and never returns.

The guard predates the Emscripten headless main loop by five months, so this is
an interaction that appeared later, not an oversight at the time the guard was
written.


Reproduction
------------

Any Emscripten LibreOfficeKit build, off the main thread:

  1. lok_init, documentLoad an ODT containing a draw:frame with
     text:anchor-type="as-char" inside a paragraph.
  2. Call doc_destroy() from a thread that is not the VCL main thread.
  3. It does not return.  (We observe 180 s and give up; there is nothing to
     wait for.)

A frame at body level (directly under office:text) is NOT enough -- a document
with 100 such frames closes in 4 ms.  The frame has to be inside a paragraph,
so that ~SwDoc reaches it through SwTextNode::DestroyAttr.

Native builds of the same commit close the same document in single-digit
milliseconds; there `Application::Execute`'s while loop runs and sets the
condition.


Suggested directions (not a patch)
----------------------------------

Anything that makes the wait terminate on a build whose main thread never
returns to `Application::Execute` would do.  Three shapes, in the order we would
rank them:

  1. Set `m_inExecuteCondtion` from the system-event-loop path as well -- e.g.
     in `SvpSalInstance`'s `loop()` callback, which is exactly "the main thread
     has reached the main message loop" for this platform.  This preserves the
     guard's meaning rather than bypassing it.

  2. Have the guard skip the wait when `Application::IsUseSystemEventLoop()` is
     true and the main loop is known to be running.  Weaker: it drops the
     guarantee the guard exists to provide.

  3. Give the wait a timeout.  Weakest -- it converts a deadlock into a stall
     and a silent loss of the invariant.

We have not sent a patch because the right answer depends on what guarantee the
guard must keep for the Windows OLE scenario it was written for, and that is
better judged by its author.


What we are NOT claiming
------------------------

We are not claiming doc_getSelectionType hangs.  It holds the same locals in
the same shape as its two measured siblings, so we expect it to, but expecting
is not showing and nothing in this report depends on it.

We are not claiming the three entry points are the only ones.  DelLayoutFormat
is simply where we happened to reach the guard; the defect is in the guard's
wait, and any off-main-thread caller of it on this platform has the same fate.

We are also not claiming the guard is wrong to exist.  It was added for a real
Windows crash and the invariant it protects is presumably still needed; what is
broken is that on this platform the condition it waits for cannot be set.
