Summary:        LOK: setTextSelection(RESET)+setTextSelection(END) silently
                creates no selection after .uno:SelectText -- FN_SELECT_PARA
                calls SttSelect() with no matching EndSelect()
================================================================


Description
-----------

After dispatching .uno:SelectText, the documented LOK sequence setTextSelection(LOK_SETTEXTSELECTION_RESET, x1, y) followed by setTextSelection(LOK_SETTEXTSELECTION_END, x2, y) creates no selection at all, and reports no error. The call returns, the cursor moves, getTextSelection() returns an empty string, getSelectionType() returns LOK_SELTYPE_NONE, and -- importantly for callers that wait on it -- LOK_CALLBACK_TEXT_SELECTION is never broadcast, because the selection genuinely did not change.

This is not a misuse of the API. That exact two-call sequence is what LibreOffice's own tiled-rendering test asserts. In sw/qa/extras/tiledrendering/tiledrendering.cxx, inside testSetTextSelection, a comment at line 151 introduces the case as testing "that LOK_SETTEXTSELECTION_RESET + LOK_SETTEXTSELECTION_END can be used to create a selection", and the two calls that follow are checked with CPPUNIT_ASSERT_EQUAL against the expected text. That existing test only covers the clean case; dispatching .uno:SelectText first makes the same two calls fail.


Steps to reproduce, at the LOK API level
-----------------------------------------

1. documentLoad() a Writer document, initializeForRendering(), and paint a tile so that a layout exists and coordinates mean something.
2. setTextSelection(RESET, x, y) to place a collapsed cursor inside a paragraph.
3. postUnoCommand(".uno:SelectText", nullptr, true), which selects the paragraph.
4. setTextSelection(RESET, x, y) to collapse the selection again.
5. setTextSelection(RESET, x1, y) then setTextSelection(END, x2, y) to ask for a range.
6. getTextSelection("text/plain;charset=utf-8").

Expected: the text between x1 and x2. Actual: an empty string, getSelectionType() == LOK_SELTYPE_NONE, and no LOK_CALLBACK_TEXT_SELECTION for step 5.

Step 3 is the only thing that matters. Without it, step 5 works. No format command is involved: we first met this after .uno:DefaultBullet, but a run with the format command and without .uno:SelectText selects fine, and a run with .uno:SelectText and no format command fails.

Repeating step 5 a second time, with nothing dispatched in between, succeeds. See the mechanism section: the failed attempt clears the state itself.


Proposed regression test
------------------------

Modelled on the existing testSetTextSelection in the same file. The local alias
keeps every line inside the comment box; it is not otherwise meaningful.

  CPPUNIT_TEST_FIXTURE(SwTiledRenderingTest, testSetTextSelAfterSelectPara)
  {
    SwXTextDocument* doc = createDoc("dummy.fodt");
    SwWrtShell* pWrtShell = getSwDocShell()->GetWrtShell();
    pWrtShell->Right(SwCursorSkipMode::Chars, false, 5, false);
    pWrtShell->SelWrd();
    SwShellCursor* pCursor = pWrtShell->getShellCursor(false);
    const Point aStart = pCursor->GetSttPos();

    // Select the paragraph the way .uno:SelectText does, then collapse.
    comphelper::dispatchCommand(u".uno:SelectText"_ustr, {});
    Scheduler::ProcessEventsToIdle();
    doc->setTextSelection(LOK_SETTEXTSELECTION_RESET, aStart.getX(),
                          aStart.getY());

    // Exactly what testSetTextSelection already asserts works.
    doc->setTextSelection(LOK_SETTEXTSELECTION_RESET, aStart.getX(),
                          aStart.getY());
    doc->setTextSelection(LOK_SETTEXTSELECTION_END, aStart.getX() + 1000,
                          aStart.getY());
    CPPUNIT_ASSERT(!pCursor->GetText().isEmpty());  // fails before the fix
  }


Mechanism -- NOT VERIFIED, treat as a hypothesis
-------------------------------------------------

The report above stands without this section. Delete it and the reproducer is unchanged. We never read the flag named below: SwWrtShell::IsInSelect() lives in sw/source/uibase/inc/wrtsh.hxx:154 and is not reachable from an external LOK probe, so what follows is a source reading plus its externally observable consequences, not a measurement of the flag itself.

.uno:SelectText maps to FN_SELECT_PARA at sw/sdi/swriter.sdi:5649. FN_SELECT_PARA is handled at sw/source/uibase/shells/textsh1.cxx:1975 and ends in EndPara(true). EndPara(true) at sw/source/uibase/wrtsh/move.cxx:402 constructs a ShellMoveCursor with bSel true, whose constructor calls MoveCursor(true), and MoveCursor(true) at move.cxx:84 calls SttSelect(). SttSelect() at sw/source/uibase/wrtsh/select.cxx:421 sets m_bInSelect to true. Nothing on that path calls EndSelect(): ShellMoveCursor's destructor at move.cxx:62-71 only does StartAllAction and EndAllAction.

A later setTextSelection(RESET) does not clear the flag either. SwEditWin::SetCursorTwipPosition at sw/source/uibase/docvw/edtwin.cxx:7105 takes the bClearMark branch, which calls ClearMark() and leaves bCreateSelection false, so neither SttSelect() nor EndSelect() runs.

The caller's END then has HasMark() false, so bCreateSelection becomes true at edtwin.cxx:7107-7111 and SttSelect() is called. This time SttSelect() hits `if (m_bInSelect) return;` at select.cxx:409 and returns before SetMark(). With no mark there is no selection, and step 7's SetCursor() merely moves the cursor.

Why the second attempt succeeds: EndSelect() at edtwin.cxx:7121-7122 is called on bCreateSelection, not on whether SttSelect() did anything, so the failed attempt clears the flag on its way out.

For contrast, search in the same tree does pair them: sw/source/uibase/uiview/viewsrch.cxx:773 calls SttSelect() and :846 calls EndSelect().


What we ruled out, and how
--------------------------

That the format command breaks the selection: an arm that dispatches .uno:DefaultBullet and no .uno:SelectText selects fine, and an arm that dispatches .uno:SelectText and no format command fails.

That the document or the coordinates are broken: every arm dispatched .uno:SelectAll afterwards and got the whole document back.

That the readback or the wait between the two attempts is what heals it: an arm that repeats the two calls with no readback and no wait in between still succeeds on the second attempt.

That a plain SetCursor, or layout priming, is what heals it: an arm that first issues a markless RESET at the END coordinate -- the same SwCursorShell::SetCursor, without EndSelect -- still fails.

That it is Emscripten-specific: it reproduces on a native Linux build, four independent runs.

That it is browser-specific: Chrome and Firefox are cell-for-cell identical on the wasm build, across three fixtures.

That some other dispatched command does it: twenty uno commands were swept one at a time (Undo, Redo, ExecuteSearch, Bold, Italic, Underline, Strikeout, DefaultBullet, DefaultNumbering, RemoveBullets, StyleApply, Delete, SwBackspace, InsertPara, InsertLinebreak, InsertAnnotation, TrackChanges, AcceptTrackedChanges, Escape, SelectText). Only .uno:SelectText poisons the next range selection.


Suggested fixes, none of them verified by us
---------------------------------------------

The smallest one, and the one consistent with the convention already in the tree, is to give FN_SELECT_PARA a matching EndSelect() the way viewsrch.cxx does.

A wider one is to make SwWrtShell::SttSelect()'s early return not skip the mark, by moving `if (!HasMark()) SetMark();` above `if (m_bInSelect) return;`. That has a larger blast radius, but it fixes the more general shape: a caller believes it opened a selection when it did not.

Either way, the regression test above is worth adding, because the existing testSetTextSelection only covers the clean state.


Environment
-----------

core 671c848b1bb8, on the libreoffice-26-8 branch (describe: libreoffice-26-8-branch-point-229-g671c848b1bb8). Native reproduction: our own build, SAL_USE_VCLPLUGIN=svp, headless LOK probe. Wasm reproduction: an Emscripten build of the same tree, Chrome 150 and Firefox 153. Host OS Ubuntu 26.04 LTS.

The source tree carries five local modifications, disclosed in full:

  solenv/gbuild/platform/EMSCRIPTEN_INTEL_GCC.mk           (1 line)
  solenv/gbuild/platform/unxgcc.mk                         (1 line)
  static/CustomTarget_emscripten_fs_image.mk               (+26/-3)

None of them are under sw/. Four are Emscripten build plumbing. The unxgcc.mk change sits inside `$(if $(filter EMSCRIPTEN,$(OS)), ...)` and is therefore inert for the native build. We have not rebuilt a pristine tree to confirm this by reproduction rather than by inspection.
