## 量完了（2026-08-22 第二輪，七次跑）：**2 PASS / 7**，而計數器指出是哪一個 callback

證據：`findings/evidence/068/caret-after-commit/`（七份報告 ＋ README）。
臂 `caret-state-after-commit`，讀的是**狀態不是像素**。

| 次數 | commit 期間的 `sourceSequence` | 游標 x |
|---|---|---|
| 5（FAIL） | 3 → **5**（兩個 callback） | **不動** |
| 2（PASS） | 3 → **6**（三個 callback） | 更新 |

**七次裡每一次 `paint()` 都回報 `drew-caret`。**頁面沒有不畫。差的是別人給它的那個
矩形。

`sourceSequence` 數的是「每一個改變了狀態的 editor callback」。commit 那一段，游標
沒動時它加二，游標跟上時它加三。**第三個就是帶著新游標矩形的那個，而它七次裡缺席
五次。**

它缺席的時候，游標被畫在**打字之前**的矩形上——也就是落後了「剛剛打的那一整串」。
打一個字，游標就停在那個字前面。

**一次跑會說出一個有信心而且錯的結論。**這支臂第一次跑 FAIL、第二次跑 PASS，同一支
臂、同一個頁面、相反的結果。這個缺陷是**間歇的**，所以次數在這裡不是嚴謹度的裝飾，
**次數就是量測本身**。

兩個正向對照都是必要的，缺一這支臂就回 `NOT_ESTABLISHED` 而不是 FAIL：
（一）移動之後必須有 `paint()` 回報 `drew-caret`，否則這個儀器從來沒看過頁面畫游標；
（二）移動必須改變游標 x，否則它看不見「x 沒變」這件事，而「commit 之後沒變」就不
可否證。七次都成立。

## 現象

**量到的**：在一個空段落裡打一段字，什麼都不要再按——**畫布上那一行沒有游標**。
按一下方向鍵（或任何會動到游標的動作），它就出現了，而且出現在對的位置。

**operator 原話**（2026-08-21，2026-08-22 修過 066 之後再次確認）：

> 「游標應該在位於文字的後面，但它是位於**最後一個字元的前面**」

截圖：`findings/evidence/068/operator-screenshot-2026-08-22.png`。
**他描述的是位置錯，我量到的是沒有畫**——兩者對不起來，見〈還沒解釋的部分〉。

## 已經量到的：**模型是對的**（這一段仍然成立，標題的後半不成立）

> **2026-08-22 第二輪修訂：原標題是「模型是對的，壞的是畫」。前半仍然成立且重要，
> 後半作廢。**畫沒有壞——`paint()` 七次都畫了游標。壞的是**別人交給它的那個矩形**。
> 「壞的是畫」這個措辭把我鎖在畫布上數了五輪像素。

這兩件事是很不一樣的缺陷，而分開它們只要一次存檔。**如果游標的模型位置真的往左偏
一個字元，接下來打的字就會落在偏左的位置。**

臂（`caret-model-or-drawing`，`findings/evidence/068/model-position-is-correct.json`）：
空段落 → 打 `CARETONE` → 再打 `CARETTWO` → 存檔。

```xml
<text:p text:style-name="P3">CARETONECARETTWO1-LC-NUMBER-ONE</text:p>
```

**連續、順序正確**（`secondLandedInsideFirst: false`）。operator 自己那一輪的檔也
一致：`r2-caret.odt` 裡是乾淨的 `<text:p text:style-name="P1">CARETHERE</text:p>`。

所以：

- **編輯正確性沒有受影響。**打字落在該落的地方，存出來的文件是對的。
- 壞的是**畫布上那一根游標的 x**。

判準刻意用**文件**而不是畫布：這一條的主題是像素沒錯，但**像素分不出這兩種缺陷，
文件分得出來**。

## 為什麼前五次量不到

每一次的失敗原因都留著，因為它們是同一件事的不同面向：

| 方法 | 為什麼失敗 |
|---|---|
| `LINE_INK` 兩次相減 | 餵給 `caret_from_columns` 的讀取器少一個 `band` 欄位，於是滿是文字的帶被判成「沒有文字」 |
| `CARET_COLUMNS` 相減，左移 1 | 訊號太小 |
| 左移 5 拉開距離 | 被**頁框**淹掉——第 13、14、710、711 欄各是整條帶高的直線 |
| 等連續兩次讀數相同 | 頁框仍然不同：不是重繪中途的抖動 |
| 用顏色單次分離（`#1a1a1a`） | 只找到四個零星像素。**原因是算術**：游標寬度是 `Math.round(scaleX * 15)` ＝ **1 像素**，畫在小數 x 上，`fillRect` 會把它反鋸齒到兩欄，**沒有任何像素是正好 (26,26,26)** |
| 量 operator 的截圖 | 360 寬對畫布 725，縮了一半，一像素的游標和字母直筆分不開 |

**成功的做法是兩件事一起**：把重繪釘住（消掉「新的 paintTile 會整張重新反鋸齒」
——量到過 725 欄裡有 686 欄在變），然後**不要相減**，直接問「哪一欄有夠高的連續
暗列」。

## 還沒解釋的部分

> **2026-08-22 第二輪：這一節原本的核心疑問已經解掉了，而答案是 operator 對。**
> 原文寫「operator 說游標在最後一個字元的前面，我量到的是那一行上沒有游標，這兩件
> 事對不起來，而我不打算硬把它們湊在一起」。**不硬湊是對的做法，而它保住了正確的
> 那個描述**：游標停在打字之前的矩形，打了一個字之後看起來就是「在最後一個字元的
> 前面」。原文列的兩個可能，第二個（「他確實看到一根畫在舊位置的游標」）成立。
>
> **還沒對上的是另一件**：像素那一輪找不到**任何**游標高度的痕跡，而一根畫在舊位置
> 的游標應該在那一行上留下一根。這一條不強行湊，具名留著。

**operator 說游標在「最後一個字元的前面」，我量到的是「那一行上沒有游標」。**
這兩件事對不起來，而我不打算硬把它們湊在一起。

- 一個可能：他截圖時看到的是最後一個字母的直筆，而不是游標。他的截圖縮了一半，
  那一行有 11 個滿高欄位、全都落在字母筆畫上——**那張圖分辨不出來**，這一輪已經
  證明了。
- 另一個可能：他的操作序列和探針不同（例如中間有別的狀態更新讓 `paint()` 跑過），
  於是他確實看到一根畫在舊位置的游標。

**要分辨需要一張原始解析度的截圖**，那還是這張單原本就寫著的下一步——只是現在
問的問題換了：不是「游標偏多少」，而是「你看到的那一根，到底是游標還是字母」。

## 歸因

**上面那句推論後來被量到了，而且它是對的那一半。**原文寫：「最可能的方向是，一次
文字提交之後，帶著新游標矩形的狀態更新沒有到」，並自己標明「這是推論，不是量測」。
現在量了：**帶著新游標矩形的那個 callback 七次裡缺席五次。**

但同一段的另一半**是錯的**，而且是它把我引去數了五輪像素：原文說「繪製那一側有問
題，而繪製在產品頁裡」。繪製沒有問題。`paint()` 七次都畫了游標，用的是
`editorState.caret` 給它的矩形——那個矩形是舊的。

責任鏈現在指向另一邊：`gEditorState.caret` **只在
`LOK_CALLBACK_INVALIDATE_VISIBLE_CURSOR` 抵達時被寫入**
（`src/probe_engine.cpp:2226`），而 `handleInsertText` 呼叫完 `paste()` 就立刻回覆
（`:2809`），**不等任何 callback**。對照組就在同一個檔案裡：按鍵移動那條路會設
`gEditorPending.requiredCallback`，**等到 callback 才算完成**——所以移動之後游標一定
是新的，七次都是。

**還沒量到的是 LOK 那一側**：paste 到底有沒有送出那個 callback，還是送了而 payload
沒解析成功。引擎自己分得出來——游標區間的 callback 若解析失敗會送
`editor-callback-parse-error`（`:2316`）——只是**沒有人在提交期間去找過那個事件**。

（順帶：這一條在 finding 058 之前根本看不到，因為那時候頁面**完全不畫游標**。）

## 這張單和 066 的關係

operator 在 2026-08-21 首報時，同一輪還報了「按『換行』之後游標沒有移到下一行」。
**2026-08-22 那一項變成正常了**（`r2-linebreak.odt`：
`<text:p>CARETHERE<text:line-break/>AFTERBREAK</text:p>`，而且 operator 說畫面上
也對）。中間唯一的變化是 066 的修法。**沒有獨立量過**，最可能的解釋是當時焦點
停在按鈕上、後續動作沒有落在他以為的地方——但那是推測。

游標位置這一條**不受 066 影響，兩天都在**。
