## 修法方向

深度規則把扣在頁面上的也算進去（`deletesInFlight + heldDeletes.count >= HELD_DELETE_DEPTH`），放開後回到「最多再刪 2 字」。任務 10-14q。

## 教訓（登錄，不是規則）

141 的修法動了「同鍵第二下怎麼等」，而這件事在文字中間也成立；10-14o 的 K1／K2 只量了邊界與一個「文字中間連按（`repeat: false`）」的對照，沒有量「文字中間按住（`repeat: true`）」。抓到它的是開跑前補的 132-B 守衛。

## 裁決（2026-10-14，任務 10-14q；fable 代擁有者裁決，擁有者選 A）

**兩處，都在頁面 `web/e2-editor-app.js`。**

1. **深度把扣住的按壓算進去。**`skipHeldRepeat` 交給 `dropsHeldRepeat` 的數字由 `deletesInFlight` 改成 `deletesInFlight + heldDeletes.count`（參數改名 `deletesOutOrHeld`，`HELD_DELETE_DEPTH` 仍是 2）。於是按住時：第一下送出（在途 1）、第一個重複鍵被扣住（扣住 1）、第二個起在 keydown 就被丟掉（1 + 1 ≥ 2）；引擎回答一下就放出一下、再扣一下。放開時最多「一個未回答＋一個扣住」，也就是 132 的「放開之後最多再刪 2 字」。
2. **放出扣住的按壓改成直接呼叫，不再合成事件。**0.2.21 用 `el.sink.dispatchEvent(new InputEvent("beforeinput"))` 重送，每個 `beforeinput` 監聽器都看得到——凍結的 input adapter 會記一筆、132-B 的儀器把它算進 `beforeinputs`（102 對 52 個鍵），判準 (c) `beforeinputs == deleted` 光因為計數就紅。現在送出的那段抽成 `dispatchDelete(action)`：監聽器對沒被扣住的按壓呼叫它，`releaseHeldDelete` 對放出的按壓呼叫它；送出的形式（121 的形狀、131 的收合形）在送出當下決定。`DELETE_INPUT_TYPE_OF` 移除。

**為什麼不是別的形狀。**只改 (1) 會讓 132-B 的 (c) 仍紅（H1 要 `132-B PASS`、判讀器不改）；只改 (2) 不會停止扣住所有重複鍵。用 `deletesUnanswered + heldDeletes.count` 而不用 `deletesInFlight` 也能給 ≤ 2，但 132 原本數的就是「送出未結算」（含重畫），沿用它，重畫那一小段多丟幾個重複鍵、引擎照樣有東西在做。141 在邊界的行為不變：沒標記的連按仍只有 1 個請求（U1c、N1）；**具名殘留**：在邊界按住（有標記）仍是每個 2.25 秒的窗一個 no-op（跟 141 之前、10-14n 的 `hold-3s` 一樣），141 的「記住上一個 no-op」沒做，留給引擎端的直接回答（§10.5 `waitedMs`）。
