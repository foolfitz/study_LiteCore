## 現象

A 寫入檔案（204，拿到 ETag `E`）。同一秒內 B 寫入**不同的內容**（204）——B 拿到的 ETag
**還是 `E`**。A 之後帶 `If-Match: E` 再寫：**204**，B 的內容被蓋掉。兩次寫入跨過秒界時，
B 的寫入會換 ETag，A 的條件式寫入是 412（正確）。

## 重現步驟

1. 使用者 A 有一份檔案，並以可寫入（permissions 3）分享給 B。
2. A：`PUT` 內容 X，記下回應的 `ETag` = `E`。
3. 立刻（同一秒內）B：`PUT` 內容 Y（與 X 不同；長度相同或不同都一樣）。
4. A：`PUT` 內容 Z，帶 `If-Match: E`。
5. A：`GET`。

**預期**：第 3 步之後 ETag 不再是 `E`；第 4 步 412；第 5 步讀到 Y。
**實際**：第 3 步回的 ETag 仍是 `E`；第 4 步 204；第 5 步讀到 Z。

探針：`wasm_sdk_probe/tools/probe_m3_versions.py --only V7`（每輪 12 次，靠自然的時間分佈
得到同秒與跨秒兩種試次；每一次都從容器裡 `stat` 檔案，記下 inode／mtime／size）。

三輪裡檔案的 inode 從頭到尾沒變（就地寫入），變的只有 mtime（秒）與大小。

## 分析

- `lib/private/Files/Cache/Scanner.php:174-183`：更新檔案快取時，若檔案的 `storage_mtime`
  與快取裡的相同（`$mtimeUnchanged`），就沿用快取裡的 `etag`（`REUSE_ETAG`），不論大小
  是否改變。mtime 的解析度是秒，所以同一秒內的第二次寫入不會產生新的 ETag。這一段是
  讀原始碼；與「大小不同也一樣」的實測一致。
- 一開始讀的是 `Local::calculateEtag`（mtime、inode、device、size 的 md5），因此預測「同秒
  **且**同大小」才會撞。**大小那一半被實測否證**：快取層在更上面就沿用了舊值，
  `calculateEtag` 的結果根本沒被採用。
- 對 `IReliableEtagStorage` 的儲存不沿用（同一段條件）。本機儲存不是。其他後端沒查。
- 上鎖／解鎖不受影響：files_lock 用 `propagateEtag` 另外寫一個新 ETag（實測 LOCK 會換
  ETag 而 mtime 不變）。

## 對我們產品的影響

`litecore` 宿主的鎖與權限規格（`specs/SPEC-M3-locks-and-permissions.md`）和 finding 102 都寫著
「寫入一律帶 `If-Match`，所以宿主不掉資料」。**這句話在一秒的窗口內不成立**：

- 宿主持有 token 鎖時，照規矩來的 DAV 用戶端寫不進來（423），所以窗口只對**繞過鎖的寫入**
  開著：拿到持有者 token 的人（finding 102），以及不看 token 鎖的伺服器端寫入（files_lock 的
  儲存層包裝不檢查 token 鎖；「從版本還原」就是一例，但還原會把 mtime 設回被還原那一格的時間，
  實測 ETag 都換了、宿主拿到 412——`evidence/m3-versions` V3、V4；唯一的例外是推論：同一秒存兩次之後
  revision 等於目前 mtime 的那一格，還原它不改 mtime）。
- 宿主**沒有**持有鎖時——~~上鎖失敗、鎖被解掉、鎖過期~~ 上鎖失敗或鎖過期（2026-09-28 修訂，審核第 5 項：鎖被解掉時
  files_lock 另寫一個新的 `uniqid()` ETag（`LockService.php:219`），宿主的 `If-Match` 不論時間都會失敗，K6 量到的就是 412）
  ——任何人的寫入若與**宿主手上那個 ETag 所屬的寫入**落在同一秒，宿主下一次存檔都會把它蓋掉。
- 被蓋掉的內容在版本歷史裡找得到（上表）；但沒有任何一方會被告知，而且**之後若有人還原任何舊版本，它就永久遺失**
  （finding [104](104-nextcloud-restoring-a-version-after-two-writes-in-one-second-loses-the-second-write.md)：同一秒的兩次寫入之後還原，較晚那次哪裡都找不到）。

宿主這一側能縮小窗口（例如存檔前先比對內容）。~~沒辦法關掉它~~ 能不能關掉**沒有研究**（審核第 13 項：依原始碼，宿主的
PUT 帶一個過去秒數的 `X-OC-Mtime` 也許能讓每次寫入都換 ETag，但副作用很壞，也沒量）。真正的修法在上游。
更正（2026-09-29）：依下方裁決做了「存檔前比對內容」，宿主 0.2.2。宿主**自己寫出的**版本的窗口關上了；還開著的是推論的
殘留（見下方裁決段），以及別的用戶端之間彼此的覆寫——那不是宿主看得到的。

## 裁決（2026-09-29，fable 代擁有者，擁有者不在時授權）

裁決全文與條件：`evidence/m3-same-second/ruling-2026-09-29-fable-d.md`。裁決是 **D**：只改宿主，先量再修。
fable 寫給擁有者的理由（原文照錄）：

> 這一輪剩下的選項裡，只有 D 是「產品自己的路就走得到、而且會永久掉資料」的缺陷：使用者連按兩次存檔（或按住 Ctrl+S——頁面沒有過濾鍵盤重複，按住就是一連串存檔）→ 每次 PUT 只要 74 ms，兩次落在同一秒 → 之後任何人從 Files 還原任何舊版本，較晚那次存檔就從檔案和版本歷史裡一起消失（104，實測 5/5）。上游修不了（送出擱置中），頁面不能動（換身分就要重跑全部計數執行），宿主是唯一能動的地方，而宿主的四張回歸網都在。其他選項都該等你回來選：A 要你出面、C 作廢所有計數判定、H 會讓你另外兩個 ddev 專案短暫 404、G 是省流量不是修缺陷、F 沒有資料遺失也還沒有修法設計。D 做完的樣子是宿主 0.2.2＋一支先紅過的新臂＋四支既有 runner 在 0.2.2 上重新全綠；`INSTALLS ELSEWHERE` 仍然只是 0.2.1 的事實，0.2.2 要不要再跑安裝窗留給你。我要求先量「頁面真的能讓兩次存檔落在同一秒」再動手：現有每一筆計數執行的兩次存檔都隔了 ≥1.18 秒，那是 harness 的路，不是使用者的路，沒有人真的量過。

**做了什麼、結果**（這張對應裁決的**半 B**，條件 6：只在「GET＋sha256 對宿主自己最後的位元組、不動伺服器、多出來的延遲
不超過一次 PUT、有自己的紅案」都成立時做）：

- 修法（宿主 0.2.2，`litecore` `695d9ad`）：每一次 PUT 之前（在那一秒的等待之後）讀回原檔；版本等於宿主手上的 ETag、
  位元組卻不同＝有人在那一秒寫過，不送 PUT，另存衝突副本。讀回中斷不算答案，照舊交給 PUT。
- 紅案（`specs/SPEC-M3-versions.md` §4 R3）：宿主在相位 0.05 存一次，runner 立刻帶持有者的 token（102 的繞過）寫入 X，
  確認 X 之後的 ETag 仍是宿主那一次的（同一秒），再存第二次。0.2.1：四趟全是 204、X 被蓋掉、沒有副本——**這張 finding
  經過真的頁面重現了**。0.2.2：X 留著、第二次存檔進衝突副本、頁面說 `CONFLICT`，而且擋下它的是讀回比對（沒有送 PUT）。
- 入場條件量過：讀回的 GET 中位數 24 ms，PUT 46 ms（9.5 KB 的 fixture）。**大文件也量了**（2026-09-29，`evidence/m3-same-second/readback-size/README.md`，判準先 commit）：到 52.4 MB 為止兩個瀏覽器每一種大小都成立，讀回／PUT 在 0.32–0.61 之間，每一臂最慢的讀回都比最快的 PUT 快。讀回是完整下載，所以在真的網路上要多付約「大小／下行頻寬」；這次是本機，那一段沒量。
- 計數執行 **`SAME-SECOND SAVES KEPT`**：R3 Chrome 3/3、Firefox 3/3，紅案 70/70（與 R2 同一份報告）。
- **還開著的**（讀原始碼，未量）：宿主手上的版本是開檔時讀到的那一個、而第一次存檔的讀回落在開檔前最後一次寫入的同一秒；
  或者別人的寫入自己把 mtime 設成宿主那個版本的秒數（`X-OC-Mtime`）。

**上游的缺陷本身沒有變**：其他用戶端之間照樣會在同一秒互相覆寫。
