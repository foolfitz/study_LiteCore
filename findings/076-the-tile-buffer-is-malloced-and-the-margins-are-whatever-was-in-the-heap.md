## 一句話

`paintTile` 只畫頁面那塊，**其餘保留 `malloc` 拿到的內容**；客戶端用 `putImageData`
**連 alpha 一起原樣**寫上畫布——所以文件沒蓋到的地方，畫的是未初始化的堆積。

## 機制（三段，都在原始碼裡）

1. `src/probe_engine.cpp`：`std::malloc(byteCount)` 配置 tile 像素緩衝區，**不清零**。
2. `gState.document->pClass->paintTile(...)` 畫**頁面**；頁面以外不碰。
3. `web/e2-editor-app.js`：`context.putImageData(strip.image, 0, strip.y)`。
   `putImageData` 是**取代**語意且包含 alpha ⇒ 緩衝區內容逐位元上畫布。
   而 `layoutCanvas()` 只做等比縮放、不裁切 ⇒ **整張畫布都顯示出來**。

## 為什麼一直沒被看見：它取決於那塊記憶體是不是新的

剛長出來的 WASM heap 頁面是零。所以在出貨那顆 core 上，未繪製的緩衝區「幾乎」是零
——而這個專案**自己早就量過**，量的人是 `tileWasPainted()`，它的註解寫著：

> an unpainted buffer is not uniformly zero -- measured, 88 of 2,105,340 sampled
> points are not

**88 / 2,105,340 ≈ 0.0042%**，而且不透明的是 **0%** ⇒ 頁外讀起來就是透明，
墨跡判準（`alpha > 128`）永遠碰不到。

a11y core 上同一塊區域（26,941 個頁外像素，放游標後）：**290 個不透明**、alpha 有
**184** 種取值（出貨那顆是 33）⇒ **1.08%**，大約 **250 倍**。

**不是新現象，是量變。**合理的解釋是配置變多（accessibility 讓 probe.wasm 多 19.9 MB）
⇒ 這塊緩衝區落在**重用過的記憶體**而不是新頁面。**這是推論，沒有量**——沒有人量過
配置流失率與雜訊率的關係。

## 兩個後果，輕重不同

- **輕的那個**：31 個夠暗的像素落在行與行之間，把分帶弄壞了 ⇒ **finding 075**。
- **重的那個**：**一張使用者可以截圖的畫布上，顯示著本行程堆積的片段。**
  這裡的堆積裝的是使用者的文件。沒有量過那些位元組實際來自哪裡，但
  「未初始化記憶體被算繪出來」這件事本身就不需要再證明什麼才算問題。

## 處方：`calloc`，已寫進原始碼

```cpp
auto *pixels = static_cast<unsigned char *>(
    std::calloc(static_cast<std::size_t>(byteCount), 1));
```

用 `calloc` 而不是事後 `memset`：沒有空窗，也不會有第二個語句被忘記。新頁面上配置器
的清零是免費的；重用記憶體上是對 2.7 MB 走一趟，而同一塊緩衝區接下來要被**點陣化
整頁**。

**已進產品（2026-08-24，`e2-editor-v8`）。**與 `queue-fresh-is-true-where-no-read-can-succeed`
同一次連結出貨，手冊 `handoff/RUNBOOK-relink-v8.md`。

那次連結**會出什麼是量出來的不是讀出來的**（`tools/what_the_link_ships.py`，用產品自己的
define 把四個 translation unit 在出貨 commit 與工作樹各前處理一次再 diff）：
**三件，不是一件**——本修法、上面那個 early return、以及 worker 裡 21 行 a11y 欄位轉發。
**讀 `#ifdef` 只會找到第一件。**

## 這修法**不會**取代 harness 那一側的修法

075 的頁面裁切留著。理由：那個裁切擋的是「頁面外的墨跡」這一類，而不是這一個成因。
一個只在引擎修好的世界裡是對的儀器，會在下一個未預期的頁外算繪上再壞一次——而且
會安靜地壞（少兩段、沒有任何檢查紅）。**兩層都要。**

## 使用者確認：看得到（2026-08-23）

原本這一節列著「使用者看不看得到——**還沒有人看過**，這一題該問操作者，不是再寫一支
探針」。**已經問了，答案是看得到。**

使用者對著 v5 預覽（`e2-editor-v5`、wasm `e32d50d3…`、頁面帶綠色橫幅寫明版本）回報
**「有雜訊」**。

⇒ 這不再只是 harness 的故事，是**這顆 core 上使用者看得見的算繪缺陷**。而畫出來的
內容是本行程的堆積，堆積裡裝的是使用者的文件。

**歸因仍然不足**，這一點不因為看得到就改變：那顆 core 同時多了 calc。

## 沒有量的（因此不指認）

- **發生率。**機制是確定的，顯現是間歇的：這篇的兩張畫布拍到了，之後的十張都沒有。
- **是不是 accessibility 造成量變。**那顆 core 同時多了 calc。兩個差異，一次量測。
- **那些位元組是什麼。**沒有去追它們來自哪一次配置。

## 證據

## 連結之後量到的，以及它**不**能證明什麼（2026-08-24）

同一支儀器（`tools/capture_canvas_edges.py`）、同樣的頁外欄（`x < 14`、`x >= 710`）、
每張 26,941 個像素：

| 畫面 | alpha == 0 | alpha > 128 | 通過墨跡判準 | 相異 alpha |
|---|---|---|---|---|
| v4 靜止（存檔） | 21,563 | 0 | 0 | 47 |
| v4 放游標後（存檔） | 21,595 | 0 | 0 | 33 |
| **v8 靜止** | 21,595 | **0** | **0** | 33 |
| **v8 放游標後** | 21,595 | **0** | **0** | 33 |
| **v8 套粗體後** | 21,595 | **0** | **0** | 33 |

沒有回歸，而且**編輯過文件之後數字不再動**——a11y core 的「放游標後」那一列是
290 個不透明、其中 31 個過墨跡判準、184 種相異 alpha。

產品路徑第一次跑在連結出來的 artifact 上：**38 PASS / 2 NOT_ESTABLISHED、`ok: true`**，
與 v7 最好的一輪相同。

### 但這**不**證明使用者看到的那個消失了

**產品 core 在 `malloc` 時代就已經讀成透明的**（0% 不透明），所以 v8 畫布乾淨只證明
兩件事：機制在原始碼裡關掉了、而且沒有回歸。**它不證明操作者看到的雜訊沒了**
——那是在 **a11y core** 上量到的，而那條線還沒重連結，仍然帶著 `malloc`。

要宣稱那件事，需要 a11y 那條線自己的一次連結，**那是另一個決定**。
這個不對稱是在量測之前就寫進手冊的，免得事後被安靜地略過。

另外，那些「非零但透明」的值（26,941 裡 21,595 是零、33 種相異 alpha）與 v4 基線
**完全相同**，所以它們不是那個 `malloc` 緩衝區。它們是什麼，這裡沒有量，也不指認。
