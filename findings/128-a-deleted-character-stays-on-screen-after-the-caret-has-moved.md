# 128 — 刪掉一個字之後，游標已經移走，被刪的字還在畫面上停留約 0.12 秒（殘影）

| | |
|---|---|
| **狀態** | **已確認、未修** |
| **所在** | 我們的頁面 `wasm_sdk_probe/web/e2-editor-app.js`（`8909564e…`）：`renderDocument` 碰到 `BUSY` 就**固定等 120 ms** 再重試（:1238），等待期間 `rendering` 一直是 true；觸發點是 `onEvent` 收到 `document-invalidated` 就立刻開一輪重畫（:2589–2591），而引擎在刪除動作**還沒回來之前**就先送出這個事件，所以那一次的 paint 撞上刪除的驗證屏障（selection barrier），被回 `BUSY` |
| **發現日** | 2026-10-12（擁有者手測宿主 0.2.12） |
| **嚴重度** | 小：不丟資料，鍵停下來之後畫面完全正確（像素逐一相同）。但每刪一下，游標都會先移過去，被刪的字晚約 0.12 秒才消失；連續刪除時，Firefox 最長量到 0.28 秒 |
| **可重現** | 每次（Chrome 與 Firefox 157；單按 4/4、連按 4/4，兩個瀏覽器、兩種游標位置都有） |
| **是否上游** | 否 |

## 現象

擁有者原話：「delete / backspace 刪去文字的時候會有殘影」。

## 重現步驟

1. 在宿主 0.2.12 開任何文件，在一行字中間點一下。
2. 按 Backspace。

**預期**：字消失的同時，游標往左移一格。
**實際**：游標先往左移（按鍵後約 44 ms），被刪的字還留在游標右邊，約 120–140 ms 之後才消失。

## 成因（讀 Worker 訊息的時間序得到，不是推論；`evidence/128/README.md`）

每一次 Backspace（Chrome 的追蹤，4/4 一致）：

1. 0.6–0.9 ms：頁面送出 `editorActionV2`（`delete-backward`）。
2. 34.6–35.5 ms：引擎在動作還沒回來時，先送出 `document-invalidated`；頁面立刻送出第一條 band 的 `paint`。
3. 39.0–43.7 ms：那次 paint 被回 `BUSY`（`a verified selection delete is still in flight`，`selection-barrier`）。
4. 44.0–44.5 ms：游標的狀態更新到了，頁面把游標畫到左邊一格——蓋在還沒消失的字上。
5. 44.6–45.2 ms：刪除動作回來了；`run()` 要求重畫，但因為上一輪還標記著「進行中」，只能設 `renderAgain`。
6. 頁面在 `BUSY` 分支**固定等 120 ms**（實測下一次 paint 在 BUSY 之後 120.2–120.4 ms 才送出；期間 Worker 沒有任何訊息往來，主執行緒也沒有 long task）。
7. 159–164 ms 才送出下一輪 paint；四條 band 每條 6.5–12 ms 就回來了。

**所以約 125 ms 裡，大約 110 ms 是頁面在等一個早就結束了的屏障。**引擎畫圖本身不慢。

| | Chrome，游標在畫面第一條 band | Chrome，第二條 | Firefox，第一條 | Firefox，第二條 |
|---|---|---|---|---|
| 單按，游標移動之後舊字還在的時間 | 122–125 ms | 131–133 ms | 126–128 ms | 134–143 ms |
| 連按（間隔 50 ms），最長 | 125 ms | 139 ms | 129 ms | **283 ms** |
| 打八個字再刪八個字，前後畫面像素 | 0 個不同 | 0 | 0 | 0 |

探針寫在執行之前的假說 H2（band 的繪製順序：游標所在那條要等上面的先畫）預測「第二條遠大於第一條」；實測只多 8–15 ms，**不是主因**。連按時它可能有貢獻（Firefox 第二條 283 ms），這次沒有分離出來。

## 沒量到的（不下結論）

- 打字（insert-text 不經過刪除的驗證屏障）會不會撞到同一個 `BUSY`：沒量。
- Delete（往後刪）：同一條 session 路徑，預期相同，**沒跑**。
- 選取後刪除（`delete-selection`）：沒跑。

## 處置方向（未決，交規格）

- **A**：動作進行中收到 `document-invalidated` 時不開新的一輪（動作回來時 `run()` 本來就會重畫）；不是動作造成的失效照舊。
- **B**：`BUSY` 時結束這一輪、交給下一個觸發點（動作完成、下一個事件），120 ms 只當沒有其他觸發時的後備。
- **C**：縮短重試間隔。

不管選哪一個，都**不能弄壞 120 ms 這個重試原本要處理的情況**：B′ 併段時屏障可能讓引擎 `BUSY` 長達約 8 秒，重試預算是 `RENDER_BUSY_RETRIES = 84` 次（約 10 秒；`:1049`、`:1131` 附近的註解）。預期修好之後，舊字在刪除動作回來後約一條 band 的時間（約 10 ms）內消失。只動頁面、不需要連結。
