# 093 — 無障礙投影節點躺在紙張底部，因為它沒有拿到 069 的那個修法

**狀態**：機制已由原始碼確認，**行為量測未做**（phase 2 待跑）。
**發現者**：擁有者，2026-09-08 00:09–01:00 CST 的 T4 人工輪，用眼睛抓到。
**證據**：`findings/evidence/manual-round-v12e-9b29e39b/`（擁有者筆記、兩趟
Orca 語音記錄）。

## 現象（擁有者原話）

> 好像只要用鍵盤方向鍵就會捲到頁面底部，沒辦法使用。

追問「畫面捲到底時編輯器還看得到嗎」，答：**「捲過頭」**——編輯器還在畫面上，
是視窗捲得太遠。

**而同一段時間裡朗讀是對的。**第二趟 00:57:39–00:58:47，Orca 依序唸出
heading 1 →內文→ heading 2 →內文→ heading 2，順序與角色都正確
（`orca-speech-t4-4b-round2.txt`）。**朗讀游標在文件裡正常前進，視窗卻停在
頁面底部**——兩件事同時為真，那個落差就是這張單。

對只用耳朵的人這一頁也許還能用；對**同時用眼睛看又開著螢幕閱讀器的人**
（低視力使用者）它是不能用的：看不到它正在唸哪一行。

## 機制（原始碼確認，非推測）

`wasm_sdk_probe/web/e2-editor.html`：

- 第 65–70 行，`.a11y-only` 是 `position: absolute`，**沒有 `top`／`left`**。
- 第 236 行，`#a11y-doc`（承載整個結構投影的容器）用的就是 `.a11y-only`，
  而它在 DOM 裡排在 `#canvas`（第 228 行，`display:block`、整份文件的高度）
  之後，容器是 `.paper`（`position:relative`）。所以它的靜態位置**就在紙張
  的最底部**。JS 從來沒有替它定位過。
- 第 82–95 行——**距離上面那條規則只有四條規則**——有一段註解，逐字寫著這件事
  為什麼要命：

  > `top`/`left` are not decoration. Without them an absolutely positioned
  > element sits at its STATIC position -- which for this one is directly
  > after the canvas, and the canvas is the whole document's height. The
  > input sink was therefore lying at the bottom of the page, and every time
  > an IME began composing, the browser scrolled the focused element into
  > view and took the whole desk with it. Reported by an operator typing
  > Chinese with 新酷音, 2026-08-22.

  那就是 **finding 069**。
- 第 98 行，`#sink` 拿到了修法：`position: absolute; top: 0; left: 0`，
  並由 `paint()` 持續騎在游標上。

**`#a11y-doc` 從來沒有拿到同一個修法。**同一個檔案、相隔約一百四十行、成因
寫在註解裡。

## 為什麼現在才被看到

`e2-editor.html` 是**兩個 profile 共用的同一個檔案**——出貨的 `e2-editor-v8`
與候選的 `e2-editor-v12` 在 DOM 與 CSS 上逐位元相同（候選頁面與出貨頁面的差異
是 `e2-editor-app.js` 裡的**兩行、一個位元組**：wasm pin 與 worker URL）。

差別在**可達性**：v12 的 manifest 提供 `caretParagraphText` 與
`documentOutline`，所以 `#a11y-structure` 裡每一段都有一個節點；v8 兩者皆無，
`#a11y-structure` 是 `aria-hidden`、沒有子節點。**同一個缺陷在 v8 上大概只有
一個停靠點，在 v12 上是每一段都有一個**——於是走訪全程視窗都被釘在底部。

**這是預測，不是量測**（phase 2 的第一項就是量它）。

## 這不是「候選帶進來的退步」，也不是「兩邊都有所以不算」

**是第三種**：缺陷躺在兩個 profile 共用的位元組裡，而**只有候選讓它在日常使用
中會被走到**。分類的後果由閘門擁有者裁定，不由起草方裁定（AGENTS.md §8）。

## 069 的回歸網沒有涵蓋這條路

`sink-does-not-drag-the-page` 只讀 `#sink`，而且是用 IME 上屏驅動的；
`arrow-keys-match-the-profile` 量的是按鍵有沒有被吃掉、游標、toast，**從不量
捲動**。兩者都沒有讀過 `#a11y-doc` 的幾何。**069 修好的是一個元素，不是一個
類別**，而回歸網跟著只守那一個元素。

## 未做

- `#a11y-doc.offsetTop` 與 `.desk` 的捲動比例，兩個 profile 都要量。
- v8 是不是真的把 `#a11y-structure` 留在 `unavailable`（預測，未量）。
- 正對照：把 `.a11y-only` 補上 `top:0;left:0`，捲動比例應該塌掉。**沒有塌掉
  就表示上面整套判讀是錯的。**
- 「捲到底之後按 Tab 看焦點落在哪裡」這個直接區辨也沒做。

## 一併記下的另一個現象，**不要跟上面併成一句**

按到文件第一行再往上，焦點會離開文件區域跑到工具列。整晚 log 裡
`leaving panel` 出現三次（00:10:42.301、00:12:13.462、00:58:20.269），全部在
頂端邊界。頁面裡**沒有任何焦點圍堵**（沒有 `tabindex`、沒有 focusin/focusout
陷阱、唯一的 `keydown` 監聽在 `#sink` 上），而這些位元組兩個 profile 共用。

主 session 一度把這兩個現象併成同一個假說，**那是推論不是量測，已在筆記裡
更正並保留**。

# Phase 2 的預先登錄（寫在任何數字存在之前，2026-09-08 01:30）

量測還沒跑。以下四個結局與它們各自**在事實上確立什麼**，寫在跑之前；
**後果（soak 計數要不要歸零）不由量測選出**，那是閘門擁有者的裁定，選項列在
最後一節，同樣寫在數字存在之前。

## 要量的四項

1. `#a11y-doc.offsetTop` 與 `#canvas.offsetHeight`，**兩個 profile 都量**。
2. 把 `#a11y-doc` 的內容捲進視野時，`.desk` 用掉可捲動範圍的**比例**
   （不是像素——069 的判準就是因為像素分不出「捲到游標」與「捲過頭」才改寫成
   比例的，這裡沿用同一個形狀）。
3. v8 的 `#a11y-structure` 是不是真的停在 `unavailable`／無子節點，
   以及兩個 profile 各有幾個可瀏覽的停靠點在 `#a11y-doc` 裡。
4. **正對照**：把 `.a11y-only` 補上 `top:0;left:0`（只在暫存鏡像上，不碰樹），
   比例應該塌掉。

## 預先登錄的結局

- **O-1 — 機制在共用位元組裡，兩個 profile 都有。**
  兩邊的 `offsetTop ≈ canvas 高度`，且兩邊把它捲進視野都吃掉 ≳99% 的可捲動
  範圍。確立：這是共用缺陷，不是候選帶進來的。
- **O-2 — 機制共用，暴露量不同。**O-1 成立，且 v8 在 `#a11y-doc` 裡的停靠點
  數目遠少於 v12（預測：v8 ≤1，v12 每段一個）。確立：v8 的使用者會撞到一次，
  v12 的使用者每按一次方向鍵都撞到。
- **O-3 — 幾何在兩個 profile 之間不同。**確立：上面整套原始碼判讀是錯的，
  093 要重開，phase 1 的結論作廢。
- **O-4 — 正對照沒有塌。**確立：即使在 v12 上，`top`／`left` 也不是成因；
  093 的機制段落必須撤回改寫，不是打補丁（AGENTS.md §4）。

**如果這個量測永遠沒做**：093 停在「機制由原始碼確認、行為未量」，
**不得**被複述成「已確認 v8 也一樣」，而修法的分類問題保持未決。

## 後果的選單（由擁有者裁定，不由數字選出）

不論落在哪個結局，以下三種處置都是可能的，而且**都不是量測能決定的**：

- **D-a — 比照 086**：共用缺陷、延後到 cutover 之後修，soak 不歸零。
- **D-b — 視為候選在實務上帶進來的退步**：cutover 前修，計數歸零。
- **D-c — 因為它是無障礙產品上的無障礙阻斷，不論分類先修**：成本同 D-b。

**一個必須一起讀的事實（finding 094）**：修法動的是 `e2-editor.html`，而
**那個檔案不被任何檢查雜湊**——`servedSha256` 與 `pageSha256` 都看不到它。
所以在機械上，改它不會讓任何一趟已押的 run 轉紅。**若裁定是「修了不歸零」，
理由必須是裁決認為它不算，不能是「守衛剛好沒在看那裡」。**這句話寫在數字
出現之前。

# 擁有者的裁定：D-c（2026-09-08，append-only）

擁有者的回覆，逐字：「D-c」。

**D-c ＝「因為它是無障礙產品上的無障礙阻斷，不論分類先修」**，而選單裡它的
成本寫的是**「成本同 D-b」**，也就是 **soak 計數歸零**。裁定以此記錄。

這一句刻意寫在這裡：**計數歸零不是機械上被逼的。**finding 094 已經確認
`e2-editor.html` 不被任何檢查雜湊，所以改它不會讓任何一趟已押的 run 轉紅——
六趟在機械上會活下來。歸零是**裁決說它算**，不是守衛看到了。這正是預先登錄
那一節要求的形式：理由不得是「守衛剛好沒在看那裡」。

（若擁有者要的其實是「修，但主張計數存活」，那是另一個裁定，需要另外寫下
理由；在那之前以本節為準。）

## 這個裁定沒有涵蓋的

上面「一併記下的另一個現象」——頂端邊界的焦點逃逸（`leaving panel` 三次，
頁面裡沒有任何焦點圍堵）——**不在 D-c 的問句裡**，因此**維持未裁定**。
它是第二個現象，不得因為第一個有了處置就順手一起處理或一起忽略。

## 由這個裁定打開的一個窗口（提出，未執行）

finding 094 的處置原本是「只登錄、不補機制，補綁排在 cutover 之後」，理由是
補綁會改變 `servedSha256` 的定義＝動到判準，而閘門正在跑且已押六趟，
不滿足 AGENTS.md §9 的「先於滿足」。

**D-c 讓計數歸零，那個阻礙就消失了**：計數為 0 的那一刻，是「先於滿足」唯一
成立的窗口。§9 的另外三個條件裡，「被逼出且指名」（093／094）與「有截止」
（第 12 趟乾淨執行）也都成立；**卡住的是形式檢驗**——bundle 的 `included` 是
手工枚舉，加一條路徑進去仍然是手工枚舉（094 自己就是這樣被判別出來的）。

所以這是**一個要決定的工作項，不是一個已經成立的判準**，且決定權不在起草方。
記在這裡是因為窗口只在計數為 0 時開著，錯過就要再等一次歸零。

## 裁定一：O-1 的門檻**照字面沒有滿足**，但 O-1 仍然成立——理由要說清楚

O-1 寫了兩個子句：(a)「兩邊的 `offsetTop ≈ canvas 高度`」；(b)「兩邊把它捲進
視野都吃掉 **≳99%** 的可捲動範圍」。

- **(a) 精確滿足**：928 對 929，兩個 profile 逐像素相同，`top` 計算值 929px。
- **(b) 照字面沒有滿足**：實測 0.9759，不是 ≳0.99。

**不把門檻改成 97%。**O-1 要確立的宣稱是「這個節點坐在紙張底部、兩個 profile
共用」，而 **(a) 就是那個宣稱本身的直接量測**；(b) 是它的代理。依 AGENTS.md
§7（驗宣稱不要驗代理），O-1 由 (a) 成立。

**同時登錄我自己寫判準時的瑕疵**：(b) 沒有把 `.desk` 的 `padding: 20px`
（`e2-editor.html:77-78`）與 `scrollIntoView({block:"nearest"})` 的停止規則算進去
——`nearest` 停在目標的下緣，永遠不會跨過最後那 20px，所以 810/830 就是這個
形狀下 `nearest` 能達到的上限。這個解釋自己帶著一個預測，而預測被證了：
換到 1920×1080，同樣的 40px 在只有 329px 的可捲動範圍裡占比更大，比例跟著掉到
0.9392。**殘差隨 padding 移動，正是那個解釋要求的。**

下一版若要再用比例當門檻，必須改用 `block:"start"`，或把上限一起寫進判準。
**這一版不追溯修改**。

## 裁定二：這一輪最該記住的不是數字，是那個差點成立的綠燈

執行者如實登錄：**第一次 1920×1080 的量測把 v12 讀成 `unavailable`／0 個子節點
——跟 v8 一模一樣**，因為它只等了 1.5 秒，而 v12 需要約 1.0–1.5 秒才完成投影
（`e2-editor-app.js:267-270` 自己就記著這個暫態）。

**那個版本會回報 O-2 未命中，而且它會是綠的。**

處置也對：換成固定次數、**刻意不提早退出**的取樣軌跡。理由要抄下來——
提早退出的迴圈會給 v12「它需要多久就多久」、給 v8「整段等待」，而**兩者之間的
時間差本身就是待測的量**。一個會在第一次成功時停下的迴圈，量的是別的東西。

## 仍然未量（不得被上面的綠燈蓋過去）

- **Orca 的瀏覽游標是不是實務上驅動捲動的那一個**。這支探針是自己呼叫
  `scrollIntoView`；這一段的連結目前靠 069 的前例與擁有者的兩趟走訪，**不是量到的**。
- 「捲到底之後按 Tab」那個直接區辨。
- 頂端邊界的焦點逃逸，維持獨立、維持未裁定。

## 這不影響 D-c

擁有者的 D-c 裁定寫在 `ed1ea02a`，**早於這些數字存在**。這裡記一筆是因為
順序本身值得留著：裁定沒有被數字牽著走。
