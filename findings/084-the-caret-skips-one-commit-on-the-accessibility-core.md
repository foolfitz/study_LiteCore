# 084 — a11y core 上，游標偶爾整整跳過一次 commit：文字進了文件，游標原地不動，等到**下一次** commit 才補上

| | |
|---|---|
| **狀態** | **已修，已量**（2026-08-27）。殼層 v43（`7e99d3a3…`）——**不動引擎、不用連結、profile 也不用重新打包** |
| **發現日** | 2026-08-26。這格檢查在 a11y 這條線上**從來沒跑到過**——finding 082 修好之後才第一次被量到 |
| **嚴重度** | **中**：文字不會掉，游標會停在錯的地方直到下一次輸入。使用者看到的是「我打的字跑到別的地方了」 |
| **可重現** | a11y core **48 次 commit 掉 10 次（21%）**，四輪各 4／2／1／3（2026-08-27，`--caret-engine-probe stalled`）。2026-08-26 的 27 掉 3 是每輪只跑三次 commit、沒有任何探針的量測；兩者不衝突 |

## 一句話

在 a11y core 上，某一次 commit 之後**游標不動**——文字確實進了文件（revision 有進），
但頁面畫游標所依據的位置停在原地，**輪詢滿 8 秒都不動**，直到下一次 commit 才一次補兩格。

## 數字

`caret-follows-the-text-you-type` 讀 `#sink` 的 `offsetLeft`，一輪三次 commit。
十九輪、兩顆 core、每一輪都落在同一組位置上：

| 輪數 | profile | 結果 | 每次 commit 之後的位置 | 差 |
|---|---|---|---|---|
| 多數 | 兩顆 core 皆有 | PASS | 163, **278**, 393, 509 | 115, 115, 116 |
| v10 r1 / v11 r2 | a11y | FAIL | 163, **163**, 393, 509 | **0, 230, 116** |
| v11 r5 | a11y | FAIL | 163, 278, **278**, 509 | 115, **0, 231** |

**只有其中一次讀數不一樣，而總和完全相同**——兩條路都收在 509，而補上的那一步是
115＋115。所以那一次 commit 的游標移動**沒有消失，是被延到下一次**。

| core | 量到的 commit 次數 | 掉的次數 |
|---|---|---|
| 出貨（`e2-editor-v8`） | **42** | **0** |
| a11y（`e2-editor-v10`／`v11`） | **27** | **3** |

## 分佈是雙峰的，所以它不是「慢」

把固定的 `time.sleep(1.2)` 換成**對判準本身輪詢**（8 秒上限）之後，等待時間進了紀錄：

```
正常：  settledAfterMs = 0 或 1      ← revision 一到，游標就已經對了
掉的：  settledAfterMs = 8013        ← 輪詢跑滿上限，始終沒動
```

**0 ms 或永不。**中間什麼都沒有。這不是延遲分佈，是**掉了一次更新**。

## 我第一個判斷是錯的，是自己的儀器打掉的

看到「總和相同、只有中間那次讀數落後」時，我的第一個判斷是
**harness 讀太早**——那支臂等 revision 之後睡固定 1.2 秒，而這格檢查自己的註解就寫著
它涵蓋的缺陷本來是個 race。

**換成輪詢之後它還是紅的，而且紅得更清楚：8013 ms。**
輪詢期間沒有再打任何字，所以「要等下一次 commit 才補上」的缺陷**無法被輪詢遮掉**——
這正是把 sleep 換成 poll 之前必須先問的那個問題。

儀器換對了兩件事：把一個沒有數字的間歇紅變成有數字的紅；並且把
「harness 讀太早」這個對手假說**排除掉**。

## 成因：兩個寫入者，一個守衛（2026-08-27）

頁面畫游標依據的是 `snapshot.editorState.caret`，而那一格有**兩個**寫入者：

| 寫入者 | 位置 | 守衛 |
|---|---|---|
| 引擎的 `editor-state` 推播 | `editor-shell-v2/narrow-editor-v2-session.js:171-173` | **有**——`sourceSequence` 沒有前進就不寫 |
| drain 自己的 `editor.getState()` | `editor-shell/editor-session.js:301-311` | **沒有**——讀到什麼就寫什麼 |

那個守衛是 finding 068 加的，它自己的註解就寫明了理由：「一個慢的事件可能落在一次
較新的讀之後，把游標往回搬」。**對稱的那一半——一次慢的「讀」落在較新的事件之後
——沒有人守。**這張 finding 就是那一半。

掉掉的那一次 commit，逐列是這樣（`stalled-run1`，`CARETFOLLOW10`）：

```
believed  seq=294  caret=3458,4904  rev=128
believed  seq=295  caret=3458,4904  rev=128
believed  seq=296  caret=5618,4904  rev=128   ← 游標到了
believed  seq=294  caret=3458,4904  rev=129   ← drain 把它蓋回去
believed  seq=294  caret=3458,4904  rev=129
applied   5618,4904                           ← sink 真的被搬到新位置
applied   3458,4904                           ← 然後又被搬回來
```

**`sourceSequence` 往回走**是這個缺陷的簽名；同一列 `revision` 往前走則指認了寫入者
——只有 drain 會把 `revision` 和 `editorState` 一起寫。

十次掉掉的 commit，**十次都有這個簽名**，而且**十次都是第一支探針**（sink 被看到沒動
之後 52–54 ms）就已經拿到新游標——引擎從來沒有落後過。

## 出貨那顆為什麼沒掉：一次 commit 只發一則公告

同一支儀器、同樣十二輪，出貨的 `e2-editor-v8` **24 次全過**。原因在同一個欄位裡：

| profile | commit | 掉 | 每次 commit 的 `sourceSequence` |
|---|---|---|---|
| 出貨 `e2-editor-v8` | 24 | **0** | **＋1** |
| a11y `e2-editor-v11` | 48 | **10** | **＋2** |

出貨那顆（passing）：

```
seq=226 rev=123 ready / busy / busy
seq=226 rev=124 busy      ← drain 的寫入（revision 前進，seq 不動）
seq=226 rev=124 ready
seq=227 caret=新 rev=124  ← 帶游標的公告在 drain 之後才到
```

a11y 那顆（passing）：

```
seq=282 rev=123 ready / busy / busy
seq=284 caret=… rev=124 busy   ← drain 的寫入，已經在 284
seq=284 rev=124 ready
seq=285 rev=124 ready
seq=286 caret=新 rev=124       ← 游標到了
```

**出貨那顆上，帶游標的公告是一次 commit 裡最後發生的事**——drain 已經寫完了，沒有東西
可以被蓋掉。a11y 那顆每次 commit 多發一則會改狀態的回呼，drain 的寫入因此落在序列
中間；落在帶游標那則公告之前還是之後，就是這一輪過或不過的分野，而在這條線上大約
五次會錯一次。

**所以「出貨那顆 66 次沒看過」是一個比率，不是免疫。**帶著這個缺陷的程式今天就在出貨。

## 舊的那個 11%，是在一支會壓抑缺陷的探針底下量的

第一版儀器在**每一次 commit 之前**都發一支 `editor-get-state`。那是一個真實的引擎命令，
而它會改變回呼交付的順序：

| 儀器 | commit 次數 | 掉的次數 |
|---|---|---|
| 每輪都問（`every-round`） | 24 | **0** |
| 只在 sink 沒跟上之後才問（`stalled`） | 48 | **10（21%）** |

同一個設定、同一顆 profile，唯一的變因是探針。Fisher exact p = 0.012。
**第一版儀器壓抑了它被造出來要量的那個東西**，所以預設改成 `stalled`：跟上的那一次
commit 一個引擎命令都不發。

而**這個結論不靠探針**：決定性的紀錄是 `caretBelieved`——那是頁面**被交到手上**的東西
的紀錄，沒有任何引擎命令參與，而它顯示推播帶著新游標到了、然後被蓋掉。

## 修法（2026-08-27，殼層 v43）

`NarrowEditorV2Session` 在 constructor 裡包住自己 state machine 的 `update`：
`editorState.sourceSequence` 倒退時**只把 `editorState` 那一格拿掉**，patch 的其他部分
（`revision`、`dirty`）照常寫入。位置在子類別，理由和 068 一樣——最自然的家
`EditorSession._drain()` 在一個綁著 E1-C 判定的檔案裡。

四個設計決定，每個都有測試、也都有讓那格測試變紅的突變：

| 決定 | 理由 |
|---|---|
| 包 `update`，**不**包 `transition` | 重開一顆引擎時序號從頭算，那是**合法的**往回走 |
| 整個 `editorState` 丟掉，不逐欄合併 | 兩邊都是某一刻的一致快照；逐欄挑會拼出一個從未存在過的狀態。頁面讀的六個欄位公告全都帶 |
| 沒有 `sourceSequence` 就不動它 | 「不知道」和「往回走」是兩種宣稱 |
| 相等要放行 | drain 的讀答在公告的那個序號上，就是同一刻 |

突變：拿掉守衛（6 紅）、裝了但永不擋（2 紅）、連相等也擋（1 紅）、把整個 patch 丟掉（1 紅）。
另有一格釘住「基底類別只指派 `this.state` 一次」——否則守衛會被靜靜換掉而其他測試照樣綠。

## 驗證：判準寫在跑之前——光綠不算，守衛必須真的燒過

一輪 12 格全過但守衛一次都沒燒，測到的只是「這輪沒輸這場 race」。所以守衛擋掉幾次
被記進報告（`window.__ppStaleWrites`）。

| 輪 | profile | commit | 掉 | `settledAfterMs` | 守衛擋掉 |
|---|---|---|---|---|---|
| 修前 | `e2-editor-v11` | 48 | **10** | 0–1 或 **8023–8053** | — |
| 修後 1 | `e2-editor-v11` | 12 | 0 | 0–1 | 2（1 次在打字輪內） |
| 修後 2 | `e2-editor-v11` | 12 | 0 | 0–1 | 10（5 次在輪內） |
| 修後 3 | `e2-editor-v11` | 12 | 0 | 0–1 | 7（6 次在輪內） |
| 修後 | 出貨 `e2-editor-v8` | 12 | 0 | 0–1 | **0** |

**那場 race 在打字輪內仍然輸了十二次，十二次都被接住。**8 秒那個峰完全消失。
三輪 a11y 都是 37 PASS／3 NE、`ok: true`；出貨那顆是 **38／2、`ok: true`**，而守衛
一次都沒燒——正是「每次 commit ＋1」預測的結果，也表示這個修法動不到它沒碰過的路。

**而且它從來就不只關於打字**：每一輪 a11y 裡守衛也在 caret 那支臂之外燒過（1、5、1 次）。

## 沒有量的（因此不指認）

- **為什麼只在 a11y core 上。**兩顆 core 差兩個 build 變因（`writer calc` ＋ accessibility
  對上 writer-only 無 accessibility），一次量測——findings 040 和 048 的規矩。
  42 對 0 很強，但它是**發生率**，不是機制。
- ~~掉的是哪一層的更新。~~ **2026-08-27 量到了**（見上）。剩下沒量的是**為什麼是這顆
  core 比較常輸**——時序，而不是機制；機制是共用的那段 JavaScript。
- **為什麼 a11y 那顆一次 commit 多發一則公告。**那是 build 差異加上一次量測——
  findings 040 和 048 的規矩，不指認。
- **出貨那顆會不會也掉。**它跑的是同一段程式；66 次沒看過是比率，不是免疫。
- **對使用者的實際樣子。**這是合成輸入；真鍵盤下是不是同一個形狀沒有量過（D5 的範圍）。
