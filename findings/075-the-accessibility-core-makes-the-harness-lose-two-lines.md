# 075 — 在帶 accessibility 的 core 上，回歸網的分帶把最上面兩行整個丟掉，而文件其實畫得好好的

| | |
|---|---|
| **狀態** | **成因確定並已修**（2026-08-23）：頁面外的未初始化記憶體，處方＝改用不透明度裁切頁面 |
| **發現日** | 2026-08-23 |
| **嚴重度** | **高，但方向要講對**：它讓回歸網對 a11y core 產生 3 個 FAIL／6 個 NOT_ESTABLISHED，而**產品可能沒壞** |
| **可重現** | 是，3 顆從該 core 建的 profile 上逐格相同 |
| **是否上游** | **可能是，但歸因不足**：那顆 core 同時多了 calc 與 accessibility，兩個差異一次量測 |

## 一句話

`e2-editor-v5` 的產品路徑紅了，而**紅的原因不是產品做不到那些事**——是 harness 的
分帶啟發式在這顆 core 上把最上面兩行分類掉了，之後所有需要「點在第 N 段」的檢查都瞄
錯地方。

## 歸因：四點變異控制

| profile | core | 本輪引擎改動 | 產品路徑 | 分帶 |
|---|---|---|---|---|
| `e2-editor-v4` | writer-only | — | **綠 35 PASS** | 9 對 9 |
| `a11y-gate0` | a11y | **無** | 紅 2 FAIL | 7 對 9 |
| `a11y-projection` | a11y | ＋段落文字 | 紅 3 FAIL | 7 對 9 |
| `e2-editor-v5` | a11y | ＋段落文字＋大綱 | 紅 3 FAIL | 7 對 9 |

`a11y-gate0` 一個本輪引擎改動都沒有（沒有段落文字欄位、沒有大綱、連那顆對著 core
內部標頭編的橋接物件都沒連進去），照樣紅 ⇒ **成因在 core 那一側，我方引擎改動全部
洗清**。

順帶證明了第三格 FAIL 是**判準過期**而不是缺陷：`the-document-region-says-why-it-is-empty`
斷言「這顆 profile 不提供段落文字」，所以只在**帶了那個能力**的兩顆上紅，
`a11y-gate0` 上是 PASS。

## 機制：合併之後被密度過濾丟掉

`text_bands()` 先把間隙 ≤ `BAND_MERGE_GAP`(8) 的 run 合併，再保留密度落在
`[0.15, 0.9)` 的帶，**其餘直接丟棄且不出現在回傳值裡**。把同一份掃描重算並印出被拒
絕的帶：

```
a11y-gate0   原始 run 15 → 合併後 11    最小間隙 2, 2, 2, 3
   [DROP] top  85 bottom 124  高 40  密度 0.133  centre 0.1125   <-- 兩行併成一條
   [keep] top 135 bottom 144  高 10  密度 0.433
   ...（其餘 7 條照常）

e2-editor-v4 原始 run 11 → 合併後 11    最小間隙 12
   [keep] top  85 bottom  98  高 14  密度 0.596
   [keep] top 114 bottom 127  高 14  密度 0.380
   ...
```

- v4 的前兩行是**兩條**帶（密度 0.596／0.380），各自遠在門檻之上；
- a11y core 上它們**併成一條 40 列的帶**，而一條橫跨兩行加行距的帶，密度自然被稀釋到
  **0.133**——差一點點低於 0.15，於是**整條被丟掉，兩行一起消失**。

⇒ 9 條 → 合併成 8 → 丟 1 條 → **正好 7**。

## 這不是「墨跡不見了」，而我一度這樣讀

第一版判讀是「上方兩段的墨跡消失」。**錯的**，而抓到它的是探針裡多加的那一格：直接問
那個 y 位置有沒有墨跡，回答是 `inkAtTopBand: True`，16 秒後仍是 True。

**段落有畫出來、使用者看得到；消失的是分類。** 只看「帶數 7」永遠分不出這兩件事——
這是同一天第十次「把儀器的輸出當成被量的東西」。

## 觸發條件：要放過游標才會發生

| | 靜止（剛開檔） | 放一個游標之後 |
|---|---|---|
| `e2-editor-v4` | 9 條 | 9 條 |
| `a11y-gate0` | **9 條** | **7 條** |

靜止時兩顆 core 的分帶**幾何完全相同**（9 條、每條的 first/last/高度逐一相同）。所以
這不是「a11y core 版面不一樣」這麼簡單，是**放游標這個動作在這顆 core 上多產生了
4 個 run**（11 → 15），其中若干間隙只有 2–3 列。

游標放在 y=0.24（第六條帶附近），而消失的是**最上面兩條**——所以那些多出來的 run
**不在游標處**。

## 成因：頁面外被畫上未初始化的記憶體（2026-08-23 拍到）

拍下四張畫布（兩顆 core × 靜止／放游標後）之後，用看的就分得出來：**出貨那顆 core
的頁面外圍是平的，a11y core 的頁面外圍是彩色雜訊**。

只看頁外的欄（x < 14 與 x >= 710），每張 26,941 個像素：

| | alpha=0 | **alpha>128** | **通過墨跡判準** | alpha 取值數 |
|---|---|---|---|---|
| v4 靜止 | 21,563 | 0 | 0 | 47 |
| v4 放游標後 | 21,595 | **0** | **0** | 33 |
| a11y 靜止 | 21,559 | 3 | 0 | 46 |
| a11y 放游標後 | 19,236 | **290** | **31** | **184** |

出貨那顆 core 的頁面外是**透明**的，所以墨跡判準（`alpha>128` 且 r,g,b < 100）從來
碰不到它。a11y core 重繪之後在那裡留下沒初始化的記憶體：alpha 出現 184 種取值、290
個像素變成不透明、其中 **31 個夠暗**。

最便宜的旁證是 PNG 檔案大小：同一份文件、暗像素數幾乎相同（4,368 對 4,424），
a11y 那張 **90,538 bytes 對 42,434**。雜訊壓不掉。

**31 個像素怎麼吃掉兩段**：它們一列 1–3 個落在**行與行之間的空隙**、兩側都有 ⇒
第一二行的間隙從 12 列掉到 2 列而被合併 ⇒ 帶的水平範圍被最外側那顆邊緣像素撐開，
157 變成 634 ⇒ 密度 84/634 = **0.133**，差一點點低於 0.15，整條被丟掉。

## 現行的排除機制為什麼沒救到

`INK_ROWS` 本來就有頁面裁切，判準是「某一欄被畫**暗**超過畫布高度的 20%」。拿四張畫布
離線重放：**它只找到 1 欄，`clipped` 四張全是 false**。也就是說這個機制在這份 fixture
上**從頭到尾都沒啟動過**——v4 沒事跟它無關，是因為 v4 的頁外剛好是透明的。

## 處方：改用不透明度找頁面（不是調門檻）

頁面是**不透明**畫出來的、外圍不是，而這是這份算繪在兩種狀態、兩顆 core 上**都具備**
的性質。裁到「不透明度超過 20% 的最外側兩欄」之間：

| | 修改前 | 修改後 |
|---|---|---|
| v4 靜止 | 9 | 9 |
| v4 放游標後 | 9 | 9 |
| a11y 靜止 | 9 | 9 |
| a11y 放游標後 | **7** | **9** |

四張畫布判出**同一段頁面範圍 15..709**。頁內欄至少 96.9% 不透明、頁外欄最多 7.6%
——最差 13 倍的分離度；在出貨那顆 core 上是 968,783,638 倍，因為那裡就是全透明。

**在出貨那顆 core 上它丟掉 0 個像素**，四張畫布都是。這不是對門檻的期望，這就是
「外圍是透明的」這句話的意思。

`BAND_MERGE_GAP` 與密度門檻**都沒有動**。動它們就是把儀器調去遷就某一顆 core 的雜訊。

掃描現在會回報 `pageOpaque`、`pageClipped`、`offPageInk`——出貨 core 上 `offPageInk`
是 0，非 0 就是這個缺陷被看見並被指名。

## 沒有量的（因此不指認）

- **是不是 accessibility 造成的。**那顆 core 是 `--with-wasm-module writer calc`
  且沒有 strip accessibility，出貨那顆是 writer-only 且 strip 掉——**兩個差異、一次
  量測**。calc 進來改變 heap 佈局沒有被排除。
- **使用者看不看得到。**雜訊在畫布上，所以人對著這個 build 看應該會看到頁面周圍有
  彩色雜訊。**還沒有人看過。**這一題該問操作者，不是再寫一支探針。
- **產品到底有沒有壞。**本文解釋了 harness 為什麼紅，**沒有讓產品變綠**。粗體反相
  很可能是下游後果（`format_arm` 無條件按一次、依賴切換交替，瞄錯就差一步），
  但那仍是假說，要人拿著它用一次才算。
