## 現象

`recovery-returns-what-the-product-promised` 在 v3 上是 PASS，在 v4 上是
NOT_ESTABLISHED。誘發器（finding 038 的「拖過尾註參照標記，再做一次操作」）沒有把
引擎卡住：`stateAfterNextOperation` 從 `recoverable-error` 變成 `ready`。

**這一格不是被 finding 071 的卡死污染的。**071 修好之後重跑，它仍然
NOT_ESTABLISHED。

## 機制：一條 ink band 被游標接起來了

harness **從 ink band 推導拖曳座標**。兩輪的數字：

| | v3 | v4 |
|---|---|---|
| 誘發前的 `bands` | `[81,95] [105,117] [126,139] [1000,1018]` | **完全相同** |
| 誘發當下的 `bandsAtInducer` | `[83,95] [106,120] [130,143] [1000,1018]` | `[83,121] [130,143] [1000,1018]` |

前兩條在 v4 併成一條，中間那 10 列多了墨。文件、語料、誘發前的 band 全部相同，
中間唯一的變化是**在那個位置打了字**。

**多出來的墨是游標。**[finding 068](068-the-caret-is-not-redrawn-after-you-type.md)
修好之前，游標畫在**打字之前**的位置（落後一整串字）；修好之後它畫在該在的地方——
而該在的地方，正好是那兩條 band 之間的空隙。游標高約 16 列，空隙 10 列，於是接起來。

`text_bands()` 的密度過濾**本來就會擋掉單獨的游標**（一個像素的墨、一個像素的寬度，
密度 1.0，高於 0.9 的上限）。擋不掉的原因是**合併發生在密度過濾之前**：游標那一段
先被 `BAND_MERGE_GAP` 併進相鄰的文字 band，聯集的密度是文字的密度，於是通過。
游標從來沒有被看見，只有行數變少了。

## 第一次修法：失敗，已撤回

**做的事**：在合併之前丟掉水平寬度 ≤ 3 的段（`CARET_MAX_EXTENT`），附七格單元測試，
含門檻兩側各一格。單元測試全過。

**結果**：`findings/evidence/072/product-path-with-the-failed-remedy.json`

- `bandsAtInducer` **仍然是 `[83, 121]`**——完全沒有解掉要解的那件事
- 我當時還寫了「**而且弄壞了兩格本來會過的檢查**」——
  `format-a-paragraph-changes-that-paragraph` 與 `ctrl-x-is-handled-by-the-product`
  從 PASS 掉到 NOT_ESTABLISHED。**這個歸因是錯的，更多次執行推翻了它。**
  撤回之後那兩格在一輪裡回到 PASS、在下一輪又掉回 NOT_ESTABLISHED，
  **它們是間歇的**，成因是我在同一批工作裡新增的 `caret-follows-the-text-you-type`
  ——它在語料裡打了 36 個字元，而那兩格是靠 **band 索引**瞄準的。
  `ctrl-x` 有一輪看到 9 條 band、下一輪 8 條，於是拖曳沒選到東西、回報
  `CLIPBOARD_EMPTY_SELECTION`。已把那格檢查移到不會有人再靠 band 瞄準的位置。

  **兩次執行就下歸因，等於用一個樣本判一件間歇的事**——而這張單自己講的就是
  「瞄準依賴會被別的東西撞掉」，我卻在同一份報告裡犯了同一個錯的另一半。

**為什麼失敗**：我把機制的**細節**看錯了。我假設游標是一段**獨立的 run**，被
`BAND_MERGE_GAP` 併進相鄰的文字 band，所以在合併之前把它濾掉就好。實際上一根 16 列
高的游標跨過 10 列的空隙，會讓那一段的墨**連續**——`counts[y] > 0` 一路成立，
從第一條 band 的底穿到第二條的頂。**根本沒有獨立的 run 可以丟。** 過濾器打在錯的
步驟上，而它真正做到的事只有改變別的 run 的存活與合併，於是別的檢查瞄錯。

撤回的理由因此只剩一條，但那一條夠：**它沒有做到它要做的事**。

**單元測試全過而修法無效**，這件事本身要記著：那七格測的是「一段獨立的細 run 會被
排除」，那個行為是對的、也真的成立——**只是它不是這裡發生的事**。一個測試可以完美地
驗證一個不相干的行為。

## 下一步（處方未定）

要濾掉的是**欄**不是**列**：游標是一條穿過許多列、只有一到兩欄寬的垂直線。正確的做法
是在算 row counts **之前**，先從掃描裡把「縱向連續很長、橫向只有一兩欄」的欄扣掉，
再讓 `text_bands()` 照舊跑。那需要掃描保留逐欄的資料（目前 `scan` 只給
`counts`／`firsts`／`lasts`，逐列聚合過了），所以這是掃描那一側的改動。

**在那之前 `recovery-returns` 維持 NOT_ESTABLISHED，而那是誠實的**：誘發器沒有誘發，
所以它對復原那條路什麼都不能說，它也沒有宣稱通過。

## 這張單真正的教訓

**一個產品缺陷的修法，會讓一個依賴它的量測工具失效。**068 修好之前，游標畫在錯的
地方，於是 band 是「乾淨的」；修好之後 band 反映了真實畫面，而 harness 的瞄準假設
了那個乾淨。

`queue-recovery-inducer-depends-on-an-unfixed-defect` 這個佇列項講的是同一件事的另一
面（誘發器依賴一個沒修的缺陷）。這一張是**第二個實例，而且方向相反**：不是誘發器依
賴缺陷本身，是**瞄準依賴缺陷的副作用**。

**處置**：這種依賴要寫下來，而不是等下一次修法把它撞出來。
