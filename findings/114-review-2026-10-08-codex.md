# Independent review of finding 114, 2026-10-08

Verdict: the corrected diagnosis is supported. This is a LibreOffice bundled-fontconfig configuration integration defect, demonstrated in the project's WASM builds and reproducible in native fontconfig. It is worth reporting upstream at normal severity. Do not describe it as a general failure of Taiwanese desktop LibreOffice deployments or as a WASM-specific font-metrics calculation defect.

## Checks completed

- Re-ran `check_fontconfig_lang_rewrites.py --profile e2-editor-v16 --expect 66`: 282 fontconfig-supported tags, 66 rewritten, all 22 packaged conf.d files loaded, no outside configuration files.
- Re-ran the same checker for e2-editor-v17 with `--expect 0`: 0 rewritten, all 21 packaged files loaded, no outside configuration files.
- Re-ran `build_base_no35_pack.py --check`: the v17 base pack differs from its source by exactly the omitted 35 rule file, with the remaining slices intact.
- Read the raw WASM match evidence and the V5 JSON: primary requests without charset select Liberation Sans with `tw` on v16 and a Noto CJK face with `zh-tw` on v17; all 11 owner-document initial caret rectangles equal their native references on v17. This does not prove every line or every editing state matches the native document.
- Downloaded current LibreOffice master at 216d39140d20bc87c2eb29014c489866991c99ee. Its external/fontconfig/ExternalPackage_fontconfig_data.mk still includes 35. The source has moved to vcl/unx/generic/font/fontconfig.cxx and still adds string FC_LANG at lines 1125 and 1406. The latter call is in matchFont, not Substitute. Normal Windows/macOS configure paths still disable freetype/fontconfig unless enabled for a headless build.
- Read fontconfig 2.18.2 source: string/string Contains uses FcStrStrIgnoreCase; strings are explicitly accepted for language properties by FcObjectValidType. Thus using FcPatternAddString is supported by the API; its interaction with this optional rule is the defect. The default conf_links list does not enable 35.

## Additional native Writer observation

The scratch fixture contains two identical short paragraphs per case, explicit 12/18 pt Asian sizes and zh-TW tagging. It uses the 13 font files extracted from v16, in both arms. Both sets of rules are absolute-path copies of the packaged rules, differing by exactly 35. The native LOK build additionally loads its fc_local.conf in both arms; this experiment is therefore a same-native-build intervention, not a claim that native loads only WASM files. The instrument reuses the existing native merge probe's loading, search, selection readback and caret callback routines, with a new scratch main that only positions and reads.

## Duplicate search and severity

Read-only Bugzilla REST full-comment substring searches for 35-lang-normalize, lang-normalize and FC_LANG return zero bugs. A combined zh-tw/fontconfig comment search returns 31186, 43984, 58324, 127922 and 137393. Combined line-height/fontconfig and line-spacing/fontconfig searches return related issues including 55469 and 64509. Read comments for 55469, 43984, 58324, 137393 and 64509; the font metrics issue (55469), font-name preference issues and missing-glyph issue have different demonstrated causes. These searches are not an exhaustive proof that no duplicate exists.

Taiwanese community searches find discussion of spacing differences between different font families (SLAT, 2018), but no located report diagnosing this language rewrite. Absence of a located report is not a measurement of incidence. Ordinary Windows/macOS builds do not use the affected backend; Linux exposure depends on actual rule activation; installed requested fonts may bypass the missing-family substitution. Desktop adoption is therefore compatible with a real defect in the self-contained WASM package. No data loss has been demonstrated; normal severity is appropriate, while the layout consequences matter to litecore.

## Corrections recommended before submission

1. Remove untested CODA-W from the summary; keep it as a possible affected configuration in the body.
2. Express the affected conditions together: the optional rule is active, a string language is rewritten, and the resulting font selection changes. Avoid saying every Taiwanese document, every CJK font name outside five Noto families, or every line has a 0.79 ratio.
3. Treat 282 tags as the fontconfig-supported input census used at the API boundary, and 66 as altered language values, not 66 measured document-layout failures.
4. Keep V4's 19-vs-20-pixel miss unresolved. Pixel rounding is plausible but was not directly tested. The language-corruption report does not require that discrepancy to be explained.
5. Replace 'no modifications in vcl' with the precise claim 'no modifications to the fontconfig matching or packaging code': the local tree does contain a QtFrame input-context patch.
6. Distinguish the Substitute call from the matchFont call when referencing both FC_LANG additions.
7. Prefer a self-contained native reproducer with both rule arms, explicit font requirements, and captured loaded-config paths. The owner's private document is unnecessary. Published WASM/CODA-W confirmation would strengthen platform coverage, but the diagnosed integration defect can be reported without claiming those unmeasured platforms.

## Upstream Qt GUI WASM follow-up

The upstream Qt GUI WASM has a source-level path to the same defect. This is an inference from the build and backend code, not a reproduction against a published official artifact.

At LibreOffice master 216d39140d20bc87c2eb29014c489866991c99ee, the Emscripten platform enables freetype/fontconfig. QtInstance::useCairo defaults to true unless SAL_VCL_QT_USE_QFONT is set; create_SalInstance consequently selects QtSvpSalInstance when the shared headless backend code is enabled. QtSvpGraphics inherits SvpSalGraphics, whose CairoTextRender inherits FreeTypeTextRenderImpl and uses the generic font substitution hooks. The standard WASM filesystem image includes fontconfig_data, and that package still activates 35-lang-normalize.conf. The standard environment.js does not override the font backend. The alternative Qt QFont backend also registers the fontconfig substitution hooks by default unless SAL_VCL_QT_NO_FONTCONFIG is set, but identical layout symptoms on that alternative backend have not been established.

Therefore, replacing the UI is not required to introduce the diagnosed language rewrite. The upstream default GUI build should be exposed under the same font-language and substitution conditions. The exact visible line-height effect remains conditional on the artifact's fonts, requested family availability, document language, and loaded configuration. In particular, neither the 0.79 ratio nor the owner's document has been tested against an official GUI WASM artifact. A different font inventory can change or conceal the symptom.
