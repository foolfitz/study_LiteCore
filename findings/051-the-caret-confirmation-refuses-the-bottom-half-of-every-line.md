## 現象

在產品頁面點一下想放游標：**要嘛 34 毫秒就好，要嘛卡 30 秒然後說
`EDITOR_CARET_NOT_PLACED`。** 差別只在於點在那一行的上半還是下半。

## 重現步驟

1. 開產品頁面（`e2-editor.html`，profile `e2-editor-v2`），等 `ready`
2. 點在某一行文字的**上半** → 0.3 秒成立
3. 點在**同一行的下半** → 等 30.1 秒，然後 `EDITOR_CARET_NOT_PLACED`

## 證據

`findings/evidence/051/`（預測寫在量測之前）：

- `four-clicks-all-refused-chrome.json` —— 四個孤立點擊，**每個都 30.1 秒後被拒**
- `halves-before-fix-chrome.json` —— 同一行：上半 0.3／0.5 秒成立，下半兩次都 30.1 秒
- `halves-after-fix-chrome.json` —— 修法之後同樣四次點擊：0.3／0.5／0.5／0.3 秒，全部成立

錯誤自己帶的欄位就說明了一切：

```
asked   yTwips 1641
caret   y 1418  height 414        → 行框是 1418..1832
sequenceAdvanced: true
```

**引擎做對了**：1641 在 1418..1832 之內，而且引擎的 `sourceSequence` 已經前進
（它有話說）。被拒絕的是判準，不是引擎。

## 分析

048 的修法用兩個訊號確認一次點擊：引擎有沒有說話、游標在不在點的那一行。
第二個寫成：

```js
Math.abs(yTwips - caret.y) <= Math.max(caret.height / 2, 1)
```

而 **`caret.y` 是矩形的上緣，不是中線**。於是可接受的範圍是
`[caret.y − h/2, caret.y + h/2]`——**行框上方半行，加上行框自己的上半**。
點在下半的，永遠等不到。

048 的註解裡寫的量測（「真實落點落在矩形上緣之上多達 119 twips」）本身沒有錯，
錯在它**只量到落點在上緣附近的那些**——那些是 harness 造的點擊。使用者的點擊
是均勻落在整個行框裡的。

## 為什麼前面每一輪都沒抓到（這條和 049／050 是同一個形狀）

- **人工輪的四格是拖曳**，而拖曳走的是 `selectRange`，那條路不經過這個判準。
- 唯一對得上的紀錄是 round 1 operator 的第一句話：「**游標沒辦法被放置，所以無法
  開始**」。當時判讀成「產品沒畫游標所以看不到」——**那句話同時也是字面上為真的**。
- 抓到它的是 `tools/run_e2_c_page_smoke.py`：**08-15 綠、08-16 紅**。而它今天之所以
  被重跑，是因為在做「產品那條路」的回歸網（本日計畫 T1）。

## 修法

```js
const slackAbove = Math.max(caret.height / 2, 1);
return yTwips >= caret.y - slackAbove && yTwips <= caret.y + caret.height;
```

**不對稱，而且不對稱正是量測的結論**：上方要留半行（點擊會落在兩個行框之間的空隙，
引擎把它歸給下面那一行，實測差距達 119 twips）；下方一格都不留，因為再往下就是
下一行自己的框。

**驗證**：

- 單元層：新增兩條測試，**把修法退回去這兩條會紅、048 的五條仍然全綠**（突變驗證）
- 瀏覽器端：`run_e2_c_page_smoke.py` 從「place-caret 等 30 秒被拒」變成
  **`定位游標 34 ms`**、整輪 `ok: true`

## 順帶修掉的兩件

1. **`make e2-c-assets` 沒有負責 `dist/editor-shell/`**——和 050 那天發現的
   `dist/input/` 是同一個缺口，只是隔壁目錄。serve.py 服務的是 `dist/`，所以
   「改了原始碼但產品跑的還是舊的」會靜靜地發生。已補上四個模組，並且**加了一條
   靜態檢查**：bundle 綁的十二個模組，每一個都必須是 `e2-c-assets` 的相依
   （拿掉那行 Makefile 相依，這條檢查會紅——已驗）。
2. **D5 的 `session-attestation.json` 會被蓋掉**。它在 operator 伺服器結束時寫入，
   而一個從更早的輪次留下來、直到殼層換代之後才結束的伺服器，會用**當下**的
   bundle 雜湊覆蓋它（實測：v4 的值被改成 v6 的）。值本身對那一輪不算錯，但它是
   **由哪個背景行程什麼時候死掉決定的，而不是由哪一輪跑在什麼上面決定的**——而這是
   判定會引用的證據。已改成一個 session 一個檔、**不覆寫**。
