## (2) Reasons (checked against the files)

- **The spec itself names the save confirmation as a family, not a string.** §33.3 (`specs/SPEC-M3-paragraph-merge.md:1146`) allows "該 case 自己的存檔確認（`已存出 N KB`…）", N variable. The runner and the reader already implement exactly that for the "no toast" clause: `SAVED = re.compile(r"已存出 [0-9]+(?:\.[0-9]+)? KB")` (`run_merge_wasm_shakedown.py:669`, `judge_counted_m2.py:83`) via `only_saves()` (`:727`, `:946`; reader `:242`, `:322`). Only `pair()` (`run_merge_wasm_shakedown.py:1116–1143`, `seen()` at `:1131–1135`) compares the same toasts verbatim. The guard overshoots the spec's own text on one field; aligning it is "守衛追上字面" (§33.3/§34.6), not a new criterion.
- **The number is a proxy for bytes, and the spec already says bytes are not comparable across saves.** The page computes it as `(bytes.byteLength / 1024).toFixed(1)` (`web/e2-editor-app.js:1438`). §12 (`:363–379`) withdraws byte comparison for typed documents (Rsid per session); §22.3 (`:750–752`) and `pair()` compare the kept documents by **paragraph text** for that reason. Comparing a rounded byte total is comparing bytes through a 1-decimal keyhole.
- **Diagnosis verified.** 252/252 `toastsAtEnd` entries across all four arms equal `toFixed(1)` of the kept file's size (JS ties go up: 14,592 B = 14.25 → `14.3`; 14,590–14,591 → `14.2`; 14,593–14,595 → `14.3`). Every differing pair differs only there; all other fields True (`judge-output.txt`, `pair-*.stdout.txt`). Within one arm (`counted-chrome.docs/C03-r1-after-key.odt` vs `C03-r3-after-key.odt`, 14,592 vs 14,590 B) the only differing zip members are `meta.xml` (`dc:date` 19:53:34 vs 19:59:47) and `settings.xml` (uncompressed size equal at 15,369; equal after removing the `config:name="Rsid"` item; deflate output 2,191 vs 2,189 B). Same for instrumented-vs-control pairs. The toast flips inside the control arm by itself (Chrome control C03: 14.2, 14.3, 14.3; instrumented: 14.3, 14.3, 14.2), so the field cannot distinguish "instrumentation changed behaviour" from "two saves happened".
- **What the control is for is independently satisfied.** §22.3 says the pair proves "回覆記錄與請求包裝沒有改變行為". Generation transitions, window state, reopen toasts, after-key and follow paragraph text are equal on all 78 pairs, both browsers; M2-1 separately pins each after-key `content.xml` to native after reduction (`compare(raw, spec["key"])`, `:873`). The KB figure adds nothing those do not already check more precisely. Nothing is lost by treating N as variable.
- **C is not "let the measurement decide"; it is a gate no honest run can pass.** C03/C10 after-key sizes observed: 14,590–14,595 B, straddling 14,592. With 6 such pairs per browser and roughly a quarter of saves landing below the boundary, a clean re-run of both browsers is on the order of 1 in 200. That is a criterion satisfied by luck, the fault CLAUDE.md §2/§4 forbids. The 34.1 default ("紅的也算") is for the case where nobody acts; here a committed honest-run witness exists (b8324a85 contains `x7-counted-m2/counted-*.json`, `counted-control-*.json`, `judge-output.txt`), which is precisely 34.1(b)'s trigger.
