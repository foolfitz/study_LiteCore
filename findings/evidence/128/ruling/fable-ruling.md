## 1. Question 1 — Option A: fix the page before freezing (register 131 as fixed-in-0.2.13, not as a limit)

Plain reason for the owner: holding Backspace is how everyone deletes several characters, and on this page about one key in four is refused with a developer's sentence and leaves its character behind. 0.2.12 already did it one key in twenty. B ships a known correction defect in the product's core promise; C brings back the ghost you reported. The trigger is one page decision, and the fix is a few lines that touch no anchored line.

Mechanism confirmed in code, not just hypothesised: the engine emits `editor-state` for every state-changing callback including the barrier's own one-unit TEXT_SELECTION (probe_engine.cpp:2648 `emitEditorStateEvent`, no barrier suppression); the session forwards it when sourceSequence advances (narrow-editor-v2-session.js:280-300); the listener reads that live snapshot (e2-editor-app.js:2306); actions are serialised page-side, so the second key is dispatched only after the first returns (editor-session.js:290-314), by which time the caret is collapsed and the gate refuses by `gEditorState.selectionRectangles.empty()` (probe_engine.cpp:5277-5303) — exactly the toast in the logs.

The rule (where: the `beforeinput` delete listener, e2-editor-app.js:2302-2309; declare the counter beside `engineActionsOut` at :100):
- Keep a counter of deletes THIS PAGE has sent and not yet seen settle (`delete-backward`, `delete-forward`, `delete-selection`), incremented before `editorAction(...)`, decremented in `.finally` (so an early return, a swallowed rejection and ENGINE_DISPOSED all release it).
- While that counter is > 0, the key goes out in its own collapsed form (`delete-backward` / `delete-forward`), whatever the engine's current shape says. Reason: the only shape that can hold when the in-flight delete returns is a caret, so the engine's range at this instant is the barrier's, not the user's.
- While it is 0, today's rule stands unchanged: engine shape, page belief as fallback (finding 121).
- Least-churn form: `deleteActionFor(action, shape, offers, inFlightDeletes = 0)` returning `action` when `inFlightDeletes > 0`; the handler passes the counter as 4th argument. Existing 121-U assertions (3-arg calls, `/deleteActionFor\(action, shape,/`) stay valid; the product-path anchor `  const action = DELETE_INPUT_TYPES[event.inputType];` (run_e2_c_product_path.py:1441) and `edit-arrows-swapped`'s `await run(...)` line stay byte-identical. Do NOT widen to `engineActionsOut > 0`: a real range + Ctrl+B + Backspace must still go out as delete-selection.
- Named edge (register, not a criterion): if the first delete on a real range is itself refused, the next key within its window goes out as delete-backward on a range and is refused too (gate, nothing dispatched; probe_engine.cpp:5277-5303 runs before `startSelectionBarrierDelete`, so no 119-style EDITOR_STATE_UNAVAILABLE restart). Two toasts, no data lost.

## 3. Corrections to the brief's mechanism

- "puts paint requests in the Worker ahead of the next delete" is not readable from the code as stated: the drain serialises page-side (editor-session.js:290-314), so the next delete is not in the Worker until the previous one resolves; whether run()'s paint (e2-editor-app.js:1742-1744) or the drain's next post wins is microtask order at :314 vs :1741 — undetermined statically. Keep it as a hypothesis. The raw data does support "one successful band paint per key": per-key delete time in 0.2.13 CLIMBS monotonically inside a burst (Chrome 70→85→100→113, Firefox 99→…→181, slope 10–15 ms/key ≈ one band paint 6.5–12 ms Chrome, slower Firefox), while 0.2.12 stays flat at 41–50 ms over 20 keys. The brief's median/p90 hide this ramp. Also readable in the data: refusals occur only in the mid-backlog regime (delete dispatched 10–45 ms late puts the 50 ms key inside the barrier's range window) and each refusal drains the queue, so the ramp resets — that is why late-burst keys at 70–113 ms had none.
- Consequence to register now (proposed finding 132, not a blocker): with A the ramp is uninterrupted. Prediction written before the run: 20th-key delete time on the fixed page exceeds today's maxima — Chrome 150–250 ms, Firefox 200–300 ms. Bounded by the burst, self-clearing, no data lost; owner's words: a long hold on Backspace trails the key by a growing fraction of a second. The remedy (coalescing paints while a key is queued, or caret band first) is a new mechanism → post-release spec with the A/B instrument, not this release (house rule §4).
- A sibling, unmeasured, register as a work item: a paragraph-format action's barrier also selects text (`.uno:SelectText`, finding 083), so a Backspace inside that window could read its range the same way; rule A is scoped to deletes on purpose (see §1).
- Minor: the README's Firefox p90 133 is the 26th of 31 sorted values; nearest-rank p90 is 146. Max 181 is unambiguous.
