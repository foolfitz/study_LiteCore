# Prediction, before the run: what WASM's fontconfig does with "思源黑體" tagged zh-TW

Written 2026-10-07, before any run in this directory. Diagnostic; nothing is counted or bound to it.

## What is already measured (not by this run)

- Finding 113's font-slot probe (`../../v15-shakedown/cjk-ab/font-slots-r3/pitches.txt`): on **v8** (full Noto Sans CJK TTC, ten families) a zh-TW paragraph whose Asian font is a name that **exists** in the profile (`Noto Sans CJK TC`, or the default slot) has pitch 20 px; every zh-TW row whose Asian font must be **substituted** (`思源黑體`, `PMingLiU`, `新細明體`, `Microsoft JhengHei`, `AR PL UMing TW`, `標楷體`) has 15-16 px, the Latin pitch. In v15, `Noto Sans CJK SC` (absent there) also fell to a Latin pitch although fontconfig says the one remaining CJK family covers zh-cn.
- Finding 114: native R0c with v16's own 13 font files and fontconfig gives the CJK line height on the owner's document.
- Native `fc-match` (system fontconfig 2.17.1) with v16's extracted `fonts.conf`: `思源黑體:lang=zh-tw` -> Noto Sans CJK TC; with **no lang**, or `lang=en`, -> Noto Sans CJK JP. With a **bare** config (only `<dir>`, no conf.d), `思源黑體:lang=zh-tw` -> Noto Sans CJK JP, but `思源黑體:lang=en` -> **Liberation Mono**. No native combination tried gives a Latin font when the pattern carries a CJK lang.

## Source read (libreoffice-26-8, read-only)

The name goes `PhysicalFontCollection::FindFontFamily` (`vcl/source/font/PhysicalFontCollection.cxx:1009`) -> not found by name -> pre-match hook `FcPreMatchSubstitution::FindFontSubstitute` (`vcl/unx/generic/fontmanager/fontsubst.cxx`, registered unconditionally by `FreeTypeTextRenderImpl::GetDevFontList`) -> `PrintFontManager::Substitute` (`vcl/unx/generic/fontmanager/fontconfig.cxx:1073`), which builds a pattern with `family=<name>`, `lang=` the font's language mapped by `mapToFontConfigLangTag`, then `FcConfigSubstitute`, `FcDefaultSubstitute`, `FcFontSetMatch` over LibreOffice's own font set. Both font caches key on the language (`FontSelectPattern::operator==`, `ImplFontCache::IFSD_Equal`), so a Latin answer cached for another language cannot leak into the zh-TW lookup. The WASM fontconfig is the bundled 2.18.2 built with `--with-baseconfigdir=/instdir/share/fontconfig --enable-libxml2` (`external/fontconfig/ExternalProject_fontconfig.mk`); the native LOK build unpacks the same 2.18.2.

## The instrument

`wasm_sdk_probe/tools/probe_fc_debug.py`: per profile, a scratch mirror where (1) the profile's `probe.js` has `ENV.FC_DEBUG="1153"` (MATCH 1 + SCAN 128 + CONFIG 1024) appended to the existing `preRun` line `ENV.MAX_CONCURRENCY="4"` (`probe.wasm` untouched), (2) the product page is repointed to the profile and creates its engine with `debug: true`, so the worker forwards stdout/stderr, and (3) a `Worker` wrapper in the page keeps every forwarded stdout/stderr line. It opens finding 113's font-slot fixture (16 variants x 2 identical lines, generated by `probe_cjk_font_slots.fixture_bytes()`), reads the canvas pitches the same way, and writes the raw log plus a parse of every `Match` block (requested families, langs, best match family and file). Chrome only; profiles v8 and v16; nothing in `dist/` written.

## Predictions

- **C0 (instrument alive).** Some fontconfig debug output arrives (a `Loading config file`, `Scanning file` or `Match` line). If not, the run says nothing about fontconfig (stdout from the engine's thread may not be forwarded); stop and record that.
- **C1 (positive control on layout).** In this run, `TW-TC` pitch 20 and `TW-SIYUAN` pitch 15-16 on both profiles (113's numbers, FC_DEBUG must not change layout). A miss: the debug run is not the same layout as the measured one.
- **C2 (the question).** Exactly one of these readings holds for the `思源黑體` lookups made while the fixture opens; I do not know which, so this lists what each means instead of guessing one:
  - **R-a: no `Match` block requests family `思源黑體`.** The pre-match hook is not reached on WASM (or not with that name); look upstream of `PrintFontManager::Substitute`.
  - **R-b: a `Match` block requests `思源黑體` but its `lang` has no `zh-tw`** (only a default such as `en`). LibreOffice's pattern lost the language on WASM (`mapToFontConfigLangTag` or the font's `meLanguage`); the Latin answer then follows from the config, as the native bare/`lang=en` rows show.
  - **R-c: the pattern has `zh-tw` and the best match is a Liberation font.** fontconfig itself scores differently on WASM; the scan lines and the matched fonts' `lang` show whether the CJK faces were scanned with a CJK langset.
  - **R-d: the best match is a Noto Sans CJK face.** fontconfig answers correctly and LibreOffice drops the answer afterwards (`findFontFileID` / family-name mapping in `Substitute`, or `ImplFindFontFamilyBySearchName` on the returned name).
- **C3 (config).** Recorded, not predicted: which config files load (`/instdir/share/fontconfig/fonts.conf`, conf.d), and any `Fontconfig error` line on stderr.
