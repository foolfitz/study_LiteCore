## 7. DECISIONS

Each is open until the main session (or the owner) rules; the arm texts above use the recommendation and say so.

Spec points that force these decisions (the spec is pinned; these are for the main session's appended corrections, not edits): §12.1 names X05–X07 and `M8-utf16le.bin` but not X15–X17, and its "直接對引擎送" has no shipped carrier for raw bytes (DM-3); M3's "M0 判非 PASS 的每一項" includes X14, which only injection makes non-PASS (DM-4); §11 M1 takes C1 (scan PASS) although §9.6 routed it to M7, and five PASS items have no native reference (DM-5); M3 and M4 name `MARKDOWN_NEEDS_CARET` for ranges, which the dialog never receives because the page refuses first (DM-7); M3 asks for `recovery: none` on a route without a session (DM-8); M3's "Undo 不變" has no reader on the shipped configuration (DM-9); M5's positive control does not show that a request from the engine's pthread would be captured (DM-12); M6's "記下 `CORE_LOG`" is not observable through the shipped worker, and its fallback re-run needs a 16 KiB corpus, not the 64 KiB one (DM-13, DM-14); M11's autosave cannot fire on the no-host page (DM-18); §10.2's premise for M10b/c (that the cache sees a selected image) is unmeasured, and the engine reads no `GRAPHIC_SELECTION` (M10 prediction, DM-17).

- **DM-1 — how the runner reaches "the page's SDK object" (M3 R-sdk, M4/M10 ranges, M8, M9, M11).** The page publishes no handle, by convention ("the product page deliberately publishes no handle" [source `tools/run_e2_c_product_path.py:791`]). A: I-3, a module hook importing the same module URLs and capturing the session through a pass-through prototype wrapper; no served product byte changes (only the HTML, which already carries the observer). B: the observer creates its own `DocumentEngine` from the same module — a second engine and worker in the page, not the page's object. C: no direct-SDK route; M3's second route is then not done and M3 takes its default. **Recommend A** (evidence: the page imports by stable relative URLs [source `web/e2-editor-app.js:29-31`]; `offersPasteMarkdown` is called on every state update [source `:1208-1212`]); its positive control is in I-3.
- **DM-2 — how text gets into the dialog's textarea, and items it cannot carry.** A: real clipboard + trusted Ctrl+V (I-4), the path §4.2 A describes and that both browsers executed on 2026-10-14 [observed `findings/evidence/paste-latency/README.md:30-31`]. B: CDP `Input.insertText` (Chrome, used in `tools/check_m3_new_document.py:397`) and WebDriver Element Send Keys (Firefox). C: setting `value` and dispatching `input` (synthetic; excluded by the brief). **Recommend A**, every instance gated by the textarea read-back (length and sha256). For items the browser's clipboard does not carry intact (candidates: `X01–X04` with U+0000; whether Chrome or Firefox keeps a NUL through the clipboard is not known [inferred]): A1 the dialog cell is registered "not representable through the dialog" with the read-back as evidence and M3 judges that item on R-sdk only; A2 the cell is not done and takes M3's default. Recommend A1 (the product cannot receive such text either).
- **DM-3 — §12.1's "direct to the engine" for raw bytes (`X05–X07`, `X15–X17`, `M8-utf16le.bin`).** Fact: no shipped message carries raw bytes; the worker refuses a non-string and `TextEncoder`-encodes a string, which never yields invalid UTF-8 [source `sdk/sdk-worker.js:23`, `:579-581`, `:1484-1497`]. §12.1 names X05–X07 and `M8-utf16le.bin` but not X15–X17, which are equally invalid UTF-8 [observed fixture]. A: an instrumented worker in the mirror only, both browsers, adding one message that passes an `ArrayBuffer` through the worker's own `accept`/`withWasmBytes`/`callStatus` [source `:544-600`] to `oxsdk_document_paste_markdown`; reports `instrumentedWorker: true`, judged on the engine's reply, with the wasm identity binding; positive control: M2's bytes through the same message complete.
