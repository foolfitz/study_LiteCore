# Ruling 4 (v22): the engine thread's stack size, and STACK_OVERFLOW_CHECK

Judge: fable (external), 2026-10-19. Read-only: files read, `python3 -I` over the three JSON reports, `git show`; no browser, no make, no link, nothing written. Brief: `findings/evidence/link-batch-v22/review/brief-fable-4-stack.md` (`d7b7d392`). `CLAUDE.md` 「驗收判準的形式」 §1–§11 read first.

## 1. 裁決（白話，給擁有者）

兩題都裁了。**第一題選 A：v22 的 pthread 預設堆疊設 1,048,576（1 MiB）。** 理由有三條腿，不是只有「8 倍保險」：今天量到的 Writer 長段落需要的是 64 KiB 以上、128 KiB 以下，到 112 頁都沒再長；可是 10 月 13 日 finding 089 已經在 writer+calc 的 v12 上量過**另一條**遞迴路徑（Calc 開 ODS），那一條 64 KiB 壞、256 KiB 才開始好、128 KiB 沒試，所以 256 KiB（選項 B）剛好踩在那條路徑的最低過關階上，沒有餘裕；而 LibreOffice 自己的執行緒程式碼在必須選數字的平台上選的就是 1 MiB（macOS，註解寫「512 KB 不夠」）。記憶體不用先量：堆疊是從固定 1 GB 的 heap 用 malloc 配的，執行緒池 7 條 × 1 MiB 是 7 MiB（0.7%），而 089 實測開 ODT 只啟動 3 條 pthread、開 ODS 7 條，當時 heap 用到約 277 MiB，8 MiB × 7 的極端組也沒出現配置失敗。**第二題選 A：v22 不開 STACK_OVERFLOW_CHECK**，登錄為具名限制 L-153-no-overflow-check——原因不只是「一次一個變因」：等級 1 只在執行緒的進入函式**回傳時**檢查 cookie，我們的引擎執行緒是永遠不回傳的迴圈，開了等於沒開；真正有用的是等級 2，但它要在 110 MiB 的 wasm 裡每個函式都插檢查，代價沒量過。簡報漏了 finding 089 和規格 §11／§12.6 早就登錄的這個問題，v22 規格必須把它們接起來，並把 153 已經找到 Writer 失敗後再也成立不了的 L-writer-stack-64k 那條掃描撤掉。連結之前還要量的東西：**沒有**；Firefox 與 N=3 本來就是判準 1，在連結後的真品上跑。

## 2. Answers (English)

### Q1. Stack size, its reason, and the memory cost

**Value: `-sDEFAULT_PTHREAD_STACK_SIZE=1048576` (option A). `-sSTACK_SIZE=131072`, `-sPTHREAD_POOL_SIZE=7`, `-sPTHREAD_POOL_SIZE_STRICT=0`, `-sTOTAL_MEMORY=1GB`, `-sASSERTIONS=0` unchanged** (`wasm_sdk_probe/Makefile:846-849`).

The reason, as finding 153 criterion 2 requires it (a measured depth *and* a native setting; the spec must carry all three legs, not only the first):

1. **Measured need on the Writer path (finding 153):** more than 64 KiB and at most 128 KiB, flat to 112 pages. `findings/evidence/link-batch-v22/stack-size/bisect1.log` (65,536: crash / hang / crash / ok-then-crash; 131,072–1,048,576: ok on all four), `headroom1.log` (12/12 ok from 131,072), `opentype1.log` (65,536 hangs on the 28-page open-and-type; 131,072–1,048,576 ok on 28/56/112 pages). Every report: `identityOk: true`, `counterfactual.stackBytes` equals the page's N, `probeWasmUntouched: true`, Chrome/151.0.7922.169, `counted: false` (read with `python3 -I` from `report-bisect1.json`, `report-headroom1.json`, `report-opentype1.json`). 1 MiB is 8× the top of this bracket.
2. **Measured need on a second, independent recursion path (finding 089, 2026-10-13, Calc open on writer+calc `e2-editor-v12`, the same link flag):** 65,536 fails (crash / timeout), **262,144 is the lowest rung that opens the stuck files 3/3**, 1,048,576 and 8,388,608 also 3/3, 32,768 is the red case; **131,072 was not tried** (`findings/089-…md` section 「堆疊臂：O-S」, the table under it; `findings/evidence/089/stack-arms-2026-10-13/README.md:29-45`). So 089's need is in (64 KiB, 256 KiB]. Option B (256 KiB) sits on that path's lowest passing rung with no margin; option C has 2×; **1 MiB has 4×**, so the value chosen now also covers the W8 (writer+calc) core without a second stack relink. 089 is not in the writer-only product today (`ScDocShell` 0 in I1, `specs/SPEC-M3-link-batch-v21.md:390`), but the flag is one flag for every product link.
3. **Native setting:** LibreOffice's own thread code sets an explicit stack where it must choose: **1 MiB on macOS** with the comment that the platform's 512 KB "is not enough" (`libreoffice-26-8/sal/osl/unx/thread.cxx:283`), 256 KiB on OpenBSD (`:279`), 12 MiB for non-optimized Linux (`:281`); the Emscripten build is outside that `#if` (`:258-290`), so every LO thread, not only the engine thread, gets the link's default. On optimized Linux it inherits glibc's default (8 MiB typical). 1 MiB is therefore LO's own smallest "enough" on a mainstream platform, 1/8 of the Linux default, and the counterfactual's value, which carries the largest body of observations (153 step 8/9: 8/8 and 2/2; today 4+3+3; 089 S2 3 runs on v12).

**Memory cost: settled by arithmetic plus two existing measurements; no new measurement is a precondition of the link.**

4. Each thread's stack is `emscripten_builtin_malloc`ed from the wasm heap at `pthread_create`, not at pool spawn (`wasm-lite/tools/emsdk/upstream/emscripten/system/lib/pthread/pthread_create.c:135-161`; emsdk `4.0.10` per `emscripten-version.txt`). The heap is fixed: `-sTOTAL_MEMORY=1GB` with `ALLOW_MEMORY_GROWTH` at its default `false` (`src/settings.js:217`). So 1 MiB per *live* pthread, freed at exit.
5. Pool 7 → **7 MiB nominal (0.68 % of 1 GiB)**; synchronous creation beyond the 7 pool workers is impossible, so 7 is also the practical ceiling of threads that can be running. The brief's F4 arithmetic is correct (0.875 / 1.75 / 3.5 / 7 MiB; 0.085–0.68 %).
6. The only measured pthread start counts in this project: **3 per ODT open, 7 per ODS open** on v12 (`stack-arms-2026-10-13/README.md:29-45`, identical across 10 runs); the measured heap top at document load on v12: `sbrk` 290,066,432 of `heapBytes` 1,073,741,824 (`README.md:47`), i.e. about 277 MiB used, 700+ MiB free; and at 8 MiB × 7 (S3) no allocation-failure shape appeared (finding 089 「堆疊臂」, "S3 的啟動數與 S0 相同"). On the writer-only ODT path the expected cost is therefore about 3 MiB.
7. A live count on v22 is a **shakedown item, recorded, no pass condition**, and only if an instrument exists that does not touch a bound byte (the 089 echo patches the loader, which is one of the five bound files; ruling-6 cond. 52 gives the diag-copy shape). Default if not counted: the spec cites v12's 3/7 and says "not counted on v22". The heap actually used is not measurable on the shipped artifact without an export; do not add one (it would be a second variable).

### Q2. STACK_OVERFLOW_CHECK

**Off in v22 (option A). Registered as the named limit `L-153-no-overflow-check`.** The cost criterion 3 asks for, both directions, written for the spec:

8. **What "off" costs:** a stack overflow on any thread is undetected; the shadow stack runs downward into the thread's own `struct pthread` (`pthread_create.c:141-152`) and shows as an out-of-bounds trap, a parked hang, or a late `std::terminate` (finding 153's three shapes). No diagnostic names it. This is the state 0.2.24 and 0.2.26 shipped with.
9. **What level 1 would buy here: nearly nothing.** It writes two cookie words at the stack end at thread start (`src/lib/libpthread.js:1004-1007`, `src/runtime_stack_check.js`) and checks them at runtime init (`src/preamble.js:154-155`), after `run` (`src/postamble.js:227-228`), in `$handleException` (`src/lib/libcore.js:1991-1992`) and **when the thread's entry point returns** (`libpthread.js:1055-1058`; settings.js:61-63 "checked at end of each tick and at exit"). The engine thread is `std::thread(engineLoop, …).detach()` (`wasm_sdk_probe/src/probe_engine.cpp:6956`, the `#else` of `OXSDK_MAINLOOP_ENGINE`, which v21's object rule does not define, `Makefile:1655-1660`), a loop that never returns and takes no JS ticks, so its cookie is never checked while it lives. Level 1 still changes the loader and adds four `REQUIRED_EXPORTS` (`tools/link.py:1208-1222`): a second variable for no measured benefit.
10. **What level 2 would buy:** `--check-stack-overflow` in wasm-emscripten-finalize (`tools/emscripten.py:508-509`) instruments every stack-pointer assignment and calls `__handle_stack_overflow`, which aborts with the requested SP and the limits (`libcore.js:1671-1680`; per-thread limits set in `libpthread.js:995-999`). That would turn a 153-class failure into one deterministic, addressed abort: diagnosable, still an engine death for the user. **Its cost is unmeasured:** code size on a 115,314,060-byte `probe.wasm` (`dist/profiles/e2-editor-v21/probe.wasm`), speed ("small", settings.js:64-65), plus `CHECK_NULL_WRITES` (settings.js:69-74). Upstream LO's own wasm ships level 1 only (ASSERTIONS=1, `libreoffice-26-8/solenv/gbuild/platform/EMSCRIPTEN_INTEL_GCC.mk:29-30`).
11. **Default if never revisited:** `STACK_OVERFLOW_CHECK` stays 0 in every later product link; the limit stays in every release text. **Work item (not a gate):** the next time the owner links a *diagnostic* (non-shipped) artifact anyway (precedents `build/e2/preguard-profiling`, `build/e2/wait-diagnostic`), add `-sSTACK_OVERFLOW_CHECK=2` to that link and record `probe.wasm` size and the open / C2 typing times against the same-tree product link; the decision for v23+ is made from those two numbers, in a ruling. If never measured: stays off. The brief's option B must be read as level 2; option A/B as written does not name the level.
