## RULING

**S, then A only if S fails, then C. B is refused for now. Q2: no registry arm; record.**

1. **The pthread-stack arm (hypothesis H-S, Amendment 3) runs first, now.** It needs no link and touches no product byte: the instrument exists (`--pthread-stack-size`, commit `90fed9b7`), it patches one anchored literal in the scratch mirror's `probe.js`, and every started pthread echoes the stack size it actually received. It is a test of a named mechanism with a bidirectional, pre-registrable prediction; the brief's option A is only a characterisation. Its design is sound subject to the confounds handled in conditions 3–8 (fixed 1 GB memory with no growth; the main runtime thread's stack is not varied; thread starts must be counted; the shrink direction needs a boot gate).
2. **A (the index-only `Debugger.pause` probe on v12) is deferred behind S** and runs only on outcome O-S-N or O-S-partial (condition 9). On O-S it is not run: the switch is then attributed without any stack, and naming the overflowing frame is an upstream-report nicety that waits for a names-carrying artifact, not a gate item.
3. **B (asking the owner now for a `--profiling-funcs` twin) is refused.** Track 2 is defined by the owner as "needs no link"; the owner's link attention is on the Track 1 spec; no Makefile rule exists for a names twin of the a11y core (F6), and a Makefile edit stales every `.o` (finding 042), so that edit belongs in a sitting that already touches the Makefile. The twin is raised at all only on outcome O-A-WASM of A (condition 10), as a `build/`-only guarded target folded into the owner's next link sitting, whichever comes first — Track 1's link or W8.
4. **Q2: no registry-override arm now.** NU-089-3 stays recorded as "measured, unexplained". The brief's source reading is partly wrong (fact check, Q2): E1 does construct the configuration listener, through `ScTokenArray::ResetVectorState()`, so "all three `SC_*` arms skip the listener" does not hold and the listener cannot be the common factor. A registry arm would need a new instrument mechanism (an `.xcu` written into the Emscripten FS before LOK init, or a repackaged hash-bound `.data` pack); the crash is confined to derived fixtures (the 306-record sweep carries `workerCrashed: true` on 0 records; the manifest's original times out rather than crashes), so it does not block G2 by itself; and the S arm's own predictions already cover the crash (condition 5). If S gives O-S, the `SC_*` crash distribution gets a measurable candidate explanation for free (different code path, different depth); if S gives O-S-N, the crash stays "recorded alongside", as Amendment 2 already has it.

**Default conclusions if nothing below is ever run:** 089 stays unattributed; H-S is a source reading and may not be quoted as a cause; the brief's option D order (A, then C) applies; G2 stays blocked by this entry.

## WHY (for the owner)

這一張單子查了四十天，到今天為止能用環境變數關掉的四種執行緒都證明不是開關，剩下的路本來只有「請你再連結一份帶函式名的診斷版」或「不連結、只看得到編號的堆疊」。但你指到的 Collabora 原始碼點出一個更便宜、也更有力的假說：我們的引擎跑在一條 pthread 上，而每條 pthread 的堆疊只有 64 KB（原生是 8 MB），而且這顆 build 沒有堆疊溢位檢查——溢位會悄悄踩壞旁邊的記憶體，這跟「原生 1.4 秒、WASM 永遠不回來、旁邊幾個尺寸的 worker 死於 memory access out of bounds」的形狀吻合。這個數字是以字面量塞在 probe.js 裡的，所以不用連結、不動產品檔，只改 scratch 鏡像那一份就能把它調大調小，而且每條執行緒會回報自己實際拿到多少，工具已經寫好、等值檢查也過了。所以我的裁決是：先跑這一臂（兩個方向、加上一道尺寸階梯），它若成立，089 的開關就找到了，不需要你連結任何東西；它若不成立，才去跑那支只看編號的暫停探針；只有連那個都說不清，才在你下一次本來就要連結的場次順便加一份帶名字的診斷版。NU-089-3 那個崩潰暫時只登錄不另開臂，因為它只出現在我們自己切出來的 fixture 上，不擋 G2，而且這一臂的預測本來就包含「崩潰會不會消失」。
