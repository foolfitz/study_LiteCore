## The three answers

### Q1 — the unit is **output-device pixels**, and the device is **96 DPI**

The runbook's reading (`CoreToPixel` → `LogicToPixel(rect, MapTwip)`) is
confirmed. The competing "1/100 mm from general UNO convention" answer is out
by a factor of 26.5.

| | |
| --- | --- |
| measured ratio `raw / twips` over the document span | **0.0666764** |
| `dpi / 1440` if the unit is pixels | 0.0666667 — **0.015% away** |
| 1.0 if the unit is twips | 15× away |
| `2540/1440 = 1.7639` if the unit is 1/100 mm | 26.5× away |

The DPI is not assumed. Three independent reads, **all agreeing**:

| read | value |
| --- | --- |
| `OutputDevice::GetDPIX()` | 96 |
| `OutputDevice::GetDPIY()` | 96 |
| `LogicToPixel(Size(1440,1440), MapMode(MapUnit::MapTwip))` | 96 × 96 |

`GetDPIScalePercentage()` is 100. This is the **headless svp** device on this
machine; it is a measurement of that device, not a constant of the API, and the
same read has to be repeated on the wasm side rather than carried over
(finding 036's rule).

**The conversion is exact where it matters.** `raw.y × 15 == twipsFresh.y` for
**all 114** paragraphs, byte for byte. Heights differ by up to one pixel's worth
(0 of 114 are exact) — that is `CoreToPixel`'s own `lcl_CorrectRectangle` coarse
snapping showing up in the inverse, and it is a pixel, not a defect.

**The two conversions are the same number here.** `twipsFresh`
(`PixelToLogic(rect, MapMode(MapUnit::MapTwip))`, the runbook's proposal) and
`twipsDevice` (`PixelToLogic(rect, dev->GetMapMode())`, the exact inverse of
`CoreToPixel`) agree on **all 114** paragraphs, because the device's MapMode is
`MapTwip` at origin `(0,0)` with scale `1`. Both were emitted rather than one,
because "they are the same" is a measurement and "they must be the same" would
have been an assumption.

### Q2 — the origin is **document-absolute**

All three registered conditions hold.

- **O-1** — `getAccessibleParent()`'s context is the walk root, by UNO object
  identity, for **all 114** children (and for all 20 probed rows). §2.2's
  premise is now measured, not argued. The tree is flat: two roles only, 26
  (`HEADING`) and 41 (`PARAGRAPH`), no intermediate node.
- **O-2** — converted `y` is strictly increasing across the 20 probed
  paragraphs, 2,340 → 96,240 twips. The window is 7,440 twips tall, so the last
  probed paragraph sits **12.9 window-heights** past the bottom of it. Neither a
  view-relative nor a clamped origin can produce that.
- **O-3** — `getLocationOnScreen() − getBounds().topLeft` is the single constant
  `(0, 64)` px for **all 114** paragraphs. So `getLocationOnScreen()` carries no
  information `getBounds()` does not; the runbook's fallback shape
  ("`getLocationOnScreen()` differencing") is not needed and, on this evidence,
  would measure the same thing with an extra call per paragraph.

One further fact worth stating because it kills the alternative outright: the
**root's own** rectangle is the window, `y` 390..7,816 twips, while paragraph
tops run to 96,780. If paragraph bounds were relative to the root's rectangle,
no paragraph could report a `y` outside that band. Most of them do.

### Q3 — it lines up, and the disagreement is **under one output-device pixel**

20 of 20 rows pass **both** C1 (containment, ±0.5 line) and C2 (top alignment,
±2 lines).

| | twips |
| --- | --- |
| `dTop = caretTop − paraTop`, range over 20 rows | **−14 .. 0** |
| `dBottom = paraBottom − caretBottom`, range | 262 .. 276 |
| line height `caretH` (identical on every row) | 276 |
| `T_contain = 0.5 × caretH` | 138 |
| `T_align = 2 × caretH` | 552 |
| one output-device pixel at 96 DPI | 15 |

The worst disagreement, **14 twips**, is smaller than one device pixel, and
**39.4× inside** the registered tolerance. It is the pixel quantisation of the
round trip, not a systematic offset: it is not constant, it walks between 0 and
−14 across the document, and it is always negative or zero (the paragraph's
converted top is never *below* the caret), which is what a floor-then-snap
round trip produces.

**No paragraph-spacing bias appeared.** The acceptance registered, in advance,
that a constant bias would still be a FAIL; it did not arise, so that clause was
never exercised. Recording that it was registered and unneeded, rather than
quietly dropping it.

Pairing was double-checked on every row: the paragraph the marker names is also
the one reporting `FOCUSED` — **20 of 20** — and exactly one paragraph matched
each marker. Identification never used a coordinate.

## The red cases

### R-1 (registered in advance) — shifted pairing: **went red, 0 of 20 leaked**

Each row re-judged against the caret of the row ten positions later in document
order. Minimum separation **57 paragraph indices**; every pair fails both C1 and
C2, by 51,000+ twips. Example: `LD-P01-L02`'s bounds against `LD-P04-L02`'s
caret gives `dTop = 51,364` twips against a 552-twip tolerance.

### R-3 (added afterwards, **not** registered, **not** gating) — nearest neighbour: **went red, 0 of 40 leaked**

R-1 separates by tens of thousands of twips, which is easy. R-3 asks the hardest
version of the same question, needing no extra run: each row's caret judged
against the bounds of the paragraphs **immediately before and after** the one it
belongs to. All 40 fail.

**And how they fail is the interesting part.** The paragraph pitch in this
fixture is 540–557 twips and `T_align` is 552, so for the *preceding*
neighbour **C2 passes** (`dTop = 538 ≤ 552`) and only **C1** rejects it. The
acceptance argued for two conditions because C1 alone is too weak (a rectangle
spanning the whole document would satisfy it). The measurement shows **C2 alone
is also too weak**, at the neighbour scale, in a direction the acceptance did
not anticipate. Two conditions were right for a reason better than the one
written down.

### Geometry stability

The full 114-paragraph snapshot taken **before** the first target and **after**

## What this does not establish

- **Nothing about the wasm artifact.** This is core's coordinate space measured
  on a native build. The DPI in particular is this device's; the wasm side's has
  still never been measured, and finding 036 is exactly about not carrying
  numbers across that line.
- **Nothing about cost.** The runbook §7.3's question — what 133
  `getBounds()` calls per state read cost — is untouched. This probe called
  `getBounds()` 114 times per snapshot 22 times and did not time any of it.
- **Nothing about the projection.** Whether a screen reader then scrolls the
  node into view remains phase 3's named limitation.
- **Nothing about empty paragraphs, tables, frames or multi-column layout.** The
  fixture is 114 plain paragraphs and headings on six A4 pages. `getBoundsImpl`
  has a branch for empty preview pages and one for non-root parents; neither was
  reached, and both are named here rather than left to be discovered later.

## Consequence for step 4 (for the owner, not a decision by the drafter)

The runbook's stop rule is **not** triggered: the answer to (3) is "lines up".
The shape option B assumes — read `getBounds()`, convert to twips on the same
OutputDevice, hand it to the page in the space the caret already travels in —
is confirmed on native at sub-pixel agreement, and needs no
`getLocationOnScreen()` differencing.

That is the whole of what step 1 was for. Steps 2 and 3 remain, and step 4 is
the owner's.
