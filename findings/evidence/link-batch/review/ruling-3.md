## RULING

### Q1 — two more completions before their own flush (COUNTEREXAMPLE): accepted

Confirmed in source. (A) Every `startEditorUnoAction` completion (`probe_engine.cpp:4284-4316`: delete-selection at `:5352`, insert-paragraph/line-break, undo, redo, the four inline formats) serialises its state on `LOK_CALLBACK_UNO_COMMAND_RESULT` (`:2742-2797`). The dispatch is synchronous when a listener is attached (`sfx2/source/control/unoctitm.cxx:655-657`), the result is queued by `dispatchFinished` (`desktop/source/lib/init.cxx:5106`), and the flush's updated types are appended only when the flush runs (`init.cxx:2485-2486`), so the completion precedes its own `SEL0` or changed rectangles. (B) The product's select-range waits on `TEXT_SELECTION` (`:5555`) and issues RESET, START and END as three separate LOK calls (`:5577-5625`); RESET's `SEL0` can complete it before START and END run.

- L-extend-prior-flush's population is **defined by the model test's printout**, not by §10.1's prose. §10.1's two members become examples. The LOK model in `tests/merge_key_undo_model_test.cpp` gains the two event shapes: a command result queued ahead of the same flush's SEL/CUR, and a multi-call synchronous selection with a flush between the calls. The readback member is modelled as "a completion by deadline with the flush still queued", not tied to the 250 ms constant.
- **Correction to ruling 2 / §10.1:** the effect of a stale extend completion is not only a stale reply. If a delete follows it, the delete's K1 can stack on the extend's still-pending key (Q2). §10.1's 「文件不會被改錯」 is struck; the effect is written as in Q2 below.

### Q2 — a pending extend stacks under the barrier's K1 (COUNTEREXAMPLE, data-changing): accepted; remedy (i′), a flagged delete

**Confirmed in source.** The anchor fence is consulted only for a MergeKey unit (`verifyAndDispatchSelectionBarrierDelete` → `classifyUnit` → `startMergeKeyUndo` → `fenceHolds()`, `:3792-3807`, `:3602-3611`). A Barrier-class unit takes `geometrySafe`/`textSafe` (one rectangle, ≤128 bytes, no separator, `:3809-3818`) and then `.uno:SwBackspace`/`.uno:Delete` on whatever core has selected (`:3836-3840`). The barrier's start precondition is `readSelection()` NONE plus a collapsed cache (`:4004-4011`); it cannot see a posted key that has not run. An extend answered by the 250 ms readback (`:5499-5502`, `:2300-2330`) is reported from the cache, "collapsed". K1 is posted behind the pending extend key (FIFO: keys `lokhelper.cxx:1291`, flushes `init.cxx:2577-2581`); both run before one flush; K1's selection holds two units; the barrier deletes both. Writer deletes one.

**Reachable today without extends? No.** A plain Left answered by readback, then Backspace: Left moves X→X−1, K1 selects [X−2, X−1], the barrier deletes that one character, which is what Writer does for "Left, Backspace". For a MergeKey unit the stale P (X) against K1's anchor (X−1) fails the fence → `anchor-mismatch` → reopen (safe direction). The hazard is specific to a pending **extend**, because K1 then extends an existing selection, and the fence holds (anchor END = X = P) exactly in that case. The main session's reading is right. Also confirmed: in the opposite direction (Shift+Right pending, then Backspace) the two keys cancel, the flush is empty-to-empty (F1), no callback arrives, and §10.5 would complete a mid-paragraph `verified-boundary-noop` that C1 cannot distinguish from a boundary.

**Why the listed candidates are not taken.**
- (ii) Waiting `MergeStepDeadlineMs` before an extend's readback only lengthens the tolerated stall (250 → 2,250 ms); it closes nothing, and it costs 2.25 s on every genuinely silent extend (Shift+End at a line end, Shift+Home at a line start, the ten native-silent cells), which are everyday keys.
- (iii) Refusing to dispatch a delete behind a readback-completed extend until the next push waits forever when the extend was a true no-op, and refusing it outright would refuse "Shift+End at the line end, Backspace".
- (iv) The owner asked for Shift+Arrow by name.
- The review's (a) (Barrier-class refused only when K1's selection arrives after the first 250 ms) does not close it either: the core can resume within 250 ms of K1 and the same two-unit selection arrives inside today's band.
- (i) as asked ("one Writer unit" in general) cannot be defined in the engine without a hand list of grapheme shapes. It is not needed in general: the hazard exists only while a posted extend may still be pending, and the engine knows exactly when that is.

**Adopted: (i′), the flagged delete.** The engine keeps one per-document flag, `extendUnconfirmed`:
- **Set** when an extend completes by readback (`verified-move-readback` on an `extendSelection` action). Not for plain moves, clicks or select-range: a pending plain move or click stacks Writer-equivalently (above), and select-range is synchronous.
- **Cleared** only by evidence that the core has run every key posted before it: a later extend or range-start move completing under rule (a) (a differing `TEXT_SELECTION` then a cursor), or a flagged delete completing with proof (below). A caret-start plain move's first-cursor completion does not clear it (that cursor is forgeable, §16.1). Cleared on close and on a new worker.
- **Effect while set**, on the next delete:
  - `delete-selection` is refused before dispatch (`.uno:Delete` runs synchronously under the SolarMutex and jumps every posted key, `:5352`; on a pending extend it deletes the wrong range). Refusal code `EDITOR_BOUNDARY_UNSUPPORTED`, new stage `prior-key-unconfirmed`, `keyPosted:false`; the page reopens as for every boundary refusal.
  - `delete-backward`/`delete-forward` through the barrier: a Barrier-class unit is accepted only if K1's selected text is **exactly one code point**; otherwise refused with the same stage. A MergeKey unit keeps the fence plus K2's text check, which already catches the stacked case (K2 selects one unit, K1 held two → `return-mismatch`, `:3643-3657`).
  - At §10.5's window expiry a flagged delete never completes as `verified-boundary-noop`; it refuses with the same stage (the cancelled-pair case).
- Everyday sequences are unaffected: "Shift+End at the line end, Backspace" is flagged, K1 selects one character (one code point for Latin, CJK, Bopomofo), the delete proceeds. The cost is named **L-flagged-delete-grapheme**: after a silent extend, a Backspace over a multi-code-point grapheme (combining marks, ZWJ emoji, variation selectors) or a `delete-selection` is refused and reopens; the typed text is kept (109's checkpoint). The refusal is in the safe direction, which is this tree's rule for every barrier exit.
- **Criterion (form 1, model test):** the LOK model gains "an extend key still queued when K1 is posted" (same direction, opposite direction, from a range) and "a delete-selection dispatched with an extend key queued". The rule must refuse every such sequence; it must never produce a `verified-selection-delete` of more than one unit, a `.uno:Delete` on a range other than the dispatch's, or a `verified-boundary-noop` with a key pending; and it must still delete in the Writer-equivalent plain-move stacking and in the "silent extend, then one-character Backspace" sequences (liveness). Red cases: remove the flag → the model prints the two-unit delete and the silent no-op; apply the one-code-point rule unflagged → the model refuses a multi-code-point unit with nothing pending. On WASM the stall is not inducible in an honest run (the review's reading is right): named, not tested; the model is the evidence.
- **Residual, stated honestly:** a *forged* rule-(a) completion (L-extend-prior-flush) leaves the extend's key pending without setting the flag, and a delete behind it can stack the same way. This needs three coincidences: a completion-before-flush operation immediately before the extend, the core thread lagging a full page round trip, and a delete at once. It is a possible wrong deletion by one unit, printed by the model as part of L-extend-prior-flush's population. Two closures are registered for the owner, neither taken in this link: applying the one-code-point rule unflagged (closes it; refuses every multi-code-point grapheme delete, a functional regression whose frequency in the owner's documents is unmeasured), or a FIFO marker event after each posted key (needs a §16.1-style forgery analysis and a native measurement first).
- §10.5's sentence "a late K1 is the same K1 with the same proof" is corrected: true for a MergeKey unit (fence plus K2), not for a Barrier-class unit, whose only proof in the hazardous state is the flag's one-code-point rule.

### Q4 — rule A's home, two-key sequences, S5's oracle (COUNTEREXAMPLE + SHOULD): accepted, with a correction to the review's mechanism

- **Rule A moves into the run-time resolver, keyed on the queue:** if the item that ran immediately before this delete was a delete (any form), the delete uses its own key's collapsed form; otherwise the session's snapshot. Sequence A ("Backspace, Shift+Left, Backspace") then reads the extend's fresh completion and sends `delete-selection`, as Writer does. Sequence B ("range, Backspace, Backspace") sends `delete-backward` as today.
- **Correction to review Q4, sequence B:** the gate reads the **cache** (`:5285-5300`), not core. With `delete-selection`'s `SEL0` still undelivered the cache says "range", so a `delete-selection` chosen from the snapshot would **pass** the gate and `.uno:Delete` (`:5352`) would run on an already-collapsed caret: a silent forward deletion of one character, not a refusal. The resolver rule is therefore a data-safety requirement, not only a UX fix. With it, the stale-cache case yields at worst a gesture refusal of `delete-backward` (a toast, nothing dispatched), which is today's behaviour and 131 §9.16's registered NOT_ESTABLISHED cell.
- **S5 gains two-key sequences, tool-closed:** for each of Table 1's 84 cells, in addition to the three one-key follow-ups: (i) the same delete key pressed twice, and (ii) one delete key before the Shift+key, each with no waits; Writer's references from the native tool as now. The "range, Backspace, Backspace" shape is covered by (i) on the range-start cells.
- **S5's oracle:** the delete arms compare `content.xml` after SPEC-M3-paragraph-merge §24's `reduce_content` (namespace order, empty `office:forms`, `soft-page-break`; `:773-796`), not raw bytes; the typed arm keeps §12's paragraph-text comparator. §10.3's layout split applies: native reference for Left/Right and single-line Home/End; for the other cells the reference is the same cell on WASM with a settled wait before the follow-up (fresh arm). **Positive control:** the runner records, per cell, the page's count of moves and extends in flight at the follow-up's `beforeinput` (S-12's counter); the overlap claim is made only over cells where it is > 0, with an empty set failing; the non-overlapped cells are still judged as sequences and reported separately.
- Q2's stall path is named, not tested, in S5.

## WHY (for the owner)

審核找到一個會改錯文件的洞：Shift＋方向鍵若因核心停頓 250 毫秒而被引擎當成「沒變」，緊接著的 Backspace 會疊在那一鍵上，多刪一個字。這一鍵改成由引擎記住「上一個延伸還沒被核心確認」，在這個狀態下接著的刪除只接受恰好一個字元的單位、不接受刪整段選取、也不會把「沒選到東西」當成成功，其餘一律拒絕並重開，打過的字照舊保住。日常的「Shift＋End 在行尾、再按 Backspace」不受影響，會被擋的只有組合字元和表情符號這類多碼位的字，而且只在上一個延伸沒被確認時。不把 Shift＋方向鍵拿掉，因為那是你點名要的；也不讓每個沒變的延伸多等兩秒，因為那只縮小洞、關不掉，還拖慢每天都在按的鍵。還剩一個更小的殘留（要三件巧合同時發生），我把它寫明是可能多刪一個字，模型測試會把它印出來；兩個能關掉它的做法都登錄給你選，這一批不做。刪除形式的規則搬到佇列執行時決定，因為審核以為引擎會擋下的那一種情況，其實引擎會放行並向前多刪一個字。頁碼的計數器改成每次回呼都加、而且自己推送，驗它的那一臂必須是「這次變化沒有游標一起到」，做不出來就登錄為沒有儀器。64 KB 的執行緒堆疊這一批不動，但在換核心之前先用不連結的鏡像補丁把 Writer 的產品路徑在 64 KB 與 256 KB 各跑一次。規格不再審第三輪，新機制交給本來就要做的引擎碼審核，兩個問題先寫好。
