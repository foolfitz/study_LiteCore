# wedge-thread-state — 卡住的執行緒是在空轉還是在等？

「呼叫不返回」有兩種，修法與下一步完全不同：

- **空轉**：執行緒在跑，只是跑在一個不會結束的迴圈裡。CPU profile 取得到樣本，
  而一個保留函式名的 build 就能把那個迴圈**指名**。
- **停等**：執行緒停在鎖／futex／wait 上。CPU profile **完全取不到樣本**，
  再怎麼 profile 也不會多說一個字，問題要改成「它在等什麼」。

Chrome 的 CPU profiler 不必重編就能分辨這兩件事，所以這一輪排在「跟使用者要一個 build」之前。

## 結果

**停等，不是空轉。**

| | 控制組（同一輪、卡死之前） | 卡死當下 |
|---|---|---|
| worker 0,1,2,3,7 | parked（`(idle)` 佔滿） | parked（`(idle)` 佔滿） |
| worker 4,5,6 | **`wasm-function[36295]` 100%** | **`wasm-function[36295]` 100%** |

**兩欄一模一樣。** 卡死當下沒有任何一條執行緒多做任何事。

`wasm-function[36295]` 三條執行緒各佔 100%——**在卡死之前就是這樣了**，
所以那是這個 build 裡某個 thread pool 的常態忙等，不是卡點。

## 為什麼一定要有控制組

第一輪沒有控制組，讀起來就是「三條執行緒在 `wasm-function[36295]` 裡空轉」，
而那正好是一句很好聽、很像結論的話——**差一點就送上游了**。
控制組（同一輪、同一批 worker、卡死之前）一跑，那三條在控制組裡也是 100%。

順帶還修了一個更基本的錯：初版把 V8 的 `(idle)` 偽框當成樣本在計，
於是**每一條停等的執行緒都會被判成「spinning」**——一個兩種答案都會通過的判準。

## 這對下一步的意義

**不要為了「指名那個迴圈」去重編一個帶 `--profiling-funcs` 的 build**——沒有迴圈。
下一個問題是「它在等什麼」，而那要的是別種工具：例如在 proxy 佇列與
`emscripten_futex_wait` 兩側加計數，或從主執行緒那側看誰沒被服務到。
