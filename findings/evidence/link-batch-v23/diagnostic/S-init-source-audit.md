# S-init: bounded source audit before the diagnostic link

Status: **source preparation, not S-init acceptance**. No browser/native execution, build, host action or service change was performed for this audit. The comparison requested by SPEC-M3-ordered-commands section9.2 remains unmeasured. This is a form3 one-time inventory of named routes, not a tool-closed enumeration of every possible initialization dependency.

Core checkout: `libreoffice-26-8`, commit `671c848b1bb81e5b1a90d97675db9a0f3ae2a9cb`. The active Writer link defaults are `wasm_sdk_probe/Makefile:1-2`: that source and `wasm-lite/build-headless-probe`. Engine line references below were read during ongoing v23 source integration; the named functions are the stable locators. The future actual link log and artifact hashes must confirm this selection; an ABI number cannot do that.

## Topology and the scope of the comparison

**Source fact.** `desktop/source/lib/init.cxx:8367-8387` enables RequestHandler without IPC and marks it not ready in both modes. Only non-unipoll starts `lo_startmain` and waits for ready; unipoll calls InitVCL instead. The regular Desktop main path posts OpenClients at `desktop/source/app/app.cxx:1656-1658`. These are distinct paths; merely opening a document successfully does not establish that their initialization effects are equal.

**Source fact.** iOS's explicit SfxApplication creation and Android's bundled-extension registration at `desktop/source/lib/init.cxx:8284-8303` are platform branches, not WASM initialization. Dictionary preloading and extension synchronization at `:7854-7899` belong to preloadData, called inside PRE_INIT at `:8305-8341`. The probe uses `libreofficekit_hook_2` (`probe_engine.cpp`, initializeKit / engine initialization, currently `:7324`, `:7790`), not the separate preinit entrance. Consequently the existence of preloadData in source is not evidence that our worker runs it.

## Dictionaries, extensions, spelling and hyphenation

**Source facts.** `wasm-lite/build-headless-probe/config_host/config_extensions.h:12` has `HAVE_FEATURE_EXTENSIONS 0`. Desktop's synchronization and dependency check at `desktop/source/app/app.cxx:1530-1542` are under that feature guard. Thus the missing Desktop::Main call does not remove an extension-registration operation that this current core would have compiled at that location. By contrast, `config_host/config_wasm_strip.h:8` has `ENABLE_WASM_STRIP_HUNSPELL 0`; `config_host.mk:58` includes HUNSPELL and HYPHEN. Do not translate “extensions disabled” into “no linguistic code”.

The public document SDK and current editor action lists expose no dedicated spelling, dictionary-installation or hyphenation API in the reviewed files (`sdk/document-sdk.d.ts`, `editor-shell-v2/narrow-editor-v2-client.js`, `paragraph-editor-client.js`). This is an observation of these lists, not proof that opening, editing, layout or rendering cannot reach linguistic services. Engine open calls `initializeForRendering(..., "{}")` (`probe_engine.cpp:3516-3517`), without explicitly setting `.uno:SpellOnline`. Writer accepts that rendering property at `sw/source/uibase/uno/unotxdoc.cxx:3936-3937`; background layout uses IsOnlineSpell at `sw/source/core/layout/layact.cxx:2248` and `:2562`. The reviewed engine call therefore leaves the inherited setting relevant.

**One-time metadata observation, not worker-FS measurement.** `dist/profiles/resources/base-r5-no35.1700ed39031eaf49.metadata` has1240 file entries. A case-insensitive filename filter for `dict`, `hyph`, `autocorr`, `extensions` found seven UI files and no dictionary payload in that subset. This is only a search over one resource pack: it neither reads the actual worker mount nor establishes all linguistic resource absence, registered locales or on-demand behavior. No “all dictionaries absent” conclusion follows.

**Inference.** For the current build, a missing extension-registration startup step is not the immediate product regression candidate. Lazy linguistic service/configuration initialization during actual document use still needs a v22 comparison, especially for documents with language and automatic hyphenation properties. Dictionary behavior being equally unavailable is a possible result, not a premise.

## Autocorrection and paragraph insertion

**Source facts.** The actual typing chain is session commitText (`editor-shell-v2/narrow-editor-v2-session.js:1290-1293`) to base commitText (`editor-shell/editor-session.js:511`) to DocumentHandle.insertText (`sdk/document-sdk.js:533`) to handleInsertText (`probe_engine.cpp:3785-3828`). The latter tries plain UTF-8 paste first. If paste returns false, it sends KEYINPUT and KEYUP for each decoded code point and reports `method:"postKeyEvent"`; otherwise it reports `method:"paste"`.

Writer's key handler obtains `SvxAutoCorrCfg::Get()` at `sw/source/uibase/docvw/edtwin.cxx:1661-1669`. Printable triggers can call AutoCorrect at `:2653-2676`; Return can choose AutoFormatByInput or CheckAutoCorrect at `:2018-2030`. This reachable fallback is enough to reject a blanket “no autocorrect usage” claim. `editeng/source/misc/acorrcfg.cxx:695-699` constructs the configuration as a function-local static, and its constructor reads autocorrect paths and scans language files at `:111-138`. These are lazy operations, not proof of runtime equivalence after skipping Desktop::Main.

**Correction to a tempting analogy.** Product `insert-paragraph-break` is not a direct Return key. It calls `.uno:InsertPara` (`probe_engine.cpp:6325`), mapped to FN_INSERT_BREAK (`sw/sdi/swriter.sdi:3624`). That handler calls `rSh.SplitNode()` (`sw/source/uibase/shells/textsh.cxx:206-217`). The declaration defaults `bAutoFormat=false` (`sw/source/uibase/inc/wrtsh.hxx:339`), and AutoFormatBySplitNode is conditional on that parameter (`wrtsh/wrtsh1.cxx:1452-1478`). This specific reviewed path does **not** establish the key handler's automatic-formatting branch. It still deserves a comparison of saved paragraph structure, but should not be labelled an autocorrect positive witness merely because it inserts a paragraph.

**Unmeasured.** Whether any unmodified public input in the bounded fixtures naturally causes paste failure; actual fallback execution; effective autocorrection flags and resources; actual transformations under either profile. A normal paste result cannot establish fallback behavior. A synthetic forced failure may validate instrumentation, but cannot be reported as ordinary product-route observation.

## OpenClients recovery and actual product recovery

**Source facts.** LOK sets the command-line headless flag (`desktop/source/lib/init.cxx:8278-8282`). OpenClients allows recovery/session scanning only when neither no-restore nor headless is set (`desktop/source/app/app.cxx:2047-2053`). On the headless path it instead creates the AutoRecovery service and dispatches `vnd.sun.star.autorecovery:/disableRecovery` (`:2066-2085`). The scan and recovery UI are in the other branch (`:2088-2140`), additionally guarded by `ENABLE_WASM_STRIP_RECOVERYUI`, which is1 in the current config. Thus the regular v22 headless path already excludes this desktop recovery scan. Skipping OpenClients also skips the explicit **disableRecovery side effect**; it is not correct to call the entire difference “nothing”. Whether another path instantiates AutoRecovery and activates timers in v23 is unmeasured here.

Product rollback is a separate implementation: EditorSession retains authority/checkpoint bytes and opens a fresh worker (`editor-shell/editor-session.js:148-180`); restart disposes the old runtime without close, then calls _openFresh (`:587-595`), and disposal terminates the engine (`:605-623`). The probe supplies `file:///tmp/user` to LOK. These source facts support comparing product recovery without pretending it tests desktop recovery-file scanning or all long-lived autosave effects.

## RequestHandler and document opening

**Source facts.** RequestHandler::Enable forces `ipc=false` on Emscripten (`desktop/source/app/officeipcthread.cxx:664-678`). The non-unipoll ready wait described above serves startup synchronization. OpenClients_Impl calls SetReady(true) (`desktop/source/app/app.cxx:1978`); OpenClients enables pending command-line requests at `:2146`, then constructs command-line document requests. The reviewed public worker open path instead calls `oxsdk_document_open` (`sdk/sdk-worker.js:1447-1459`), handleOpen loads through LOK `documentLoad` (`probe_engine.cpp:3468-3495`), and LOK calls XComponentLoader::loadComponentFromURL directly (`desktop/source/lib/init.cxx:2967-2969`).

**Inference.** The reviewed SDK open route bypasses RequestHandler's command-line request queue and IPC. This is not a global proof that every downstream UNO operation is RequestHandler-independent. A cold open followed by operations and a fresh-worker reopen is the minimum behavioral comparison of the route actually offered by this product.

## Concrete post-link comparisons needed for this bounded S-init reading

These specify observations for the already required v22 comparison, not new release-wide populations or a declaration of section9.2 completion. Use actual frozen v22 and the exact owner-linked diagnostic artifact, identical fixture bytes and resource-pack identity, Chrome and Firefox, N=3 as section9.2 prescribes. Record actual state, saved content, callbacks and request errors. Missing discriminating observations remain NE.

1. **Cold open / direct-load / recovery:** open a small deterministic language-tagged Writer fixture, insert a marker, save, dispose and reopen those exact saved bytes in a fresh worker, then save again. Compare paragraph text/structure and successful public operations. Run the existing bounded diagnostic kind1 recovery control for the candidate; compare v22's established fresh-worker checkpoint/restart path without assuming its worker contains the candidate-only private entrance. This measures product recovery/direct loading, not desktop scan or long-duration AutoRecovery timer absence. Record that the headless desktop scan is excluded by the source guards above; keep the skipped disableRecovery side effect explicitly unmeasured unless separately inspected at runtime.
2. **Linguistic document behavior:** open the same language-tagged document with a narrow automatically hyphenated paragraph and both correctly spelled and misspelled words. Capture final page geometry/rendered output, relevant callbacks and saved text on both profiles, with actual effective online-spelling setting/resources if a diagnostic read is available. A visible hyphenation/spell distinction on v22 supplies a positive witness; without one, equal ordinary renders do not establish dictionary availability. If no runtime service/resource read or discriminating v22 behavior is available, keep that part NE rather than asserting unused.
3. **Normal input versus fallback:** on the same empty en-US paragraph, send public insertText strings `teh `, `"word" ` and `1. `, each from a fresh authority document, recording the actual inserted method and saved text; add public insert-paragraph-break and compare saved paragraph structure. This tests the actual paste path when method is paste. Only a naturally observed postKeyEvent method counts for fallback; if none occurs, explicitly retain the fallback/autocorrect dependency as unmeasured. Do not add a new private arbitrary-key entrance just to make the result green. The listed triggers are probes, not assumed locale/config-specific transformations; v22 must demonstrate any claimed positive autocorrect effect.

A source disposition for extension registration / desktop recovery scanning can be recorded now with its compile/headless guards. The remaining lazy linguistic and fallback behavior cannot honestly receive a complete S-init PASS from this source audit. No comparison has been run.

## Exact native FODT bytes and the diagnostic filename

The page now accepts `fixtureName` and the runner offers `--fixture-name`, keeping fixture bytes unchanged. The JS SDK checks only nonempty ArrayBuffer (`sdk/document-sdk.js:418-429`), but the **C public entrance** checks the suffix: `src/sdk_api.cpp:110-128` requires lowercase `.odt` on the Writer branch. A literal `.fodt` name is therefore rejected before LOK; do not mistake it for a core loader failure. To try unchanged native FODT bytes, use an explicit `.odt` loader alias and record both the original fixture SHA and actual alias. Whether LOK content detection accepts those XML bytes under that alias is a required first post-link observation, currently unmeasured. No source whitelist was widened and no XML was repacked for this audit.
