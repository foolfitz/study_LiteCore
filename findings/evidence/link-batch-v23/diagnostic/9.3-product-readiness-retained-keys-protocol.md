## Readiness is a prerequisite, not a performance test

The forcing evidence is `post-link/r2-attempt-01/c2-prep/r2-chrome-gap80/`: exact fetched identity and1400×1000/DPR2 were established, and20 real keys were captured, but document revisions and fresh paints were absent. A ready label, a key event, an existing canvas, or correct fetched bytes alone therefore cannot establish that a product test reached an editable loaded document. Do not use this NE as a product regression or as a v19 pre-red witness.

Before accepting any feature product-path or pre-red cell, establish all of the following on its bound fixture and page graph:

1. Bind the exact profile, manifest, WASM, loader, worker, shell generation, local import graph and executed mirror overrides. Capture browser-fetched identity, actual user agent, source fixture SHA256 and the actual open request bytes/name. A profile label or ABI number alone is insufficient. Use isolated owned browser profiles and the existing lock/CPU guard/cleanup. Hash canonical pages and reject reused pages under different browser/round keys.
2. Match the successful public open terminal to its actual request ID, worker generation and document handle. Capture actual document state and a fixture-specific text/structure witness from a public read or saved document; match that witness to parsed source bytes. An old document handle, a file-input filename or page text alone is insufficient.
3. Record the actual product input element, `document.activeElement`, disabled/readOnly/isConnected state and its associated live document immediately before input. Focus must be the editable product sink. Send browser-native CDP/WebDriver input through the page, preserving actual keydown/repeat/keyup/beforeinput events; synthetic DOM events are not browser product evidence.
4. On a disposable readiness copy of that same fixture, place a known supported text caret, send a literal `Z` through the product input path, and require an attributed public mutation request and successful terminal on that open handle, revision progression, and saved ODT content containing exactly the expected insertion at the known position. A key recorded only in the textarea is not a witness. Record before/after parsed content, not just a success label or screenshot. If fixture placement or saved content cannot establish this, readiness is NE and the cell does not proceed.
5. Reopen the original unchanged fixture for the measured sequence, bind the new open handle/generation and fixture witness again, and establish its specified caret/range using actual returned state/selection. The readiness marker must be absent. Do not run setup mutations in the measured race interval. A save used to prove readiness must not silently become an unrecorded predecessor of the measured sequence.

The readiness mutation is a precondition, not an additional counted behavioral arm or a numeric latency gate. Missing evidence gives NOT_ESTABLISHED, never a successful pre-red. Causal reader controls must remove the open terminal, change its handle, keep a stale fixture witness, focus another element, omit the wire mutation while retaining the key, and leave the saved content unchanged; each must reject readiness. Preserve original reports rather than inventing retrospective sidecars.

Product continuations are dispatched without inserting that readback into the race. Collect their state afterward. S5's nonempty actual overlap set remains its own obligation; do not claim overlap from an artificial sleep or a page busy label.

## Held Shift: two distinct existing obligations

S-12 comes from link-batch section10.4, line223: hold Shift+Right for2seconds; growth after release is bounded by extensions actually in flight at release. The separate three-product-route requirement at lines149–154 contains a1second Shift+Right arm. They must retain different case IDs and durations; neither report substitutes for the other.

The cadence is prescribed by `specs/SPEC-M3-held-key.md:30`; the existing132 scheduling source is `tools/probe_hand_test_0212.py:437–470`: first key at0ms, repeats beginning500ms at30ms intervals, final keyup half an interval after the final scheduled keydown. Its2000ms schedule contains52 downs and releases at2015ms. Its1000ms parameter produces18 downs at0,500..980ms and releases at995ms. Scope explicitly adopts that existing “1second schedule”, including its planned995ms keyup. These are input schedules, not performance thresholds. Record planned and actual key times, actual repeat flags and final keyup; never merely sleep2seconds and call that a hold. Do not round the995ms planned release to1000ms or substitute planned timestamps for actual timestamps. Use the existing browser-native paths with Shift held across the Right events; all actual move wire payloads must carry the public typed extension flag.

Recommendation for a fixed positive text fixture is the existing native `long200.fodt`, whose first paragraph has enough ordinary text for the52-down schedule (`ordered-commands/tool/make_fixtures.py`, first-paragraph text generated by that tool). Start at its first text caret. Pin the bytes and parse the first paragraph before running; require that neither schedule can hit its boundary. The selection's anchor must remain at that caret, each admitted Right extend advances the moving endpoint according to the same-browser public single-step reference, document content/revision remain unchanged, and no recovery occurs. This avoids using layout pixels as a character-count oracle. The release witness must be the latest attributable engine state at/before the release event, plus actual pending identities; a read started after release cannot be backdated to release.

The literal wire-in-flight reading gives `postReleaseGrowth <= number of posted unanswered extension requests at release`; queued or held operations may not be added secretly to its right-hand side. The132 admission depth instead concerns all admitted outstanding work. **Scope has ruled that S-12 uses the strict wire-pending meaning**, with the queued and held sets recorded separately. No arbitrary extra-character tolerance is proposed. If the release endpoint cannot be established without disturbing the run, this observation is NE. If no actual repeats or extension requests occur, it is NE, not a zero-growth pass.

Required causal controls: remove Shift from one wire payload; substitute page selection for the actual release witness; omit a pending request; copy a post-release read into a pre-release slot; admit/dispatch extra work beyond the release bound; remove all repeats. Controls are mutations of the finite evidence, not extra browser populations.

## Retained keys after removal of the old window

The surviving property is conservation and ordering of actual admitted inputs while an operation is outstanding, not a2.25second timer. Existing source `web/e2-editor-app.js:2886–2965` already restricts holding to the same original delete key with no intervening session enqueue, releases earlier held inputs before another enqueue, and discards held inputs only on a standing boundary-noop, failed operation or vanished document. Those rules, plus132's depth2 including held work, remain the semantic baseline. Do not preserve the withdrawn engine window merely to make an old test schedule pass.

Reuse the closed existing page-test member sets from `page-held-deletes.test.mjs`, `page-held-depth.test.mjs` and the141/144/145 tests named by link-batch-v21 section11.1 D8. Enumerate actual test names from those source files, bind their hashes, and compare expected membership; a source member must not disappear through a hand-maintained summary. The18 unflagged press source and52 flagged/unflagged hold source are distinct: unflagged genuine presses in text remain one-for-one, whereas flagged repeated keys are admitted under depth2. Preserve original beforeinput count: releasing a held key must not manufacture another user input event.

For a unit witness, explicitly leave the first fake request unresolved while injecting the existing finite input schedule, then resolve it with the chosen actual completion/state shape. This establishes overlap without inheriting the obsolete2250ms response delay or2500ms ready bound. Test standing boundary-noop (same revision, collapsed selection and identical caret), real deletion, changed-state noop, missing state, rejection, document replacement and another intervening enqueue. Only the standing no-op may discard same-boundary held presses as already answered; rejection/document replacement may discard old-document work but must clear counts. Real deletion releases preserved original keys in order. Do not infer “one request total” for fast real boundary repeats that arrive after an earlier reply; the one-request oracle applies only to presses known to have been held behind that unresolved request.

Keep the existing D8 ordered input families: (a) start Backspace→Ctrl+End→Backspace; (b) start Backspace→Ctrl+Home→18 unflagged Backspaces; (c) start Backspace→Ctrl+End→two Backspaces; (d) start Backspace→click middle→Backspace; (e) in-text Backspace,Backspace→Ctrl+End→Delete. Original held-key direction and order must survive enqueue boundaries. The old≤2 request clause for(b) depends on its outstanding-work schedule: a successor test must prove that schedule, not impose the old window on the faster engine. Any canonical change to that count needs an explicit append, never a silent reader edit.

For the144 positive text hold, preserve the existing after-release deletion bound2 and admission conservation. Do not import the mocked66ms delete service time or≥20 fake-engine deletions as a WASM throughput requirement. ## Counts and closure recommendation

The two held-Shift obligations, the two immediate product sequences, save→move→type, two deletion strings and three L-C positions are ten distinct named input families, not a claim of a new ten-cell gate. The native table/frame memberships, existing product-runner membership and unit-test memberships remain owned by their original source tables. Browser repetitions for the three product routes are explicitly required to be fixed before running, but no existing N is stated in link-batch10.1. Scope now explicitly sets N=3 in each browser for the three product routes and S-12:4 families ×2 browsers ×3 rounds =24 cells, with the2second and1second holds distinct. This is a new prospective choice authorized where the original specification left N open, not a claim that an old N3 existed. Scope separately sets S1–S5 to one execution per source cell per browser; those source populations are owned by the S1–S5 protocol. Do not apply N3 automatically to deletion, L-C or table/frame families. Scope must publish their finite manifest and counts with the unresolved oracle bindings before feature implementation. Missing these remains an open prerequisite, not permission to choose them during execution.

Freeze that protocol and instrument graph before the first qualifying pre-red/count. Existing clean diagnostic cells do not reset. Each new feature cell independently requires readiness and provenance; causal negative controls must reject absence of the defining actual input/oracle. Missing readiness/oracle/identity is NE, clean contradictory behavior is failure, and an existing explicitly limited position remains a limitation. No performance threshold, extra capability grant, or recovered synthetic success may be introduced to turn those outcomes green.
