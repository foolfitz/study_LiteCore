### 2.3 Q3 — Completion and the drain: right in shape, wrong in one clause; the watchdog is a new number in disguise; N1 must be split

- **One command per poll, reply at the next poll: adopted** (draft §5.2). The page's serial queue (`editor-session.js:287-311`) sends one command at a time, so the cost is nil in practice and the inventory's gap (6) (gates reading a pre-flush cache) closes. Form 1: every command's reply is emitted after its call returned and after the tick that ran its flush. Default if N1 never runs: no engine code (as drafted).
- **The draft's poll condition is wrong by half.** `ImplYield` (`svpinst.cxx:440-455`): one user event, then return (`:440-444`); else `CheckTimeout()` runs one scheduler task (`:446-447`); then `if (!bMustSleep && !anyInput()) return` (`:453-455`); only then the poll (`:471-481`). So the poll is reached on a tick with **no user event** AND (**nothing else ran OR the client's `anyInput` is true**). Today's `mainLoopAnyInputCallback` returns `!gState.commands.empty()` (`pe:6845-6851`) — a **pending reply does not count**. On a long document after an edit, Writer's `LOWEST` layout idle runs one slice per tick for many ticks; with `anyInput` false, no poll comes until layout is done, and every reply waits for it — `ReportWhenIdle`'s latency through the back door. **Hard rule (form 1, every tick):** `anyInput` = a command is queued ∨ a reply is pending. Red case: the native harness in two modes (anyInput with/without the pending-reply term) on a 200-paragraph document after a paragraph join — the "without" mode must show the longer first-poll delay (that is its own positive control; equal delays mean no idle layout ran and the arm measured nothing).
- **The poll must not block on WASM.** The mainloop profile waits up to 1 s inside the poll (`pe:6795-6819`); under `emscripten_set_main_loop` that blocks the tick. Rule: on WASM the poll drains at most one command and returns at once; pacing is the 100 fps tick. (Natively the harness may sleep to pace; that is the harness's business.) The re-entrancy guard (`pe:6822-6835`) stays as a belt; ruling 1 §2.8(a)1 makes nested pumping forbidden anyway.
- **Watchdog: no new 5 s.** The 5000 ms constant bounds a **wait for a callback** (`FormatBarrierStageDeadlineMs`, 034's silent paragraph, `pe:1047`); a bound on **how long a synchronous LOK call may run** is a different quantity with the same digits — a new number (CLAUDE.md §4's self-check). A 64 KiB Markdown paste, a save of a long document, a large open can honestly exceed 5 s, and the watchdog's action (new worker) is data loss since the last checkpoint. The SDK already has the bound and the action: request timeout 30 s (`document-sdk.js:160`, `:243`) and the recovery path. **Rule:** the only watchdog is the existing SDK timeout; §9.2 records the longest honest command on the diagnostic (open of the largest fixture, the 64 KiB Markdown paste, save of `long60`), form 1 over the arms' durations ("every honest command completes under the bound"); the red case is a test-build command that never returns, which must reach the recovery path within the bound (the crash path already has `worker-crash-is-never-noticed`; the hang path needs its own diagnostic command). Lowering the bound is a later ruling with the recorded numbers. Default if never measured: 30 s stands; it exists already.
- **N1 (draft §9.1) is over-broad and would go red on its own threshold.** Timer-driven callbacks — `STATE_CHANGED` from `SfxBindings`, `RULER_UPDATE` — arrive after the first poll by construction (they are scheduler tasks, not part of the key's flush); natively 142 measured `STATE_CHANGED` up to ~765 ms after leaving a table and ~300 ms after a range collapse (`142-ctrl-home-end/README.md:20`, `:31`). As written, N1 fails there and the next step would be "widen the window" — the after-the-fact move §9 forbids. Split it:
  - **N1a (hard, form 1):** for every arm and command kind, the callbacks the reply depends on — `INVALIDATE_VISIBLE_CURSOR`, `TEXT_SELECTION(_START/_END)`, `UNO_COMMAND_RESULT`, `INVALIDATE_TILES` — are all delivered by the first poll after return. N = 5. Red case: the synthetic report with one such callback moved after the first poll → red (as drafted).
  - **N1b (record, not a criterion):** per callback type, the delay after the first poll for the timer class. **Positive control the draft lacks:** the table-leave arm must record a non-zero `STATE_CHANGED` delay; zero means the harness does not see late callbacks. Consequence for the spec: no reply field may be fed from the timer-class cache (059's state check, A7 — read the format state directly or keep the html readback); register `L-timer-class-callbacks` in §11.
  - **N1c (hard, form 1):** the anyInput arm above.
  - Default if N1 never runs: no engine code; if N1a fails, §5.2's completion rule is false and the batch returns to this ruling.
