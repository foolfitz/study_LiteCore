# 048 — `placeCaret` 在點擊生效之前就回報成功，緊接著的格式動作落在舊游標上

| | |
|---|---|
| **狀態** | **已確認（六組對照＋延遲量測）／**產品側已修並驗證**／引擎側機制未定** |
| **發現日** | 2026-08-15（E2-C D3 清單目標格第二次執行） |
| **Bugzilla** | —（尚未判定是否上游） |
| **嚴重度** | **嚴重**——「點一下、按項目符號」會把清單套到上一個游標所在的段落 |
| **可重現** | 100%（Chrome 八格 × 無等待；Firefox 的延遲亦已量到 23–33 ms） |
| **是否上游** | **未判定** |

## 摘要

`EditorSession.placeCaret`（`editor-shell/editor-session.js:310`）點擊之後
輪詢這個條件：

```js
state.selectionType === "none"
  && state.selection?.observed === true
  && state.selection?.collapsed === true
```

**這三件事在文件剛開啟、還沒點任何地方時就已經成立**（實測：`observed: true`、
`collapsed: true`、游標矩形在 `y=1418`）。所以 `placeCaret` 會立刻回報成功——
它確認的是「有一個收合的游標」，不是「游標到了你點的地方」。點擊的座標從頭到尾
沒有被拿來比對過。

**點擊本身是有效的，只是不同步。** 點完立刻讀，游標還在原處；輪詢到它抵達，
八格量到的是 **22–28 ms**（`settle=poll`，5 ms 一次，八格全部抵達、無一逾時）。
中間發生什麼事沒有任何訊號通知呼叫端。

於是：**點完立刻派送的格式動作，落在上一個游標所在的段落。** `placeCaret` 的
輪詢間隔是 10 ms，而它第一次讀就已經滿足條件——所以它幾乎總是在那 22–28 ms
**之前**返回。

## 對照（Chrome，profile `e2-editor-v2` / `572035ac`）

| 手勢 | 點擊後等待 | 要求的 y | 事後游標 y | 動作落在哪 |
|---|---|---|---|---|
| `placeCaret` | 0 | 1950–4810（八格） | **全部 1418** | **第一段**（八格皆是） |
| `placeCaret`＋先繪製整頁 tile | 0 | 1950–4810（八格） | 全部 1418 | 未派送（被閘門擋下） |
| `selectRange` 定位後再點下方兩行 | 0 | 2730 / 3900 / 3510 | 1945 / 3184 / 2795（＝`selectRange` 放的位置） | 未派送 |
| `placeCaret` | **250 / 500 / 1000 / 2000 ms** | 1950 / 3120 / 3640 | **1999 / 3238 / 3645** | **點的那一段** |
| `placeCaret`，輪詢到抵達 | **22–28 ms**（量出來的） | 八格 | 八格全部命中 | 點的那一段，八格 `verified-format-readback` |
| `placeCaret`，中間夾一次 `save()` | 0（存檔本身約 250 ms） | 1820 | 讀回仍是 1418 | **點的那一段** |
| `selectRange`（零寬） | 0 | 八格 | 全部命中（誤差 ≤ 65 twips） | 點的那一段 |

第二列排除「LOK 視圖沒繪製過所以座標無處可落」——引擎裡根本沒有
`setClientVisibleArea`，唯一可能建立視圖狀態的是 `paintTile`，繪製過仍然一樣。

**第五列是最要緊的一列**：中間夾一次存檔（約 250 ms）之後，動作就落在點的地方，
**而游標讀回仍然回報舊位置**。所以「讀回的游標」與「動作實際作用的位置」是兩個
不同步的東西，兩個都不能單獨用來判斷點擊好了沒有。

## 這件事怎麼被看見的

E2-C D3 第一次能派送的那一輪（`run-1b-before-skip`），八格全部在**文件第一段**
動作：`set-list-unordered` 把 `E1-LC-HEADING` 變成清單項，而那一格的錨點是四段
之外的 `E1-LC-BETWEEN`；三格 `set-list-none` 打在本來就不是清單的標題上，
回報 **`verified-format-readback`——綠燈，而且什麼都沒量到**。

## 影響

- **產品頁面**：`web/e2-editor-app.js:301` 的「定位游標」就是這條路。使用者點一下
  canvas 再按工具列，會不會落在點的地方，取決於中間有沒有別的事情花掉時間。
- **E2-C D3 第一次派送輪整輪作廢**（已改用可證位置的路徑重跑）。
- **E2-C D2 沒有作廢**：D2 每一格在手勢與動作之間都有一次 `snapshot()` 存檔，
  實測那足以讓點擊生效——`d2-refused-no-mutation-engine` 的存檔文件顯示變成清單項的
  正是點的那一個空段落，不是第一段。這一點在本 finding 寫成「點擊完全無效」的
  第一版時判斷錯了，是 D2 的存檔文件推翻的。
- **E1-C 的人工輪沒有被推翻**：那九項是注音組字、剪貼簿、取消，沒有一項是
  「點擊定位游標」。SPEC E1-C §5 C1 第 1 步寫的是「click並等待typed collapsed
  caret」——正是這個不足的判準。**兩邊不衝突，是這個手勢從未被驗證過。**

## 修法（2026-08-16，已進）

改的是判準本身，不是把定位改接到 `setTextSelection`——後者是繞開，而且會讓
產品的點擊手勢**永遠沒被驗證過**。

`EditorSession.placeCaret` 現在要兩個訊號同時成立才返回：

| 訊號 | 為什麼單獨不夠 |
|---|---|
| **`sourceSequence` 前進**（引擎對「改變了編輯器狀態的 callback」的計數，就在產品的 `editorGetStateV2` 裡） | 它也會因為與游標無關的 callback 前進（例如 tile 失效），單看它會拿到陳舊的游標 |
| **游標矩形在點擊的那一行上** | 落點會落在矩形上緣之上多達 119 twips，也就是點擊可能落在兩個行框之間；鬆到能接受每一次真實落點的容差，同時也接受上面那一行 |

完全安靜達 400 ms 之後，接受一個已經在那一行上的游標——那是**同點點擊**，
引擎沒東西可說是因為沒東西要改（實測：點在游標已經佔著的同一個點，
`sourceSequence` 一動也不動；點在同一行的不同位置則會前進）。
**游標不在那一行時絕不返回，逾時失敗**（`EDITOR_CARET_NOT_PLACED`）。

容差用游標矩形自己高度的一半，不用 twips 常數：矩形就是行框，半個高度就是
半行，不隨字級改變。

驗證：`editor-shell/tests/place-caret.test.mjs` 六條（寫成讓舊實作會失敗），
以及 D3／D2 在修好的殼層上雙瀏覽器各一輪——D3 八格與修法之前逐位元組相同、
產品自報等待 22–28 ms 且八格 `engine-acknowledged`，D2 12／12。

**代價**：這個檔案是 E1-C 殼層 bundle 綁的五個之一，`E1_GO_ODT_EDITOR` 的殼層
綁定因此斷開（artifact 三個雜湊不受影響），申報在
`e1/editor-shell-bundle-v1-divergence.json`，記在 SPEC E1-C §11.7。

## 機制（引擎側）：未定

已知的是點擊會生效、而且不是立刻。不知道的是誰在等什麼：可能是 LOK 的
mouse event 排在主迴圈後面，也可能是 `LOK_CALLBACK_INVALIDATE_VISIBLE_CURSOR`
比游標本身晚到。**兩者的產品對策不同**（前者要等引擎，後者要等回呼），所以
在量出來之前不要寫成其中任何一個。

與 [047](047-a-save-immediately-before-a-click-placed-caret-makes-the-next-format-action-time-out.md)
同一個家族——都是「`placeCaret` 的確認不足以保證下一個動作」——但**觀察到的後果
不同**：047 是 barrier 等不到選取回呼而逾時，這一個是動作落在舊位置並且成功。
047 的四組對照全部在第一段上量的，重讀時要記得這一點。

## 還缺什麼

- [x] **窗口寬度**：量到了，22–28 ms（Chrome、八格）。但**不要拿它當對策的常數**
      ——它是一台機器、一種語料、一個 build 的數字，而正確的對策是等一個訊號，
      不是等一個時間。
- [ ] **引擎側機制**：native 重現，或在 WASM 上抓 mouse event 與游標回呼的時序。
      產品已經不再受害，但「為什麼要 22–28 ms」仍然沒有答案；
      這決定它是不是上游的事。
- [x] **Firefox**：延遲 23–33 ms，八格；修法之後兩瀏覽器各一輪全過。
- [ ] **是不是只有游標**：拖曳選取（down → move → up）是否也有同樣的延遲，沒量過。
      產品目前沒有拖曳選取（SPEC E2-C 2.4），所以這一項在 D5 之前不擋任何事。
- [x] 產品對策已定並已進：**改判準，不繞開**。改接 `setTextSelection` 的零寬選取
      被否決——它會讓產品的點擊手勢永遠沒被驗證過，而那正是這個 finding 的成因。
