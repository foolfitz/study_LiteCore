# 069 — 輸入框躺在文件的最底部，所以每次組字都會把整頁拉下去

## 現象

**operator 原話**（2026-08-22）：

> 「如果用新酷音輸入，打字的時候會使頁面捲軸往下拉」

## 機制

`web/e2-editor.html`：

```css
#sink {
  position: absolute; width: 1px; height: 1px; opacity: 0; ...
}
```

**沒有 `top`／`left`。**一個 `position: absolute` 而沒有位移的元素會停在它的
**靜態位置**——而 `#sink` 在 DOM 裡就排在 `<canvas>` 後面，canvas 的高度是**整份
文件**。所以那個接收鍵盤的 `<textarea>` 一直躺在文件的最底端。

IME 一開始組字，瀏覽器就把**焦點元素**捲進視野，於是 `.desk`（`overflow: auto`）
捲到底。

**這與 066 的 `focus({ preventScroll: true })` 無關**：那個旗標管的是 `.focus()`
自己引發的捲動，而這一次捲動是瀏覽器為了組字視窗做的，發生在 focus 之後。

## 量到的

`sink-does-not-drag-the-page`（`tools/probe_064_format_reaches_typing.py`）：

| | sink 的 top | 把 sink 捲進視野會用掉可捲動範圍的 |
|---|---|---|
| 修法前（對照組，`top: auto`） | **929**（＝canvas 高度，文件底部） | **99.5%** |
| 修法後 | **228**（＝游標所在） | **15%** |

**剩下那 15% 不是缺陷**：這一輪的 desk 只有 139px 高，游標在 228px 是真的在摺線
下面，捲過去正是編輯器該有的行為。

**判準因此是「占可捲動範圍的比例」而不是像素數**，而第一版判準就是寫成像素才錯的
——它要求修法後小於 50px，實測 125px 判 FAIL。**像素分不出「捲到游標」和「捲過頭
到文件末端」，占比分得出來。**

**對照組是一次突變不是第二次讀數**：把 `top` 設回 `auto` 讓 sink 回到靜態位置，同
一支掃描必須回報那次拖動。少了它，「頁面沒有捲動」和「這支臂看不見捲動」是同一種
綠。

## 修法

1. `#sink` 加上 `top: 0; left: 0`——只是起點，之後由 `paint()` 接手。
2. `paint()` 每次畫游標時把 sink 移到游標上（`moveSinkToCaret()`）。
   **用的是畫布的 CSS 尺寸，不是 backing 尺寸**：`box()` 算的是 backing 像素，
   兩者差一個 `devicePixelRatio`，拿後者去定位 DOM 元素會在 HiDPI 螢幕上偏一倍。
3. sink 的高度跟著游標高度——IME 的候選字窗是貼著焦點元素的框開的，一個 1px 高的
   框會把候選字窗擠在一列像素上。
4. `pointer-events: none`——把 sink 移到 canvas 上方等於在繪圖區上放了一個 1px 的
   透明標的，而放置游標靠的是 canvas 自己的 `pointerdown`。sink 只會被程式
   `focus()`，**從來沒有被點擊過**（`el.sink` 的八處呼叫都查過），所以沒有人少收
   到一次點擊。

## 這張單和 068 的關係

**兩張不同的單，同一天由同一個人回報，而且都在輸入路徑上。**068 是游標的矩形沒有
更新；這一張是輸入框的位置。修 068 不會修到這一張，反過來也不會。

順帶：sink 移到游標上之後，中文候選字窗會出現在游標旁邊而不是頁面底部——那是這次
修法的副產品，**沒有量過**，等 operator 確認。
