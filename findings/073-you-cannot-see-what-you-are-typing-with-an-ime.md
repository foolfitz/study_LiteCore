## 現象

用新酷音打中文：**注音打到一半的那串（ㄊㄞˊ）看不見，選字框也看不見。**
字最後會正確進到文件裡——只是使用者要等到它 commit 才第一次看到自己打了什麼。

其餘八項人工檢查當天全部通過（剪下、上下鍵、重做、第二次中文、按鈕後直接打字、
真剪貼簿貼上、游標跟隨、存檔往返）。**只有這一項是壞的，而它壞在自動化從來沒有問過
的一個維度上。**

## 機制：構造上必然，不是巧合

`#sink` 是一個 `<textarea>`，CSS 是 `width: 1px; opacity: 0`。它的存在理由是收鍵盤事件
——文件是畫布，沒有 DOM 可以打字。

而**瀏覽器把輸入法的 preedit 畫在那個 textarea 裡面**。

所以：一像素寬、完全透明的框，裡面正在顯示你打的注音。

頁面裡**一個 `compositionstart`／`compositionupdate` 處理都沒有**——組字整段是瀏覽器
的事，只有 commit 之後的字經由 `beforeinput` 走 input adapter 進到文件。那一半一直是
好的（finding 050 修的就是那條路），而「看得見在打什麼」那一半**從來沒有被寫過**。

## 這不是 finding 005，雖然使用者記得早期處理過

[005](005-qt5-wasm-no-input-context.md) 是 Qt5 的 wasm platform plugin **完全沒有註冊
composition 事件**，所以組好的中文永遠抵達不了應用程式。那是**另一個產品**（LOWA）、
另一個根因，而且症狀更嚴重：字根本進不去。

我們這個 sink 的做法**正是**當時那個問題的對策。但對策只做到「收得到字」，沒有做到
「看得見在打什麼」——**一個對策解掉了它瞄準的那一半，而另一半沒有人回頭看。**

## 修法

組字期間讓 sink 看得見，結束後變回一像素透明。

- **字級從游標高度導出**。`moveSinkToCaret`（finding 069）已經把 sink 的高度設成引擎
  給的游標矩形高度，所以組字框大致就是它將要落下的那一行的大小——不是一個在每個縮放
  比例下都錯的常數。
- **寬度用一個獨立的離屏 canvas 量**。問「這段 preedit 有多寬」不該去借畫布的繪圖狀態。
- **兩個結束事件都接**：`compositionend` 是正常那個，`blur` 是會被忘記的那個。點走的
  時候不是每個瀏覽器都會發 `compositionend`，而**一個留在畫面上的 sink 會帶著過期的字
  蓋在文件上——那比看不見更糟**，使用者得重整才能拿回頁面。

殼層 generation **v36**（`23163eb6c97a1083…`）。不需要連結：這整件事都在殼層。

## 這一格結果不是「只能靠人」，而那是這張單真正的收穫

`every-ime-commit-reaches-the-document` 用的是**合成的** composition 事件，驗的是
commit 那條路。真的輸入法不能從 harness 驅動——這一直被歸類成 **D5 定義上做不到**。

**但 CDP 有 `Input.imeSetComposition`**，它走的是 renderer 自己的 IME 路徑，會在聚焦
元素上真的觸發 `compositionstart`／`compositionupdate`。所以「使用者看不看得見自己在
打什麼」是有儀器的。

新增 `the-composition-you-are-typing-is-visible`：

| | opacity | width | left | top | value |
|---|---|---|---|---|---|
| 靜止 | 0 | 1 | 132 | 250 | `""` |
| 組字中 | **1** | **38** | 132 | 250 | `ㄊㄞˊ` |
| 結束後 | 0 | 1 | 132 | 250 | `""` |

**兩端都驗**，而且位置必須沒動——一個出現在頁面角落的框不算「使用者看得見自己在打
什麼」。正向對照是**組字到底有沒有開始**（`compositionActuallyStarted`）：沒開始的話，
「看不見」講的是儀器不是產品。

突變 `composition-never-shown`（把那兩個 handler 改名，也就是今天以前真正出貨的狀態）
讓它 PASS → FAIL，而且只有它動。

**教訓**：「這件事只有人做得到」是一個**可否證的宣稱**，不是一個分類。這一格被歸在
D5 底下，理由是「真的輸入法不能自動化」——那句話是對的，而它推不出「組字的可見性
不能量」。中間少掉的那一步是**去查一下有沒有工具**。

## 為什麼自動化在此之前完全看不到它

每一格關於 IME 的檢查問的都是「**字有沒有進到文件**」——`every-ime-commit-reaches-the-document`、
finding 050 的第二次中文、`caret-follows-the-text-you-type`。**它們全部只讀 commit 之後
的狀態。**組字進行中的那一秒鐘，這棵樹裡沒有任何東西看過。

而 sink 的不可見性是**刻意的、寫在註解裡的、而且對它原本的用途是正確的**。
[069](069-the-input-sink-sits-at-the-bottom-of-the-document.md) 才剛改過同一條 CSS 規則，
改的是 `top`/`left`，`opacity: 0` 一動也沒動——因為當時問的問題是「它在哪裡」，
不是「看不看得見」。

**一個屬性可以在它被寫下的那個用途上完全正確，而在另一個用途上是缺陷。**

## 還沒定案的一小塊

Operator 回報時把「拼音看不見」和「選字框看不見」講成一件事。修法之後**兩件都好了**
（使用者當日確認），但**只有第一件是我量到的**：選字框是輸入法自己的視窗，位置由
瀏覽器回報的游標矩形決定，harness 量得到 sink 的幾何，量不到 fcitx 把視窗畫在哪裡。

合理的推測是同一個原因——一個一像素寬的透明框給不了輸入法有意義的錨點幾何——但
**那是推測，這裡不當成量測**。真要釘死它需要一個能讀作業系統層視窗位置的儀器，而
目前沒有。
