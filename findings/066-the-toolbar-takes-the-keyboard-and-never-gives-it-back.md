## 現象

operator 的原話（2026-08-22）：

> 「樣式按鈕按下以後，焦點不會自動回到輸入畫面，而是停在按鈕上（感覺是 html 的行為）」
>
> 「樣式套用時好時壞，壞的居多，我看不出 pattern」

**這兩句是同一件事，而且第一句是第二句的原因。**

## 重現步驟

1. 在文件上點一下（游標定位，鍵盤焦點進到 `#sink`）。
2. 按工具列的 **`B`**。
3. **直接打字。**

**預期**：打出粗體字。
**實際**：**什麼都沒有發生。**文件沒變、revision 沒動、沒有任何訊息。

4. 為了能打字，點一下畫布。
5. 打字。

**實際**：字打出來了，**但沒有粗體**。

## 證據

`findings/evidence/066/`。兩個臂，各自帶正向對照。

### 臂一：焦點跑去哪了

必須用**真實點擊**（CDP `Input.dispatchMouseEvent`）。`HTMLElement.click()` 不行
——它只派送事件、不執行預設動作，所以不會移動焦點，整個缺陷會完全看不見。

| | |
|---|---|
| 點畫布之後的焦點 | `{id: "sink", tag: "TEXTAREA"}` ← **正向對照**：焦點是進得去的 |
| 點**按鈕**之後的焦點 | `{tag: "BUTTON", action: "set-bold"}` |
| 不動焦點直接打字 | 派送到 `BUTTON`；revision `1 → 1`；標記**不在文件裡** |
| 還原焦點再打同一段 | 派送到 `sink`；revision `1 → 2`；標記**在文件裡** |

最後一列是這一臂的正向對照，也是讓前一列可讀的東西：**同一個派送，只差一行
`sink.focus()`**。沒有它，「打字沒作用」和「探針打字的方式不對」長得一模一樣。

### 臂二：那一下點擊會把格式弄掉

單一變數：在「按下格式」與「打字」之間有沒有點畫布——而點畫布是唯一能把鍵盤
帶回文字的動作。

| | 標記 | 結果 |
|---|---|---|
| 按完直接打 | `MKNOCLICK` | **粗體 true**，`carrier: span`，`T1` |
| 先點畫布再打 | `MKAFTERCLICK` | **粗體 false**，`carrier: paragraph`，`P2` |

第一列是對照組：它證明格式在這顆 build 上**到得了**打出來的字，所以第二列掉的
是那一下點擊，不是別的。

> 兩個臂都是在 `inline_styles_of()` 於 2026-08-22 修好**之後**跑的（紀錄裡有
> `fromParagraphStyle`）。064／065 是用壞掉的版本讀出來才被撤銷的；這一張不受
> 那個影響，而且臂一根本沒用到 ODF 判讀工具——它讀的是 `document.activeElement`。

## 歸因：產品頁自己的事件處理，讀得到行

三行原始碼就講完了：

- 鍵盤輸入綁在 `#sink` 上：`session.attachInput(el.sink)`（`web/e2-editor-app.js:787`）。
- **整個檔案裡 `el.sink.focus()` 只出現一次**（`:559`），在 canvas 的 `pointerdown`
  處理器裡。
- 工具列的 click 處理器（`:805-816`）派送動作之後**沒有任何還原焦點的動作**。

所以按鈕吃掉焦點是瀏覽器對 `<button>` 的正常行為（operator 的直覺是對的），
**缺陷是頁面沒有把它還回去**。

而第二半也不是引擎的錯：點畫布會移動游標，那是**點擊本來就該做的事**。缺陷在於
使用者**被迫**做那個動作。

## 為什麼自動化從來沒看到

**因為 harness 每次都替使用者補上那一步。**`run_e2_c_product_path.py` 裡每一個
鍵盤 helper——`TYPE_KEY`、`DELETE_KEY`、`COMPOSE`、`CUT`——**開頭第一行都是
`sink.focus()`**。

而產品路徑的格式檢查更走不到這裡：它用的是頁面的「插入文字」欄位加「插入」按鈕
（`session.commitText`），根本不經過鍵盤。

這是 `harness-path-vs-user-path` 的又一次，而且是最乾淨的一次：**harness 補上的
那一行，正好就是缺陷本身。**

## 處方（已實作，殼層 v26）

`web/e2-editor-app.js` 多了一個工具列上的 `mousedown` 監聽器，兩行，**兩行都承重**：

```js
el.toolbar.addEventListener("mousedown", (event) => {
  if (!event.target.closest("button")) return;
  event.preventDefault();
  if (session) el.sink.focus({ preventScroll: true });
});
```

- `preventDefault` 讓按鈕**一開始就不拿走鍵盤**，這是每一個編輯器工具列的做法。
  `click` 照樣觸發，所以動作本身完全沒變。
- `focus` 補上前一行補不了的情況：**第一個動作就是按 B** 的使用者，焦點在
  `<body>` 上，阻止按鈕拿走焦點沒有用。

只對 `<button>` 生效——`#fixture` 與 `#text` 也在這個工具列裡，使用者還要點得進去。
**鍵盤啟動那條路刻意不涵蓋**：用 Tab 走到按鈕再按空白鍵的人，焦點應該留在按鈕上，
那才是鍵盤導航該有的行為。

`el.sink.focus()` **不會移動游標**——只有 canvas 的 `pointerdown` 會——所以這個修法
不會變成它要修的那個缺陷。

### 第二半沒有修，而且是刻意的

「點畫布會丟掉待套用的格式」**本身還在**——只是使用者不再被迫踩它。要不要讓
「點在原處」不重設待套用狀態，是另一個問題，**這一張單不主張**，也沒有量過。

### 這個修法自己踩到的坑

第一版把新檢查放在 `formatting-survives-the-next-paragraph-break` **前面**，
而它結束時 bold 是開著的——頁面又從快取決定 `enabled`，所以下一格想「打開」時
送出的是「關掉」，那一格的前置條件當場死掉（NOT_ESTABLISHED，量到的）。

**這是同一個檔案兩天內第二次踩同一個坑**，而且警告的註解在踩下去的時候就已經
寫在那裡了。順序已改，理由寫在程式碼裡。

## 為什麼「時好時壞」

operator 說看不出 pattern。量到的行為是**穩定會掉**（先點再打，一定沒有格式）。
最可能的解釋是**哪一次他需要點、哪一次不需要**——例如上一個動作是不是已經把焦點
留在 `#sink` 上。這一段是推測，**沒有量**。
