## 現象（量測，不是推論）

- 貼上本身很快：一次 `paste` 事件，送出一次 `insertText`，引擎呼叫一次 `paste()`。四十段文字在 Chrome 花 22.5–24.8 ms、Firefox 7.5–8.8 ms（原生 LibreOfficeKit 26.8 是 6.7 ms）。之後 10–27 ms 狀態回到「就緒」，200–260 ms 內重畫完成。
- **卡住的是貼上之前的那一下點擊。**在空白文件第一行以下點一下：
  - 2–5 ms 內 session 進入忙碌狀態，700 ms 後顯示「處理中」（finding 125 的延遲）；
  - `placeCaret` 每約 5 ms 輪詢一次 `editorGetStateV2`，共 5,328–5,550 次，一直到 `caretTimeoutMs` 的 **30.0 秒**用完；
  - 最後跳出 `EDITOR_CARET_NOT_PLACED` 的提示，**排在後面的貼上這時才送出**（點擊後 30,005–30,014 ms）。
- 成因：`placeCaret` 只在兩種情況下返回，一是游標落在被點的那一行，二是序號推進**而且**游標動了。空白文件只有一行、游標只有一個位置可放，引擎把它夾回原位：游標不會動，被點的 y 又遠在唯一那一行之下，所以兩個條件都永遠不成立，只能等到逾時。session 的佇列是串行的，貼上只好排在後面。

擁有者感受到的是「十幾秒」，量到的是 30.0 秒，這一點沒有重現。可能的原因是點擊之後過了一陣子才貼上，或者在等待中途又做了別的事，這是推測，沒有量過。整條路上找不到任何一段約十秒的耗時。

## 與 finding 052 的關係

這是 **052 的具名殘留**，以新的形狀出現：點在文字範圍之外，引擎什麼都沒移動。052 當年的登錄寫著「`editorPlaceCaretV2` 把它限制在 38／251 ms 內」，**但只有實驗頁 `web/e2-c-block-identity-app.js` 呼叫它，產品的 `placeCaret` 從來沒用過。**以前這個殘留要「在文字範圍外點第二下」才碰得到；在空白文件上，**第一下就碰到**。

引擎這一側早就準備好了：worker 的 `editorPlaceCaretV2`（`sdk/sdk-worker.js:1552`）「即使什麼都沒動也會回答」，v19 與 v20 的匯出清單都有 `_oxsdk_editor_place_caret`。

## 裁決（2026-10-14，fable 代擁有者；只追加，不改上文）

**選 A：產品的 `placeCaret` 改成問引擎。** 引擎早就有這個入口（`editorPlaceCaretV2`，052 當年的處方）：它自己送滑鼠事件，點擊有造成游標回呼就在回呼時回答，點擊什麼都沒改、也沒有回呼，就在自己的 250 ms 期限到時把當下的游標讀回來回答，並在 `completion` 說明是哪一種。它只會被「可見游標」回呼完成，tile 或文件大小的回呼完成不了它，所以 finding 138 那種無關回呼騙不到它。v19 與 v20 兩個 profile 都有這個匯出，worker 用 `narrow-editor-v2` 把它開著，不用連結。056 那個「指紋那一半在 WASM 上是空的」的保留意見**與這次無關**：出貨的 Writer core 沒有 a11y，回答裡的段落指紋確實是空的，但這個修法一個字都不讀它，只用游標矩形、選取與 completion——這些跟 `getState` 給的是同一批欄位，056 量過的 38／251 ms 就是這一半。

不選 B（「點在最後一行之下或文件只有一個空段落就直接接受」）：session 手上只有游標自己的那一個行框，沒有別的行框可比，「只有一個空段落」又要靠出貨 core 沒有的大綱；而且 B 只救空白頁，文件裡行與行之間、頁邊旁邊那些一樣「點了但沒動」的點擊還是等 30 秒。不選 C（縮短逾時）：那是把一次引擎處理正確的點擊改成 N 秒後拒絕，貼上一樣排在後面，提示一樣會跳。

**引擎的回答不是收到就算數，仍然照 138 的判準判**：序號推進**而且**游標位置或選取跟點擊前讀到的不同，才算證據；只有序號推進不算。有證據就是基底原有的三種結果；沒有證據而游標在被點那一行，就跟今天一樣等滿寬限期後回 `already-at-target`；沒有證據又不在那一行——就是空白頁這一下——先給 core 同一段 400 ms 寬限期（048 的防護：core 還沒處理到這一下點擊時，期限讀回拿到的是舊游標；點擊在寬限期內落地會被重讀看到、照證據判），寬限期過了就回報「引擎回答了，游標留在原位」（`engine-answered-the-caret-stayed`，`caretOnClickedLine: false`），佇列不再被佔住。沒有這個入口的 client、worker 拒絕（`UNSUPPORTED_OPERATION`）、引擎在 barrier 後面忙（`BUSY`），都走 v67 原本的輪詢路徑，逾時與錯誤不變。**具名極限**：core 在寬限期之後才處理到的點擊，會帶著舊游標被當成「留在原位」——這跟「點在原點」那一條本來就有的界限相同；本機 core 處理一次點擊是 22–28 ms（048），要卡到十倍以上才會碰到。

**實作與驗證**：只動 `editor-shell-v2/`（`narrow-editor-v2-session.js` 的 `placeCaret`、`paragraph-editor-client.js` 與 `narrow-editor-v2-client.js` 新增 `placeCaret` 請求、兩個 `.d.ts`）；`editor-shell/` 沒碰，`check_e1_c_bundle_intact.py` 改前改後都 intact。單元測試先紅後綠：`editor-shell-v2/tests/place-caret-blank-page.test.mjs` 13 項，在 v67 位元組上 7 項紅、候選全綠；138 的七條臂與對照原封不動仍綠；全套 412 → 425 全綠。瀏覽器見證用 `tools/probe_paste_latency.py`，界限先寫再跑（`insertText` 要在點擊後 1,500 ms 內送出）：v20 的紅案先量（v67 位元組配 v20 頁面：點擊後 30,007 ms、5,542 次輪詢）；候選在 v19（dist）與 v20（repoint 的頁面，沒有 `--write`）、Chrome 與 Firefox，頁面中間與往下 25% 的點擊都在 **405.9–412.8 ms** 回答（「定位游標 405–407 ms」，沒有拒絕提示，重讀 27–28 次），之後的貼上在 `paste` 事件後 1.3–2.2 ms 送出、revision 1；第一行點擊結果不變。表格與原始紀錄在 `findings/evidence/paste-latency/README.md`（Ruling、Witness 兩節）。

## 裁決（第二輪，2026-10-14，fable 代擁有者；只追加，不改上文）

**為什麼有第二輪。**上一節的修法在凍結 v68 之前先跑了 129-B（`findings/evidence/link-batch/v68-witness/README.md`），結果是紅的，兩個缺陷：(1) `s3` 形狀的六格在兩個瀏覽器都跳出 `定位游標：INVALID_ARGUMENT：editorPlaceCaretV2 requires non-negative integer twips`，範圍選取留在原地——頁面送的是 `caret.y + caret.height / 2`，游標行高 277 時是 x.5，worker 拒收非整數；(2) 其他每一格的「定位游標」從 v67 的 26–32 ms 變成 253–268 ms。

**先量再改。**主 session 對 (2) 的判讀（引擎等不到可見游標回呼，到 250 ms 期限才回答）是讀原始碼推的，這一輪先用探針在紅的那份位元組上把 `completion` 錄下來（`findings/evidence/paste-latency/second-pass/`，Chrome）：會移動游標的一般點擊，引擎 24.1 ms 在回呼時回答（`documented-callback-visible-cursor`）；按方向鍵讓頁面在游標端點一下、把範圍選取收起來的那一下，251.4 ms 才回答，`verified-caret-readback`，回答裡序號 35→36、選取已經收起——也就是 TEXT_SELECTION 回呼**有到**，引擎算進了狀態，但 place-caret 的完成條件只認可見游標回呼；點在游標原點的那一下 250.6 ms，序號沒動。所以 (2) 的機制證實而且更精確：不是沒有回呼，是來的那個回呼不算數。另外讀原始碼確認兩件事：`moveFromPoint` 只在選取形狀不是 collapsed 時才會先點（`web/e2-editor-app.js:2704–2708`），所以 129-B 每一格的點擊都是在範圍選取打開時做的；引擎的 place-caret 懸著的時候，後面那個方向鍵會被引擎回 BUSY（`probe_engine.cpp:5452`），所以「先回傳、讓引擎慢慢答」在殼層這邊做不到。交接文件列的「第二下點擊可能被 core 當成雙擊」查過是不成立的：VCL 的 LOK 路徑 `ImplLOKHandleMouseEvent` 照傳入的次數用（`mnClickCount = nClicks`），不靠時間合成雙擊——不過這一輪的設計本來就不多點第二下。

**裁決：點擊走哪條路，由點下去當時的選取決定。**

- **範圍選取打開時**走 v67 的輪詢路（`document.click` 加每 5 ms 一次 `getState`，判準仍是 138 的）。理由：在打開的範圍上點一下，一定會把它收起來，收起來就是這一下點擊自己的證據，速度就是 v67 的 26–32 ms；引擎那條路在這種點擊上一定等到期限，還會卡住後面的鍵。`document.click` 照呼叫者給的值送（含 x.5），和 v67 完全一樣——wasm 邊界把它截成整數，129-B 的參考回合就是用這些位元組做的。輪詢迴圈多一個出口，免得第一輪買到的界限在這條路上又丟掉：被點擊收起、游標留在被點那一行之外，寬限期過了就回 `engine-answered-the-caret-stayed`（約 400 ms，不是 30 秒）。**具名極限**：範圍打開而 core 完全沒處理那一下（什麼證據都沒有）仍是 v67 的 30 秒逾時，不補第二下點擊去問引擎；文字文件裡還不知道有這種點擊。
- **選取是收起的**走第一輪的引擎路，但送 `Math.round` 過的 twips（worker 的契約；重開檔那條路 `:1821` 會把 x.5 送到這裡）。游標會動就在回呼時回答（24 ms），不會動（空白頁、原點）就等期限加寬限期約 405 ms——v67 的原點點擊本來就付這個價。引擎路的「移到別行」判定現在要求游標真的動了；只有選取變、游標沒動的算「留在原位」。
- 沒選交接文件的另一個方向（先輪詢、沒收斂再問引擎）：第一輪的測試這一輪要原封不動留著，它釘死「引擎回答時由引擎自己點，殼層不再點第二下」，而且那是一個第一下不需要的第二下滑鼠事件。沒做引擎改動（讓 TEXT_SELECTION 也能完成 place-caret）——要連結，列為下批連結的建議，見 `findings/evidence/paste-latency/README.md` 最後一節。
