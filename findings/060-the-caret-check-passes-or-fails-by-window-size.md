# 060 — 游標那一格的檢查，**綠不綠取決於瀏覽器視窗多大**

| | |
|---|---|
| **狀態** | **已確認並已修（2026-08-18 同日）**——判準改成錨定那一行自己的墨水 |
| **Bugzilla** | —（**不是上游**：缺陷在我們的檢查裡） |
| **發現日** | 2026-08-18（T0 的對帳守衛第一次跑在真報告上就掉出來） |
| **嚴重度** | **中**——產品沒壞，但一格 `done` 靠的是一個會隨視窗大小改變答案的檢查 |
| **可重現** | Chrome 1/1（725×929 的畫布）；Firefox 未量 |
| **是否上游** | 否 |

## 現象

一次乾淨的產品路徑輪（`mutation: none`，served 殼層 digest 與宣告的 v16 相符）
把 `the-caret-is-drawn-where-it-was-placed` 判成 **FAIL**：

```
darkWithCaret        2051
darkAfterItMovedAway 2051      ← 兩次一模一樣
band                 y=242 h=46 width=725
```

同一格在 2026-08-17 是綠的，數字是 **2763 → 2739**（[[058]]）。
中間 `dist/` 與 `web/` **一個位元組都沒動**（`git status` 為空）。

## 游標是有畫的——**這不是 058 修法的迴歸**

判準改成「量**每一列**的深色像素」而不是一條 46 列的帶，並且對**兩個 root** 各跑
一次：`dist/`，以及 `caret` 突變鏡像（那個突變就是把畫游標那一行關掉，是 058 自己
用過的對照）。同一個手勢、兩個 root 相減，游標就被隔離出來了：

| | clean 與 no-caret 相差的列 |
|---|---|
| 點 A（`y = 0.28`）之後 | 文字區內**沒有** |
| 點 B（`y = 0.42`）之後 | **第 276–283 列，各 +1 個深色像素** |

八列、一像素寬、只在畫游標那一行還在時出現。**那就是游標。**

## 那它為什麼還是紅的

`layoutCanvas()` 用 `el.desk.clientWidth` 決定畫布大小，所以**畫布是瀏覽器視窗的
函數**。這一輪是 725 × 929、`devicePixelRatio` 1；058 記下 2763 那次的視窗比較大。

在這個幾何下，兩個寫死的點擊比例produces 不出判準假設的狀態：檢查取樣的帶是第
242–287 列，而游標落在第 276–283 列——**在第二次點擊之後仍然在那條帶裡面**，
而那正是判準預期游標已經離開的那一讀。比較因此反向；文件夠短、兩個比例落在同一行
時，則塌成相等。

**不是等太短**：單次點擊之後在 1 s／3 s／6 s／12 s 重複取樣，那一筆從來沒有出現。

## 不指認的

- **第一次點擊之後游標在哪。** 沒有可數的墨水增加，這與「筆畫壓在本來就是深色的
  像素上」相容，但那是推論不是量測。
- **Firefox 是不是一樣。** 只跑了 Chrome。
- **第一次點擊與第二次點擊為什麼不對稱。** 沒量到，不寫。（040／048 的先例。）

## 代價，以及為什麼它值得一張單

驗收清單的 `see-where-the-caret-is` 是 `done`，靠的就是這一格。
檢查**仍然能紅**（突變對照證明了），但它的**綠**取決於 harness 剛好開多大的視窗。

這是「harness 的路 vs 使用者的路」的又一個形狀：判準寫成了畫面比例，而畫面比例
不是產品的性質，是執行環境的性質。

**修法不在這一張單裡**：它與 `put-the-caret-where-i-clicked` 要的是同一個東西——
**錨定在引擎回報的文字矩形上**的判準，而不是寫死的視窗比例。計畫
`PLAN-2026-08-18-usable-editor-autonomous.md` 的 T3a 已經排了。

## 這一格是怎麼被抓到的

T0 的對帳守衛：`check_usable_editor.py --report`，規則是「`done` 的列，它的檢查
必須在一次乾淨的基線跑裡是綠的」。**它第一次跑在真報告上就掉出這一張單。**
在它之前，清單只驗參照存不存在，一格 `done` 配一個紅著的檢查是全綠的。

證據：`evidence/060/`。


## 修好了（2026-08-18，同日）

判準不再取固定的視窗比例。**同一行點兩次**（靠近行首 x=0.06、遠過行尾 x=0.92），
文字在兩次讀之間不會動，所以**多出墨水的那一欄是游標的第二個位置、少掉的那一欄是
第一個**——不需要參考影像，也不需要引擎的座標。

行的墨水範圍由**兩次都有墨水的欄**決定（游標自己因為移動了而被排除）。

**第一次跑就抓到我自己判準的一個缺陷**：`inkSpan` 回報 724，而畫布寬 725——
兩端的「墨水」是**頁面邊框**，不是文字，所以「沿著這一行的比例」其實是「橫跨整個
畫布的比例」，x=0.92 的點擊算出 0.605 而被判紅。修法：**排除填滿整個帶高的欄**
（字形不會填滿含行距的整條帶，邊框會）。之後 `inkSpan` 是 355，量的是真的文字寬度。

修好之後（`evidence/060/anchored-oracle-baseline.json`）：

| | 靠近行首那次 | 遠過行尾那次 |
|---|---|---|
| 游標在行墨水上的位置 | **-0.006** | **1.003** |

正好落在文字的起點與終點。

**而且它會紅**（`anchored-oracle-mutation-caret-ignores-x.json`）：新突變
`caret-ignores-x` 讓游標照畫、照畫在對的那一行，**只忽略給它的 x**——舊的帶狀計數
判準對這種壞法是綠的。兩格都變紅，run 判定「the mutation was detected by the check
that owns it」。

**具名的極限**：這個判準是靠**看游標移動**認出它的，所以一個被釘在固定欄位的游標，
與一個根本沒被畫的游標，在這裡讀起來一樣。兩格會一起紅。

⇒ `see-where-the-caret-is` 與 `put-the-caret-where-i-clicked` 兩格都收復成 `done`。
