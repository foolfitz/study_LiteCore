## 機制（崩潰堆疊對到函式名＋讀原始碼）

- Writer 排版一段新段落時，**後續頁框是在前一個頁框的排版裡遞迴排的**（`sw/source/core/text/frmform.cxx`：`FormatAdjust` → `AdjustFollow_` → `CalcFollow` → `Calc`）。一次排版產生幾頁，就多巢狀幾層。
- 崩潰堆疊有 112 層，其中這個遞迴環重複了 11 次，最後在 `InsertPage` 底下的 `__pthread_mutex_trylock` 裡一個 store 越界。函式名是拿兩個帶 name section 的同源連結做函式體比對對出來的，最內層 20/20 都唯一對上。
- 執行緒的記憶體由低到高依序是 `struct pthread`、TLS，然後才是 stack；stack 往下溢位，先寫壞的就是執行緒自己的 `struct pthread`。所以症狀有三種：越界存取、卡死、中止。

## 量測（Chrome，headless；每格各開一個新瀏覽器）

| 輸入 | 結果 |
|---|---|
| 一段中文，43,008 位元組（14,336 字，10 頁） | 正常 3/3 |
| 一段中文，43,520 位元組（14,508 字） | 失敗 3/3：卡死 1、回答成功後才中止 2 |
| 一段中文，≥ 49,152 位元組 | `memory access out of bounds` |
| 65,536 位元組，拆成 2、4、16 段 | 正常（各 14–15 頁） |
| 65,536 個 ASCII `a`、或每 100 字一個空格的中文 | 崩潰 |
| SDK `insertText` 同一段（純文字路徑） | 卡死（SDK 對 `insertText` 沒有大小上限） |
| Ctrl+V 同一段 | 頁面不送：輸入轉接器上限 16,384 位元組（v21 與 0.2.24 都一樣） |
| 連續三次 16,383 位元組的 Ctrl+V，貼進同一段（11 頁） | 正常：每一次排版只長出少數頁 |
| **開一份已含 10 或 14 頁單段的文件** | 開檔正常；**在那段開頭打一個字**：0.2.24 失敗 4/4，v21 失敗 2/2；1 頁的對照組正常 |
| Firefox 157 | 65,536 崩潰 3/3；43,520 貼上成功後引擎壞掉；43,008 正常 |
| 原生 LibreOffice（round 2 的 probe） | Markdown 與純文字都正常 6/6，約 50 ms，12 頁 |
| **反事實**：只把 mirror 裡 `probe.js` 交給 `_emscripten_thread_init` 的預設 stack 從 65,536 改成 1,048,576（`probe.wasm` 不動） | 所有失敗的輸入都正常 8/8，含開檔後打字 |

## 為什麼 0.2.24 的使用者也碰得到

一次貼上（Ctrl+V，上限 16 KiB）碰不到。但只要**開啟的文件裡本來就有一段夠長的段落**（約 10 頁以上不分段，例如沒有分段的長篇貼文、匯出的逐字稿），在那段裡打字就會讓引擎死掉。宿主若直接呼叫 `pasteMarkdown`／`insertText` 送這樣的文字，兩個版本也都會死。

## 裁決（fable 裁決 1，2026-10-17，擁有者授權；原文 `findings/evidence/link-batch-v21/shakedown/review/ruling-fable-1.md` Q4）

**選 A：第 2 項不在 v21 出貨**。不提供頁面入口，具名 L-md-sdk-callable，SDK 仍可呼叫。M3 在已連結的引擎上是紅的，套用它釘死的預設；修法要重新連結，屬於下一批，並有自己的判準。v21 只出第 1 項。

白話理由（fable 寫給擁有者）：一段 43,520 位元組以上的中文（約十頁）一貼，就讓引擎執行緒把 64 KiB 的堆疊撐爆。三種死法都量到了，兩個瀏覽器一樣；只把 loader 的預設堆疊改成 1 MiB 就 6/6 正常，所以原因確定。這要重新連結，是擁有者的步驟，也是新的引擎身分，今晚不可能做。M3 釘死的「引擎直接送 65,536 要完成」這一臂是紅的，預設就是第 2 項不出貨；把 SDK 上限降到 16 KiB 救不了這一臂，那是事後搬門檻。0.2.24 的引擎其實也會死，只是 Ctrl+V 的 16 KiB 上限擋住了使用者；第 1 項不改變這件事。

裁決之後補上的事實（主 session，2026-10-17）：fable 指出「開啟已含長段落的文件」這條路還沒量。崩潰診斷同一晚補量了：開檔本身正常，但在那段開頭打一個字，0.2.24 失敗 4/4。所以 0.2.24 的使用者**不必經過任何貼上就碰得到**。這不改變今晚的作法（修法仍要重新連結），但會影響下一次連結的優先順序，留給擁有者決定。

**下一批的判準（現在就寫下）**：

1. 上表四個失敗輸入：65,536 中文一段、43,520 中文一段、65,536 ASCII 一段、開檔後在長段開頭打字。都要正常完成，N=3、兩個瀏覽器。
2. stack 大小要附理由。理由可以來自量到的巢狀深度，或來自原生的設定。也要量記憶體成本：執行緒池約 7 條 × 每條的 stack。
3. 要不要開溢位檢查（`STACK_OVERFLOW_CHECK`）要有決定，寫明代價。
4. 若沒做：第 2 項（Markdown 入口）繼續不出貨。0.2.24／0.2.25 的發佈說明，要寫「開啟含超長單一段落的文件並在其中打字可能讓編輯器停止回應」。
