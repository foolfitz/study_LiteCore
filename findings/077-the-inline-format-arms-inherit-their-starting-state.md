## 一句話

`format_arm` 每一臂用 `insert-paragraph-break` 開一個新段落，而新段落**繼承**前一段
末端的格式——所以每一臂的起始格式狀態**由這一輪前面發生過什麼決定，從來沒有被控制過**。

## 機制：一個錯的起始值，其餘全部是決定論

工具列不是「設成 X」，是**切換**，而且它送什麼由快取決定
（`web/e2-editor-app.js`）：

```js
const options = FORMAT_ACTIONS.has(action)
  ? { enabled: formatStateFor(action) !== true }
  : {};
```

v5 上同一輪逐臂量到（`formatCacheBefore -> formatCacheAfter`，以及存出文件的實際值）：

```
MKBOLDON   want=True   快取 true ->false   文件 False   ✗
MKBOLDOFF  want=False  快取 false->true    文件 True    ✗
MKITALON   want=True   快取 false->true    文件 True    ✓
MKITALOFF  want=False  快取 true ->false   文件 False   ✓
MKPREOLD   want=True   快取 true ->false   文件 False   ✗
MKSURVIVE  want=True   快取 false->true    文件 True    ✓
```

**文件 13/13 完全跟著快取走。**唯一異常的是 `MKBOLDON`——**第一支臂，在按下之前**
快取就已經是 `true`（v4 上同一位置是 `false`）。於是頁面送出「關」，文件得到不粗體，
快取正確地移到 `false`；下一臂起始就變成 `false`，送出「開」，於是想關掉的那一臂
反而拿到粗體。**整串失敗只由那一個起始值決定，後面每一步都是決定論。**

## 這也解釋了我先前那個「20 秒 timeout」

第二版的等待條件是「等 `aria-pressed` 變成目標值」。反相發生時，按下去送的是相反的值，
**快取因此往離目標更遠的方向移動——那個條件永遠不可能被滿足**。八臂各等滿 20 秒不是
「快取不跟著動」，是**我在等一件按照設計不會發生的事**。

v4 上 13/13 都在 202 ms 滿足，只是因為那一輪的起始值剛好都是對的。
**同一個假象在兩顆 core 上長得像一個 core 的缺陷。**

## 產品那一側不是缺陷（但值得記著）

從快取推導要送的值是**刻意的**，頁面自己的註解說得很清楚：明確地送值在讀取過期時
是**穩健**的——猜錯了，使用者再按一次就對了，而 toggle 會把過期讀取變成靜默的 no-op。
對人來說這是自我修正的；對一支「按一次然後依賴交替」的自動臂來說不是。

## 處方（已實作）

臂不能再繼承起始狀態，要**建立**它，而且只用產品自己提供的東西：

1. 開新段落之後按 **`#clear-format`**（「清除格式」）。它**對什麼都不宣稱、只要求關閉**
   ——正是可以拿來歸零的東西。
2. `turn_on` 的臂：起始應為 `false`。`turn_on=False` 的臂需要先讓它變 `true`，
   所以多按一次按鈕（此時快取為 `false`，送出的是「開」）。
3. **用快取斷言前置條件**。不成立就記成 `NOT_ESTABLISHED` 並寫明原因，
   **不要當成 FAIL**——那是臂沒站好，不是產品做錯。

## 驗證：13/13（2026-08-23）

處方實作之後在 v5 上重跑：

```
set-bold  MKBOLDON   前置要 false 實得 false 成立 -> 快取 true   文件 True   ok
set-bold  MKBOLDOFF  前置要 true  實得 true  成立 -> 快取 false  文件 False  ok
...（13 臂全部如此）
```

**十三臂全部 PASS，前置條件十三次全部成立。**整支檢查從 FAIL 變 PASS，整輪從
3 FAIL / 6 NOT_ESTABLISHED 變成 **1 FAIL / 6 NOT_ESTABLISHED**。

⇒ **粗體在 a11y core 上從來沒有壞過。**壞的是臂從一個沒被控制的狀態出發，而那個
狀態在出貨 core 上剛好是對的。這一格因此也回答了原本要請使用者人工確認的兩題之一
——但**人工那一輪仍然值得跑**，因為 harness 的路不是使用者的路（`commit()` 走產品的
插入欄位＋工具列，使用者走真的鍵盤），而這條規矩今年已經兩次讓兩邊得到不同答案。

順帶：`清除格式` 在 v5 上實際是**可用的**（十三次歸零全部成功），儘管
`clear-format-removes-every-inline-format` 那支檢查仍是 NOT_ESTABLISHED——
**那支檢查沒有量到的東西，這十三次順手量到了。**

## 沒有量的（因此不指認）

- **v5 上那個起始 `true` 是不是「對的」。**若游標當時真的落在粗體文字裡，讀到 `true`
  就是正確的，而錯的是臂的假設。**沒有去查那一刻游標在哪。**
- **兩顆 core 為什麼起始狀態不同。**v5 那一輪前面有數支 NOT_ESTABLISHED，
  文件狀態本來就已經岔開；**這不需要用 core 的差異來解釋**，而在排除掉之前也不得歸因於它。
- **`清除格式` 在 v5 上可不可靠。**`clear-format-removes-every-inline-format` 在 v5 上是
  NOT_ESTABLISHED，也就是不知道。處方的第 3 步就是為了這個而存在。
