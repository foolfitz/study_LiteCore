## A1. The 250 ms move readback (`gEditorPending`, `verified-move-readback`, finding 096)

- **Where** [SRC]: struct `EditorPendingOperation` `pe:446-468` (`readbackDeadlineArmed`, `readbackDeadline`); global `pe:1098`; constant `EditorMoveReadbackDeadlineMs = 250` `pe:506` with its arithmetic (37–39 ms band, 6.4×) `pe:481-505`; armed for **every** key-path action `pe:5756-5799`; the loop's wake `pe:6455-6474` synthesises `EditorActionReadback` (enum `pe:217-226`), dispatched with a correlation guard `pe:6376-6385`, answered by `completePendingEditorActionByReadback` `pe:2360-2388` (`changed:false`, `refreshCaretParagraph()`).
- **What**: if no cursor/selection callback arrives within 250 ms, answer from the current state with its own completion name; never claims a move.
- **Premise** [SRC `pe:2324-2348`]: a posted key at a boundary changes nothing, core broadcasts nothing, the waiting operation wedges the worker (40/40).
- **Guards**: finding 096 (`findings/096-…md`), 018's End case, and 142's Ctrl+Home/End (`pe:5731-5743`). Downstream it enabled finding 151 (readback answered with the OLD caret before `GoToEndOfDoc` ran, `session:103-114`) [SRC].
- **Not in the mainloop profile** [SRC `pe:2349-2363`]: deliberately unbounded there.
- **Under C** [INF]: premise gone — the key ran inside `postKeyEvent`; at return the caret either moved or did not. What remains is that `gEditorState.caret` is refreshed only by the flush (next tick), so a reply that carries `state` must be emitted after the flush tick, or the state must be read directly. 151's mechanism (reply before the key ran) cannot occur. The completion name and the client's acceptance of it (B) are the visible residue.

## A2. The "first callback completes a move" rule

- **Where** [SRC]: `completePendingEditorOperation` `pe:2215-2276`; `requiredCallback` = `EditorCaretOrSelectionCallback` for a plain move, `TEXT_SELECTION` for extend (`pe:5762-5764`), `TEXT_SELECTION` for select (`pe:5974`), `INVALIDATE_VISIBLE_CURSOR` for place-caret (`pe:6099`); called from `onLokCallback` after every state-changing callback `pe:2727`. Completion string `documented-callback-<type>` `pe:2259-2273`.
- **Premise**: the effect of a posted key is observable only as a later callback; the first matching callback is taken as the key's.
- **Guards / known weakness**: SPEC E1-D, finding 018 (line navigation completion nondeterministic). The rule is forgeable by an unrelated flush — merge spec §16.1 and `extend_completion.hpp:20-30` ("a completion on the first TEXT_SELECTION would put the pre-key caret in the reply"), and finding 138 for the page-side twin [SRC].
- **Under C** [INF]: the callback after a key is no longer the key's *evidence* (the effect is at return) but is still the only thing that refreshes `gEditorState` (`pe:2614-2702`). If the drain yields between commands, every callback flushed in the tick after command N is N's (or idle layout's), so the rule becomes trustworthy and unnecessary at once. A key that moves nothing gets no callback; the "flush tick carried nothing" answer (ruling 2.8(a)2) replaces the readback.
